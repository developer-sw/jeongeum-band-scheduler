## 2. 회원·권한·팀

### 사용자 확정 정책

- 가입은 전체 관리자가 발급하는 개인별 일회용 초대를 사용한다.
- 2026-10-10 사용자 확정: 로그인은 마지막 접속 후 90일 동안 유지하고 접속 시 연장한다. 브라우저를 종료한 뒤 다시 접속해도 유효한 쿠키와 서버 세션으로 인증한다. 로그아웃·회원 비활성화·탈퇴 시 접근을 해제한다.
- 전체 관리자: 개발자, 회장·부회장·총무·매니저 등 임원진.
- 팀장: 자기 팀 범위의 관리자다. 전체 관리자 권한을 자동으로 갖지 않는다.
- 전체 관리자와 팀장 역할을 겸할 수 있다.
- 팀 생성과 팀 구성은 MVP에서 전체 관리자가 처리한다.

- 팀은 고정 멤버 단위다. 추가 곡을 위한 추가조를 구성할 수 있으며 예약 주체는 팀을 유지한다.
- 모든 활성 팀원은 자기 소속 팀 예약을 생성할 수 있다.
- 팀별 곡 목록을 제공한다. 수정 권한은 전체 관리자와 해당 팀장이다.
- 팀장이 탈퇴하면 전체 관리자가 후임을 지정한다.

## 4. 예약 주체와 점유

- 정규조와 추가조: 합주실 전체 독점. 다른 모든 예약과 겹칠 수 없다.
- 개인: 악기별로 방을 공유한다. 보컬·건반·일렉기타·베이스·드럼·통기타의 여섯 종류에 각각 같은 시간 한 건만 가능하다.
- 일반 개인 예약은 악기 한 종류만 선택한다.
- 개인 한 명의 동시간 개인 예약은 한 건만 허용한다.
- 2악기 개인 90분 예약은 묶음 교환으로 만들어지는 예외다. 최대 두 종류이며 60분 예약에는 허용하지 않는다.
- 평일 주간, 고정 배정 없는 평일 야간, 심야와 주말의 빈 시간 모두 선착순 팀·개인 예약에 개방한다.

## 5. 날짜 개방과 잔여 시간

- 한국 날짜 기준 오늘부터 오늘+14일까지, 양 끝을 포함한다.
- 매일 00시에 새 날짜를 개방한다. 고정 배정을 먼저 반영한 뒤 빈 시간을 공개한다.
- 시작 직전과 진행 중 블록의 남은 시간 예약을 허용한다.
- 예: 14:10에 B03을 선택하면 14:10~15:00을 이용한다. 별도의 14:10 자유 시간 블록을 만드는 것은 아니다.
- 종료한 블록은 새로 예약할 수 없다.

## 6. 하루 한도

- 일반 60분 예약은 개인별 또는 팀별로 하루 최대 두 블록이다.
- 개인 연습과 소속 팀 연습 시간을 합산하지 않는다. 여러 정규조·추가조 모두 각 팀을 별도 주체로 계산한다.
- 90분 예약은 이 60분 블록 한도에 합산하지 않는다.
- 관리자가 배정한 원래 위치의 60분 고정 합주는 면제다.
- 고정 합주를 단건 변경·교환으로 옮겨 만든 60분에는 일반 한도를 적용한다. 상대방이 면제를 넘겨받지 않는다.
- 진행 중 잔여 시간 예약도 60분 한 블록으로 계산한다.
- 시작 전 취소는 한도를 복원한다. 시작 후 취소는 당일 사용량에 남는다.
- 악기 수와 관계없이 60분 한 건은 60분으로 계산한다.
- 두 시간 예약은 연속된 60분 예약 두 건으로 유지한다.

## 7. 취소·변경

- 취소 권한: 예약자, 해당 팀장, 전체 관리자. 개인은 해당 회원 또는 전체 관리자다.
- 시작 전과 진행 중 취소를 허용한다. 종료된 예약은 이용 이력으로 보존한다.
- 변경은 시작 전 예약만 가능하며 동일 주체의 날짜·블록·개인 악기를 바꿀 수 있다.
- 변경 권한은 취소 권한과 같다.
- 실패하면 기존 예약과 점유·사용량을 유지한다.
- 진행 중 취소는 남은 점유를 해제한다. 이미 사용한 60분 블록 한도는 복원하지 않는다.

## 8. 반복 배정

- 정규조와 추가조 모두 관리자에게 매주 같은 시간의 고정 배정을 받을 수 있다.
- 회차별 취소·변경·교환은 그 회차에만 적용하며 다음 주 배정은 유지한다.
- 전체 고정 시간표 수정은 전체 관리자가 적용 시작일을 지정해 처리한다.
- 개별 취소·변경·교환 예외와 완료 이력은 보존한다.
- 새 고정 배정이 기존 선착순 예약과 충돌하면 배정 작업을 거절하고 충돌 목록을 보여준다. 기존 예약은 유지한다.
- 필요하면 관리자가 기존 예약을 직접 취소한 뒤 재배정한다.

## 9. 교환

- 시작 전 예약끼리 시간만 교환한다. 각자의 주체·예약자·악기는 유지한다.
- 개인↔개인, 팀↔개인, 정규조↔추가조를 허용한다.
- 한 건↔한 건은 60분·90분 길이가 달라도 가능하다.
- 연속 60분 두 건↔90분 한 건을 허용한다.
- 묶음 두 건은 같은 날짜, 연속 블록, 같은 회원/팀, 같은 예약자를 만족해야 한다. 개인 악기는 달라도 된다.
- 두 개인 60분의 악기가 다르면 교환 결과 90분 한 건이 두 악기를 전체 90분 동안 점유한다.
- 2악기 90분을 두 60분으로 교환하면 각 블록에 한 종류씩 배분하고 예약자가 순서를 선택한다.
- 2악기 90분을 단일 60분으로 변경할 때는 한 종류를 선택한다. 악기 유지가 필요한 직접 교환에서는 이 축소를 자동으로 하지 않는다.
- 상대 개인 예약자 또는 전체 관리자, 상대 팀 예약자·그 팀장·전체 관리자가 승인할 수 있다.
- 승인자는 예약 주체나 예약자로 바뀌지 않는다.
- 요청 중 기존 예약을 유지한다. 두 예약 묶음 중 가장 이른 시작 시각에 요청을 만료한다.
- 관련 예약의 변경·취소는 요청을 자동 무효화한다.
- 승인 시 제3자 예약, 현재 악기 상태, 한도와 권한을 다시 검사한다. 실패하면 양측 기존 예약·점유·한도를 유지한다.

상세한 1↔2 변환과 악기 배분, 이력 연결은 `RESERVATION_RULES`와 `ERD`에서 정의한다.

## 10. 탈퇴·팀 해체

- 팀 해체: 미래·진행 중 팀 예약 취소, 반복 배정 종료, 관련 교환 요청·예정 알림 종료.
- 회원 탈퇴: 미래·진행 중 개인 예약 취소, 관련 교환 요청·예정 알림 종료.
- 존속하는 팀의 예약은 유지한다. 탈퇴자가 생성했던 팀 예약도 같은 원칙을 따른다.
- 종료된 예약은 이력으로 보존한다.
- 팀장 후임은 전체 관리자가 지정한다.

팀에서 멤버만 제거하는 관리 기능도 존속 팀의 예약을 유지하는 방식으로 제안한다. 탈퇴 회원은 현재 권한을 상실하며 미래 알림 대상에서 제외한다. 이력 보관은 개인정보를 최소화하는 방식으로 별도 운영 관리한다.

## 11. 악기 고장

- 방 전체 차단은 필요하지 않다. 악기별 고장 상태를 관리한다.
- 고장 악기의 신규 개인 예약은 제한한다.
- 팀 합주는 고장 안내와 함께 허용한다.
- 고장 등록으로 기존 예약을 자동 취소하지 않는다.
- 원래 위치와 악기를 유지하는 기존 예약은 보존한다.
- 변경·교환으로 새로 배치하면 현재 고장 상태를 검사한다.
- 2악기 90분 취소는 두 악기의 점유를 모두 해제한다.

## 12. 공지와 알림

- 전체 관리자만 전체 공지를 작성한다. 제목·본문·중요 공지 고정을 제공한다.
- 2026-10-13 사용자 확정: 처음 중요 공지로 작성할 때만 전체 활성 회원의 알림함에 안내한다. 수정·일반 공지의 중요 전환·고정 해제/재고정은 재알림하지 않는다.
- 조별 공지는 제공하지 않는다.
- Push 구현, 사용자의 알림 허용 동선, 사이트 내 알림함을 첫 운영에 포함한다.
- 예약 생성 알림은 즉시 발송한다. 팀 예약은 해당 팀원, 개인 예약은 해당 회원에게 보낸다.
- 시작 약 한 시간 전 알림을 보낸다. 생성 시 이미 지난 알림 시점은 생략한다.
- 변경·교환은 이전 예정 알림을 무효화하고 새 시간으로 다시 설정한다.
- 탈퇴·해체 자동 취소는 교환 요청과 예정 알림도 종료한다.
- 사건별 수신자와 알림 실패·중복 처리 설계는 `NOTIFICATIONS`를 따른다.

## 13. 기술 설계 권고안

| 항목 | 권고안과 이유 |
|---|---|
| 모델 | 단일 동아리·단일 방으로 시작, 팀과 곡은 1:N |
| 인증 | 서버 세션과 HttpOnly 쿠키; Spring Session JDBC로 재시작과 다중 앱 고려 |
| 가입 입력 | 로그인 ID·비밀번호·표시 이름을 사용하는 안; 필수 이메일과 SMTP는 기본 범위에 추가하지 않음 |
| 조회 | 활성 회원만 일정·공지에 접근; 개인 정보 공개는 최소화 |
| API | `/api/v1`, 같은 origin의 `/api` 경로로 프론트와 연결 |
| 점유 | 서로 겹치지 않는 10개 블록을 직접 사용; 30분 내부 슬롯을 추가하지 않음 |
| 동시성 | PostgreSQL 주체·날짜 잠금과 점유 unique 제약, 하나의 변경·교환 트랜잭션 |
| 알림 | DB에 알림·발송 작업 저장, 커밋 이후 Push 전송; 재시도와 중복 억제 |
| 갱신 | 활성 화면 15~30초 조회, 포커스·재연결 갱신, mutation 후 invalidate |
| 오프라인 | 설치와 안내·읽기 fallback만; 오프라인 예약 변경 큐 제외 |
| Git | 단일 저장소, 안정적인 main, 기능별 브랜치, PR·CI |
| 로그 | 요청 식별자와 업무 오류 중심, 민감정보 제외 |

가입 입력·조회 시 인명 표시·초대 유효기간·기기별 로그아웃/Push 처리 같은 세부 값은 기술 제안이다. 확정 정책에 섞어 추가 운영 질문이나 개발 중단 조건으로 만들지 않는다. 사용자가 다른 방식을 원하면 관련 API·UX·보안 문서를 함께 수정한다.

### 2026-10-10 사용자 요청: 내 공연조 일정 모아보기

현재 소속된 정규조·추가조의 합주실 예약을 서버의 한국 오늘부터 실제 예약 가능 마지막 날짜까지 한 번에 조회한다. 기본 범위는 오늘~오늘+14일이며 날짜·시작 시간 오름차순, 전체 소속 공연조 또는 한 공연조 필터, 날짜·요일·시간·공연조 종류·예약 출처·현재 상태를 제공한다. 다른 팀원이 만든 소속 공연조 예약도 포함하고 개인 예약·취소된 회차는 확정 일정에서 제외한다. 취소 이력은 기존 예약 화면에서 확인한다.

일반 팀 예약과 반복 배정의 실제 확정 회차를 함께 표시한다. 아직 미개방인 날짜나 패턴만 존재하는 미래 배정은 확정 예약으로 표시하지 않는다. 별도 `/my-schedule` 페이지와 메뉴를 사용하는 것은 날짜별 생성·취소 화면을 유지하면서 여러 날짜의 일정 조회를 분리하기 위한 구현 선택이다. 기존 기간별 `scope=mine` API와 현재 소속·권한 검증을 재사용하며 신규 API·DB 테이블·예약 정책을 추가하지 않는다.

## 16. 다음 단계와 완료 기준

예약 기본 PR #6은 `cf02718`로 main에 반영했다. 사용자는 실제 로컬 DB의 최초 관리자 계정 생성을 완료했고, 정규조·추가조의 반복 고정 배정과 날짜 개방 구현을 요청했다. 이번 구현 계약과 실제 검증 결과는 [RECURRING_ASSIGNMENTS](RECURRING_ASSIGNMENTS.md)에 기록한다. 기존 관리자 계정·PostgreSQL 볼륨·세션·예약 이력을 보존하며 V1~V4 migration을 수정하지 않는다. 예약 변경·교환·알림 등의 첫 운영 필수 기능은 별도 후속 단계로 유지한다.

반복 배정 관리자 UI의 최종 브라우저 검증과 내 공연조 일정 구현·검증 결과를 보고한 뒤 사용자 승인으로 [PR #7](https://github.com/developer-sw/jeongeum-band-scheduler/pull/7)을 정식 전환·main 병합했다. 병합 커밋은 `4fccdc7`이며 [main CI](https://github.com/developer-sw/jeongeum-band-scheduler/actions/runs/38060582682)의 백엔드·프론트엔드 검증이 모두 통과했다. 데이터 변경 검증은 별도 임시 PostgreSQL의 합성 계정으로 수행했고 기존 개발 DB의 관리자·예약·Docker 볼륨을 보존했다. 최신 화면의 최종 모바일 실행 검증은 미완료이며 직접 확인 절차를 구현 문서에 기록했다.

1. 이 문서와 ERD·API·UX·테스트 설계를 서로 맞춰 검토한다.
2. GitHub·개발환경 준비 이후 사용자가 요청한 backend/frontend 초기 구성·연결을 검증한다. PR 생성·정식 전환·main 병합은 사용자 승인을 받는다.
3. 인증·팀·곡, 예약·한도, 반복 배정, 변경·교환, 화면·공지·Push를 구현한다.
4. 실제 PostgreSQL 경합, 권한, rollback, 실기기 Push, HTTPS와 백업 복원을 검증한다.
5. 필수 기능과 핵심 검증 상태를 확인하고 오픈한다.

2026-10-11 사용자가 회장 시안과 상세 다이어리 설계안에 따른 프론트엔드 리디자인을 요청했다. `codex/diary-ui-redesign` 브랜치에서 중단된 예약 공통화를 이어 달력·주간 시간표·빠른 예약·모바일 하루 카드/바텀시트, 계정·더보기와 공통 디자인을 구현·검증했다. 후속 피드백으로 흰색 상단 카드·새 기타 이미지·`STUDIO NOTE` 배지·모바일 전체 제목과 압축 행을 반영했다. 메인 소개는 작은 `JEONGEUM · SENTIMENTAL MUSIC`, 굵은 닉네임 인사말, 연한 로그인 ID·전역 역할(전체 관리자/회원)을 표시한다. 하단 사용자 문구와 기존 팀장 권한을 유지한다.

백엔드·API·Flyway·예약 정책은 변경하지 않았고 실제 DB를 보존했다. 데이터 변경 검증은 합성 계정의 별도 DB에서만 수행했다. 프론트 88건과 타입·lint·build, 최종 화면의 320~1440px 브라우저 확인을 기록했으며 이번 UI 요청에서 백엔드 114건을 재실행하지 않았다. 완료된 UI의 커밋·Push·`main` 대상 초안 PR 생성·원격 CI 확인은 사용자 승인 범위다. 새 원격 CI 결과는 다이어리 UI PR의 검사에서 확인한다. 정식 PR 전환·`main` 병합은 별도 승인 후 진행한다. 최신 완료 단계와 실제 검증·미실시 범위는 [DIARY_UI_REDESIGN](DIARY_UI_REDESIGN.md)에 기록한다.
