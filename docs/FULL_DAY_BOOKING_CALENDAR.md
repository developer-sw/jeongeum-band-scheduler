# 전일 시간 블록·선택 날짜 예약 요약

작성일: 2026-11-04, `Asia/Seoul`. **사용자 확정 요구사항의 구현 및 로컬 격리 검증 결과**다. 실제 개발/운영 DB 적용과 운영 배포는 별도 단계다.

이번 작업은 로컬 코드·문서·격리 테스트를 대상으로 한다. 기존 운영 사이트는 앞선 rc.5 배포로 오늘 포함 31일 범위를 제공한다. **이번 V13을 실제 개발/운영 DB에 적용하거나 새 앱을 운영 배포하지 않았다.** 기존 회원·팀·예약·세션·Docker 볼륨과 동결한 로컬 원본을 보존한다. 후속 사용자 승인으로 변경 검토·커밋·Push·main 대상 초안 PR·동일 HEAD 원격 CI 확인을 진행하며, 실제 DB 적용·운영 배포는 포함하지 않는다.

## 1. 확정 정책과 유지 범위

- 평일·주말 모두 `00:00~18:00`은 60분 18개 블록, `18:00~24:00`은 기존 90분 4개 블록으로 구성한다. 하루 총 22개다.
- 기존 `B01~B10`의 코드·시각·의미는 바꾸지 않는다. 새 `B11~B22`를 `00:00~12:00`의 12개 시간에 추가한다. 정확한 매핑은 [예약 운영 규칙](RESERVATION_RULES.md#2-운영-시간과-고정-블록)을 따른다.
- 시간순은 코드 문자열이나 enum 순서가 아니라 실제 시작 분/시각으로 판단한다. `B22(11:00~12:00)`와 `B01(12:00~13:00)`은 인접한다.
- 서울 오늘부터 오늘+30일까지, 양 끝을 포함한 31개 날짜를 유지한다. 31일이 모두 준비되면 날짜×블록은 `31×22=682`개다.
- 개인별·팀별 일반 60분 일일 한도는 각각 **120분**으로 유지한다. 시간이 늘어나도 한도·관리자 원래 고정 면제·변경/교환·취소 규칙을 바꾸지 않는다.
- 기존 90분 블록·개인 공유/팀 독점·반복 회차 예외·고장·권한·시작 알림 및 재시도 정책도 유지한다.
- `D일 B10`의 종료는 `D+1일 00:00`, `D+1일 B11`의 시작은 그 시각이다. 시작 포함·종료 제외를 유지하고 두 운영일의 한도를 섞지 않는다.

## 2. DB·API 계약

새 Flyway **V13**에서 시간 블록 행과 코드별 정확한 시각 제약을 확장한다. 적용된 V1~V12 migration 파일을 수정하지 않는다. 기존 블록 행·참조 FK·예약 시각 snapshot·반복 배정/회차·점유·한도 ledger·이력은 재번호 부여하거나 삭제하지 않는다. 시간 확장만으로 기존 예약을 새로 생성하거나 취소하지 않는다.

기존 API 경로와 요청/응답 구조를 유지한다. 생성·변경·교환·반복 배정은 확장된 canonical `blockCode`를 서버에서 해석한다. 일정의 `days[].blocks`는 시작 시각순 22개를 제공하며 예약·공유 악기·개방 상태·조작 권한을 계속 반환한다. 화면에서 악기 수 문구를 없애도 `availableInstrumentCodes` 등 데이터나 서버 검증을 없애지 않는다.

읽기 전용 달력 요약은 기존 schedule 응답만 사용한다. 신규 목록 API·DB 테이블·별도 기기별 Query를 추가하지 않는다. 현재 소속과 공개된 팀명/악기 코드만 사용하며 다른 개인의 이름·아이디·연락처·예약 ID를 표시하지 않는다.

운영 적용 전에는 백업/복원 실행자의 V13·22블록 계약과 기존 V12 백업 복원 호환성을 함께 검토해야 한다. 새 스키마를 허용하기 위해 출처·최소 권한·내용 검증을 생략하지 않는다.

## 3. 시간표와 빠른 예약

- PC 주간 표와 모바일 하루 목록의 모든 칸에서 `이용 가능 악기 n/6` 문구를 제거하고 칸 높이·불필요한 세로 여백을 줄인다.
- 빈 시간·예약 종류·점유/지난 시간·상세/예약 진입과 키보드 포커스는 유지한다. 필요한 악기별 상태는 예약/상세 화면에서 확인한다.
- `00~18시 60분 · 18~24시 90분`으로 안내하고 블록 선택 목록·변경/교환·관리 화면도 실제 시간순으로 정렬한다.
- 빠른 예약의 `개인은 악기 한 종류, 소속 공연조는 합주실 전체를 예약해요.` 문구를 제거한다. 실제 악기 선택·팀 독점 안내/검증과 한도는 유지한다.
- 로고·상단 계정/더보기·사용자 하단 문구 `JEONGEUM · SENTIMENTAL MUSIC`은 보존한다.
- 2026-11-04 후속: `/reservations` 예약·이력의 PC 시간표에서도 `예약 가능 악기 n/6` 문구를 제거하고 칸 패딩·버튼 위 여백을 줄인다. 고장 경고·예약 종류·시간 상태와 44px 이상 선택 버튼은 유지한다.
- 같은 화면의 날짜 선택은 모바일에서 날짜 입력을 한 줄 전체로, 이전/다음 날 버튼은 아래 동일 폭 2열로 배치한다. `sm` 이상은 기존의 날짜·이전·다음 한 줄 배치를 유지하며 날짜 입력의 최소 폭 제약을 해제한다.

## 4. 달력의 선택 날짜 예약 요약

PC 왼쪽 달력과 모바일 전체 달력에서 기존 `서울 기준 오늘부터 30일 뒤까지 (오늘 포함 31일). 이전 기록은 예약·이력에서 확인해요.` 단락을 제거하고 그 위치에 **선택 날짜 예약**을 표시한다.

- 선택 날짜의 `CONFIRMED` 예약만 시간순으로 표시한다. 해당 날짜의 이미 종료된 확정 예약도 포함하며 취소·교체 이력은 제외한다. 다른 날짜나 미개방 미래 패턴을 합성하지 않는다.
- 각 행은 시간대와 팀명 또는 개인 연습의 악기만 간단히 보여준다. 직접 고정 회차에는 짧은 `고정` 표시를 둘 수 있다.
- 같은 블록의 개인 공유 예약은 악기 목록을 모아 한 행으로 표시해 길어지지 않게 한다. 90분 두 악기 교환 예외도 같은 점유 요약으로 읽되 개인 식별정보를 추가하지 않는다.
- **현재 소속된 모든 정규조·추가조**의 합주만 색·강조 및 `내 공연조` 문구로 구분한다. 상단의 특정 공연조 강조 필터 때문에 다른 소속 팀을 누락하지 않는다. 개인 예약이나 이름이 같은 미소속 팀을 강조하지 않고 전체 관리자에게 모든 팀을 본인 팀처럼 표시하지 않는다.
- 모바일 달력에서 날짜를 선택해도 펼친 달력을 자동으로 닫지 않아 바로 아래 새 요약을 볼 수 있게 한다.
- 예약 없음, 날짜 준비 중, 아직 조회하지 못한 상태를 구분한다. 재조회 실패로 캐시를 보여주면 마지막으로 확인한 예약임을 알린다. 오프라인에서 예약 성공을 표시하거나 쓰기를 자동 재실행하지 않는다.

## 6. 운영 적용 전 남은 단계

1. 승인된 변경 검토·GitHub 게시·동일 HEAD 원격 CI 결과를 해당 초안 PR에서 확인한다. 정식 전환·main 병합은 별도 승인 단계다.
2. 합성 운영 컨테이너의 **새 58항목 전체 검사**와 **실제 V13 암호화 백업·독립 복원**을 수행한다. 위 백업 계약 테스트를 실제 dump/복원 성공으로 확대하지 않는다.
3. 실제 V13 적용 **전에** 새 V12/V13 대응 백업·복원 도구와 승인된 출처 pin을 서버에 먼저 설치·검증한다. 기존 비공개 복원 실행기의 이전 SHA pin이나 과거 암호문 출처를 조용히 바꾸지 않는다.
4. 승인 후 새 원본 백업·독립 복원과 기존 데이터 대조를 거쳐 실제 DB V13·이미지 배포·후속 백업 및 설정 복구본 갱신을 수행한다. 새 B11~B22 예약이 생긴 뒤에는 이를 읽지 못하는 구 Backend 이미지로 단순 롤백할 수 없다. 쓰기 중단·복원 시점과 이후 예약 보존 방안을 포함한 복구 절차가 필요하다.

**이번에 실제 개발/운영 DB migration·운영 배포·AWS 설정/데이터 변경·실회원 시험 예약은 실행하지 않았다.**
