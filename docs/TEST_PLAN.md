## 1. 목표와 우선순위

첫 운영 필수 범위인 초대·인증·팀·팀 곡·고정 일정·예약·한도·변경·교환·공지·알림함·Push를 검증한다. 포트폴리오용 테스트 수보다 실제 중복 예약·권한 우회·부분 교환·알림 오발송을 막는 증거를 우선한다.

**P0 배포 조건:** 서버 정책·권한·동시성·전체 롤백·운영 데이터 복원·실제 모바일 주요 흐름을 확인한다. 검증하지 못한 항목은 미검증으로 기록하고 테스트 통과로 표시하지 않는다. 2026-10-30은 목표일이며 테스트 실패를 목표일 때문에 성공으로 간주하지 않는다.

**P1 운영 점검:** 일일 회차 생성·알림 worker 재시작·Push 실패 정리·모바일 가독성·로그·비용·운영 종료 처리를 검증한다. 필수 기능 자체를 P1이라는 이유로 첫 운영에서 제외하지 않는다.

## 4. 60분 블록 하루 한도

- 개인 회원별·팀별 하루 120분을 별도로 검사한다. 개인 120분이 해당 팀의 120분을 자동 소비하지 않는다.
- 같은 날짜 60분 두 건은 성공하고 일반 세 번째 60분은 거절한다. 진행 중 블록 신청도 잔여 분수로 한도를 줄이지 않는다.
- 한 회원이 여러 팀에서 예약해도 팀별 사용량을 정확히 구분한다. 예약 작성자를 팀 한도 주체로 잘못 사용하지 않는다.
- 관리자 고정 배정의 면제를 서버 출처로 판단한다. 일반 예약 요청에서 면제 플래그를 보내 한도를 우회할 수 없다.
- 시작 전 취소는 한도를 복구한다. 진행 중 취소는 이미 소비한 사용량을 유지한다. 종료된 예약은 취소하지 않고 이용·소비 이력을 보존한다.
- 진행 중 취소자는 60분 사용량을 유지하고, 잔여 시간을 새로 예약한 다른 회원은 본인의 60분 사용량을 소비한다.
- 날짜 이동·60↔90 변경·교환에서 양측 최종 60분 배치를 계산한다. 자기 source의 기존 사용량을 잘못 중복 가산하지 않는다.
- 원래 관리자 고정 회차·위치의 60분만 면제다. 실제 단건 변경·교환으로 이동한 60분은 일반 사용량을 소비하며, 상대도 면제를 얻지 않는다. no-op 요청은 원래 면제를 유지한다.
- 이미 다른 60분 예약이 있는 상대에게 120분 묶음이 도착해 한도가 초과하면 교환 전체를 거절한다.

## 5. 변경·취소·계보

단건 변경의 실행 기록은 [RESERVATION_CHANGES](RESERVATION_CHANGES.md)를 따른다. `ReservationChangeIntegrationTest`는 격리 PostgreSQL에서 원본·점유·quota·operation·lineage·회차·멱등 기록의 집계 상태를 실패 전후 대조한다. 원본은 시작 전이어야 하며 목적지는 종료 전 잔여 시간도 허용한다. 개인 owner 비활성화는 관리자 대리 새 변경도 막고, 존속 팀의 비활성 최초 작성자는 이력으로 유지한다. 완료 재시도는 새 날짜 개방이나 후속 예약을 만들지 않는다.

V6는 빈 테스트 DB에서 전체 Flyway 적용과, 데이터가 있는 V1~V5 DB의 V6 업그레이드를 구분해 검증한다. 실제 개발 DB에 V6를 적용하거나 계정·예약 fixture를 넣지 않는다. 실제 PostgreSQL 잠금으로 시작 경계 통과·10초 timeout·동시 변경/취소/예약/한도/고장 경합을 확인하며 timeout 후 원본을 유지하는지 대조한다. 프론트는 권한·no-op·원본 사용량 제외·다른 주체의 관리자 한도·불확실한 동일 요청 재시도와 성공 후 공통 Query 갱신을 검사한다.

## 6. 교환과 개인 두 악기 예외

2026-10-12 교환 구현 검증은 [RESERVATION_EXCHANGES](RESERVATION_EXCHANGES.md)에 실행 결과·미검증 항목을 기록한다. 실제 개발 DB는 V1~V6 상태로 보존하고 V7·시간 제어·경합·쓰기 검증은 별도 PostgreSQL에서 수행한다.

- 60↔60, 60↔90, 90↔90, 연속 두 60↔90을 실제 최종 점유로 검증한다. 정규조·추가조·개인 조합에서 같은 검사 원칙을 적용한다.
- 두 60분 묶음은 같은 날 연속, 같은 개인/팀, 같은 creator 조건을 확인한다. 관리자·팀장의 권한이 있어도 서로 다른 creator 조건을 우회하지 않는다.
- 다른 악기의 개인 60분 두 건이 90분에 도착하면 두 악기를 90분 전체 동안 점유한다. 전반·후반으로 자동 분할하지 않는다.
- 두 악기 예외 90분이 두 60분에 도착하면 해당 개인 예약자가 직접 선택·저장한 순서대로 각 블록 하나를 배정한다. 순서 누락·중복·허용 외 악기 선택은 거절한다. 전체관리자의 승인 권한과 개인 악기 배분 권한을 구분하고, 미선택 상태에서는 관리자도 승인 완료할 수 없다.
- 한 악기 90분이 두 60분에 도착하면 각 블록에 같은 악기 하나를 유지한다.
- 두 악기 예외는 90분에서 최대 두 종류다. 일반 신규 개인 예약·일반 한 악기 예약에 예외를 위조할 수 없다.
- 예외 90→다른 90 일반 변경에서는 악기 선택·교체, 점유·고장 검증을 확인한다. 예외 90→단일 60 일반 변경은 한 악기 선택을 요구한다.
- 두 악기 예외 90↔단일 60 직접 교환은 거절한다. 먼저 한 악기로 변경한 경우와 두 60분 경로의 허용 여부를 구분한다.
- 개인↔팀 교환에서 팀의 전체 독점이 도착 위치의 제3자 개인 예약과 충돌하면 전부 거절한다. 상대 예약만 비웠다는 이유로 나머지 자원을 무시하지 않는다.
- 대기 요청 중 원래 예약·점유는 유지한다. 승인 전 실제 배치는 이동하지 않는다.
- 승인 시 source 전 건·현재 버전·양측 권한·소속·활성 상태·시각·자원·한도를 재검증한다.
- 가장 이른 source 시작 직전 승인은 조건을 만족하면 성공, 해당 시작 시각부터는 만료로 거절한다.
- 관련 예약 변경·취소, 요청자 권한 상실, 개인 탈퇴에 따른 실제 예약 취소, 팀 해체 후 해당 이전 요청을 승인할 수 없다. 같은 요청 중복 승인은 추가 계보·알림을 만들지 않는다.
- 상대 승인 후보 한 명만 팀장·소속 권한을 잃으면 그 사람의 승인은 403이지만 요청을 자동 무효화하지 않는다. 다른 적법한 예약자·팀장·전체관리자는 현재 조건을 검증받아 승인할 수 있다.
- N:M 교환에서 원본·후속 계보, 예약 주체·creator 유지, 새 실제 길이와 면제 출처를 확인한다.
- 첫 범위에 없는 두 건 묶음↔두 건 묶음 등 다른 교환 모양을 직접 API 호출로 추가할 수 없다.

## 7. 실제 PostgreSQL 동시성·전체 롤백

테스트는 독립 DB 연결과 독립 트랜잭션으로 동시에 시작한다. 시작 장벽과 종료 제한시간을 사용하고 실제 경합이 발생했는지 확인한다. 각 작업이 같은 테스트 트랜잭션을 공유하거나 전체가 순차 호출되는 상황을 동시성 테스트 성공으로 보고하지 않는다.

| ID | 경합 | 검증할 불변조건 |
| --- | --- | --- |
| X01 | 여러 사용자의 같은 자원·날짜·블록 생성 | 정확히 하나 성공, 나머지 충돌; 성공 알림도 한 업무 결과 |
| X02 | 다른 자원 개인 예약 동시 생성 | 자원이 다르면 필요한 예약 모두 성공 |
| X03 | 전체 합주 생성과 개인 생성 경합 | 최종 상태에 전체 합주와 개인 점유 공존 없음 |
| X04 | 한 회원의 같은 블록 다른 악기 생성 경합 | 최대 개인 예약 한 건 |
| X05 | 같은 개인/팀의 잔여 하루 한도를 넘는 서로 다른 블록 동시 생성 | 점유는 달라도 120분 초과 없음 |
| X06 | 생성과 고장 상태 변경, 고정 회차 생성과 자유 예약 경합 | 최종 정책·충돌 처리 일관성, 조용한 덮어쓰기 없음 |
| X07 | 변경 또는 교환 승인과 제3자 예약 생성 | 최종 전체 배치에 중복 없음; 패자는 원래 상태 유지 |
| X08 | 같은 요청 중복 승인, 같은 source가 포함된 다른 요청 동시 승인 | 최대 한 유효 적용; 중복 후속 예약·업무 알림 없음 |
| X09 | 승인과 source 취소·탈퇴·해체 경합 | 결정된 순서에 맞는 상태, 권한 상실 후 잘못된 추가 승인 없음 |
| X10 | 일일 회차 생성 worker 두 개 동시 실행 | 실제 회차·예외·생성 이벤트 중복 없음 |
| X11 | Push worker 두 개와 변경·취소 경합 | 중복 DB 알림 없음, 이전 버전 시작 알림의 발송 조건 재검증 |
| X12 | 서로 다른 전체 관리자가 서로 다른 팀에 개방 범위 밖의 같은 미래 요일·블록 고정 패턴을 동시 등록 | 날짜 행 유무와 관계없이 패턴 하나만 성공, 상대는 충돌; 미래 중복 배정 없음 |
| X13 | 날짜 개방·고정 회차 생성과 주간 패턴 수정 경합 | recurring_schedule_guard와 날짜 잠금의 순서 준수, 최신 패턴 재검증, 고정 반영 전 자유 시간 공개 없음 |

묶음 교환은 두 번째 또는 마지막 후속 점유 생성에서 의도적으로 충돌·실패하도록 구성한다. 실패 후 **source 전체, 점유 전체, 사용량 전체, 교환 상태, 계보, 알림함, outbox, 시작 알림 계획**이 부분 성공 상태로 남지 않는지 확인한다. mock이 예외를 던졌다는 사실만으로 DB 롤백을 증명하지 않는다.

경합 시 내부 DB 제약 오류가 사용자에게 원문으로 노출되지 않고 일관된 API 오류가 되는지도 검사한다. 교착 상태·타임아웃은 무한 대기 대신 정해진 실패 또는 안전한 제한 재시도로 끝나야 한다.

## 8. 반복 일정·악기 사용 중지

반복 배정 단계의 실제 실행 결과와 회차 경계·날짜 개방 계약은 [RECURRING_ASSIGNMENTS](RECURRING_ASSIGNMENTS.md)에 기록한다. 가변 Clock과 실제 PostgreSQL을 사용해 서울 자정, 시작/종료 경계, 동일 날짜 중복 worker, V4 데이터 보존과 V5 적용, 예외 tombstone, 미래 패턴 경합, preview 후 최종 충돌 rollback을 검증한다. 악기 고장 관리와 변경·교환 API는 후속 단계이며 계획 목록을 구현 완료로 취급하지 않는다.

실제 worker 활성화 상태의 별도 3개 JVM과 합성 PostgreSQL에서도 등록된 서울 자정 cron을 제어된 시각으로 실행하고, 10초 실제 잠금 timeout의 전체 rollback·비공개 날짜 유지, 등록된 60초 catch-up의 자동 재시도, 재시작 누락/PREPARING 복구와 중복 방지를 확인했다. 개발 PC의 시스템 시각이나 실제 개발 DB를 조작하지 않았다. 일반 수정·종료 화면의 VERSION_CONFLICT 후 명시 갱신, 동일 미래 적용일의 최신 revision 선택, 종료일을 넘는 예정 패턴 오표시 방지는 프론트 회귀 검증에 포함한다.

- 같은 주간 패턴과 날짜를 반복 생성해도 회차가 하나만 존재한다. 한국 자정에 새 +14일 회차가 생성되고 자유 예약보다 고정 점유가 먼저 확정된다.
- 단일 회차 변경·교환·취소 후 일일 생성 작업을 재실행해도 원래 시간이 되살아나지 않는다.
- 전체관리자의 반복 패턴 적용 시작일 변경이 시작일 전 회차·기존 단일 예외·계보를 손상하지 않는다. 일반 회원·팀장은 반복 패턴을 바꿀 수 없다.
- 새 고정 배정이 이미 존재하는 자유 예약과 충돌하면 조용한 삭제·덮어쓰기를 하지 않는 오류 처리를 검증한다. 구체 충돌 응답은 API 설계 제안을 따른다.
- 고장 악기의 신규 개인 예약은 거절하고 다른 정상 악기는 예약할 수 있다. 고장 하나가 합주실 전체 폐쇄로 취급되지 않는다.
- 기존 개인·팀 예약은 사용 중지 등록 때문에 자동 취소되지 않는다. 팀 전체 예약은 고장 경고를 표시한다.
- 기존 고장 자원 예약의 no-op 요청은 유지된다. 실제 시간·자원 재배치는 현재 정책을 검증한다.
- 복구 후 신규 개인 예약 가능 상태, UI 가용 상태, server 검증이 일치한다.

### 관리자 고장 등록·복구·이력과 V8

`codex/instrument-incidents`의 계약과 실제 검증 결과는 [INSTRUMENT_FAULTS](INSTRUMENT_FAULTS.md)를 따른다. 실제 개발 DB의 V7·계정·예약·볼륨은 보존하며 아래 쓰기·실패 주입·업그레이드는 임시 PostgreSQL의 합성 데이터에서만 검증한다.

- 전체 관리자 등록·복구와 실행자·시각·사유/메모·버전·커서 이력, 비회원·일반 회원·팀장·권한 상실·CSRF·계약 외 필드·입력 경계를 확인한다.
- 동일 키 재확인·본문/경로 키 재사용 거절, 이미 고장/복구된 상태·오래된 버전·한 악기 열린 이력 한 건을 확인한다.
- 실제 PostgreSQL 동시 고장 등록·복구·개인 신규/이동·교환 승인, 권한 변경 잠금 대기, 부분 쓰기 실패와 10초 timeout 전체 롤백·재시도를 확인한다.
- 기존 예약·점유·quota·회차·대기 교환의 값이 고장 등록·해제 전후 보존되는지 대조한다. 고장 중 no-op·팀·반복 배정의 허용과 개인 새 배치 차단을 함께 검증한다.
- populated V7→V8에서 모든 기존 테이블·컬럼·Flyway 이력·세션과 assets NORMAL/FAULTY·버전을 보존하고, LEGACY를 원래 등록자/시각으로 오인하지 않는지 확인한다. 재기동·마이그레이션 재실행 0건·validate를 확인한다.
- 프론트는 관리자 접근·등록/복구 확인·입력·오래된 버전 새로고침·같은 본문/키 응답 유실 재확인·계정/권한 캐시 제거와 PC/모바일 레이아웃을 확인한다.

## 9. 인증·인가·팀·곡·공지

- 미인증 예약·변경·교환·관리 API, 잘못된 로그인, 초대 방식 우회와 중복 초대 사용을 검사한다.
- 허용된 일정·교환 정보와 현재 권한 범위를 넘는 다른 개인 예약 상세·개인정보 조회 및 변경을 차단한다. 다른 사용자의 알림·Push 구독 ID를 직접 지정한 조회·변경도 차단한다.
- 비소속·비활성 회원은 팀 예약을 생성할 수 없다. 소속 일반 팀원은 생성 가능하지만 다른 creator의 변경·취소·교환 요청은 불가하다.
- 한 회원의 여러 정규조·추가조 소속을 허용하고 같은 팀의 활성 멤버십 중복은 거절한다. 정규조 두 팀에 동시에 등록해도 서로 다른 멤버십이 유지되는지 실제 PostgreSQL 경합 테스트로 확인한다. 팀별 예약 한도는 다른 소속 팀·개인 한도와 합산하지 않는다.
- 여러 팀 소속에서 한 팀의 팀장 권한이 다른 팀으로 전파되지 않는지 검사한다. A팀 팀장·B팀 일반 팀원은 A팀 곡만 수정할 수 있으며, 전체 관리자 권한은 별도로 검사한다.
- 가입 전 명단의 여러 소속·팀장 배정이 개인 초대 가입 후 같은 계정에서 조회되는지 검사한다. 동명이인·표시 이름 변경은 연결 기준이 아니며 공개 초대 확인에서 명단·팀 정보가 노출되지 않는다.
- 명단 일대일 연결·기존 계정 연결과 가입의 경합, 기존 계정 중복 연결, 같은 명단의 초대 중복·재발급 ID 계승·해지 경합을 실제 PostgreSQL로 검사한다. 실패하면 계정·명단·초대 상태를 함께 롤백한다.
- 역할·팀장·소속 변경을 기다린 뒤 현재 권한을 다시 검사한다. 마지막 활성 전체 관리자 강등, 오래된 version의 명단·팀·곡 수정, 다른 팀 경로로 곡 ID를 바꾼 요청을 거절한다. 역할 감사 이력과 자기 팀 밖의 명단 비노출을 확인한다.
- 해당 팀장·전체관리자의 기존 예약 관리와 상대 측 승인 권한을 검사한다. 요청자 자신이 상대 승인자 역할을 위조할 수 없다.
- 생성 당시 조원이었더라도 요청·승인 직전 탈퇴·비활성·팀장 해제됐으면 현재 권한을 적용한다. 과거 로그인 세션의 낡은 권한만 사용하지 않는다. 요청자 권한 상실과 승인 후보 한 명의 권한 상실이 전체 요청에 미치는 차이를 검사한다.
- 회원 탈퇴 시 미래·진행 중 개인 예약과 실제 취소·요청자 권한 상실로 영향을 받는 대기 교환 정리를 확인하고, 존속하는 팀 예약은 보존한다. 상대 승인 후보 한 명만 탈퇴한 경우 다른 승인자의 처리 경로가 유지된다. 팀 해체는 관련 미래·진행 중 팀 예약·교환을 정리하고 과거 이용 이력은 보존한다.
- 팀 곡 CRUD는 전체관리자·해당 팀장만 가능하다. 다른 팀장·일반 조원의 직접 API 수정은 거절한다. 팀명·곡명·공지 입력의 검증과 XSS 렌더링을 확인한다.
- 관리자 API·중요 공지 기능·악기 관리의 권한을 직접 호출로 검사한다. 프론트 메뉴를 숨긴 사실로 테스트를 대체하지 않는다.
- 쿠키 인증 설계의 CSRF·CORS·로그아웃·세션 만료·계정 전환을 실제 보안 필터로 확인한다. secret·password hash·구독 키가 응답과 로그에 노출되지 않는다.
- 90일 로그인 유지: 실제 PostgreSQL에서 로그인 쿠키의 `Max-Age`·`Expires`·보호 속성, 새 클라이언트의 쿠키 복원, 30분을 넘는 유휴 후 인증, 인증 요청의 DB·쿠키 만료 연장, 90일 만료 거절을 검사한다. 만료되지 않은 기존 30분 세션과 로그인 전 CSRF 세션도 90일로 전환한다. 같은 DB로 앱을 재시작해 세션을 복원하고, 로그아웃·비활성·탈퇴 응답이 연장 쿠키를 재발급하지 않으며 이전 쿠키 재사용이 거절되는지 검사한다. 시간 경과는 DB의 접근·만료 시각을 조정해 재현하고 임의 장시간 sleep을 사용하지 않는다.

## 10. 알림·worker·Push

### 회원 탈퇴·팀 해체 정리 V11

`codex/member-team-lifecycle`의 계약과 실제 실행 결과는 [MEMBER_TEAM_LIFECYCLE](MEMBER_TEAM_LIFECYCLE.md)을 따른다. 실제 개발 DB V10과 관리자·예약·볼륨을 유지하며 종료·실패 주입·업그레이드는 격리 PostgreSQL의 합성 계정/데이터에서 검증한다.

- 관리자·CSRF·입력/version·마지막 활성 관리자·동일 키 재확인/다른 요청 재사용과 현재 권한을 검사한다.
- 미래/진행 중 개인·팀 예약 취소, 종료 이력·최초 예약자·계보·존속 팀 예약, 시작 전 quota 복원/시작 후 소비·점유를 대조한다.
- 팀장 공석·소속 종료·모든 세션/기기 해제와 로그인 최종 저장/새 예약/변경/교환/반복 개방 경합을 확인한다.
- 관련 대기 교환만 정리하고 다른 승인 후보·팀/회원 상태를 보존한다. 해체 전 활성 수신자 확보·탈퇴자 제외·기존 알림함·존속 팀 계획 보존을 검사한다.
- 후반 INSERT 실패와 실제 10초 잠금 timeout의 전체 rollback·동일 요청 재시도, V10→V11 기존 데이터 보존을 확인한다.
- 관리자 확인 화면·PC/모바일·응답 유실 뒤 같은 원래 요청 재확인·오프라인 쓰기 차단·다이어리 UI 보존을 검사한다.

### 공지·알림함 V9 이번 구현 검증

- 관리자 공지 생성·수정·고정 변경·soft delete, 현재 계정/역할·CSRF·버전·입력 제한·일반 텍스트를 실제 HTTP로 확인한다. 일반/비활성 회원의 쓰기를 직접 API로 차단한다.
- 처음 중요 공지로 작성할 때만 활성 회원별 한 건이 생성되고 일반 작성·수정·중요 전환·고정 해제/재고정·동일 키 재시도에서는 추가 생성되지 않는다. 삭제 후 참조·재시도 기록을 보존한다.
- 공지 중요/시각/ID cursor와 본인 알림의 ID cursor·미읽음 필터·건수, 다른 수신자 ID 거절·읽음 멱등·전체 읽음 기준 시각·미래 기준 거절을 검증한다.
- 예약·실제 고정 회차 CREATED, 단건 CHANGED/CANCELED, 교환 요청/완료/거절/철회/만료/무효화의 개인/활성 팀/요청자 수신자와 중복 제거를 검증한다. 전체 관리자에게 무조건 발송하지 않는다.
- no-op·성공 재시도·회차 재개방·교환 후속 행 생성의 중복 알림을 막는다. 마지막 알림 INSERT 실패와 실제 PostgreSQL 잠금 timeout 시 업무 데이터·알림·재시도 기록이 함께 롤백되는지 확인한다.
- 합성 값을 채운 V8→V9에서 기존 모든 테이블·컬럼·Flyway·세션·예약/교환/고장 상태를 보존하고 migration 재실행 0건·validate를 확인한다. 실제 개발 DB에는 V9를 적용하거나 검증용 공지·알림·예약을 만들지 않는다.
- PC·모바일 공지/알림함과 중요 최초 안내·확인·권한 차단·계정 전환·오래된 항목 이동·응답 유실 동일 키 재확인을 격리 환경에서 검사한다. 실제 Push·시작 알림 worker·실기기·운영 준비 완료로 확장 보고하지 않는다.

아래 worker·Push 항목은 2026-10-14 구현의 검증 기준이다. V9 알림함 기록은 [NOTICES_NOTIFICATIONS](NOTICES_NOTIFICATIONS.md), V10·Push·시작 계획·CSRF 동시 초기화의 실제 결과와 실기기 제한은 [WEB_PUSH_REMINDERS](WEB_PUSH_REMINDERS.md)에 별도로 기록한다.

- 논리 예약 생성만 CREATED, 변경은 CHANGED, 교환은 EXCHANGED로 처리한다. 후속 예약 행 생성으로 중복 CREATED가 생기지 않는다.
- 팀 활성 조원 전체와 개인 본인 수신자를 검사한다. 같은 사용자의 여러 역할은 한 이벤트로 중복 제거한다. 알림 수신자가 승인 권한을 얻지 않는다.
- 고정 회차 생성 즉시 알림을 만든다. 재실행은 중복하지 않는다. Push 일괄 요약을 채택하면 건별 알림함 보존과 즉시 처리 여부를 검증한다.
- 1시간 전 시각이 미래인 생성·변경만 새 계획을 등록한다. 이미 지난 시각·진행 중 예약은 생성/변경 알림만 제공한다. 동일 시각 경계 처리도 API 계약대로 검사한다.
- 미래 시작 알림 계획을 저장했다고 시작 알림함 항목이 미리 노출되지 않는다. due 시점의 유효성·수신자 검증 후 알림함과 발송 작업을 생성한다.
- 변경·취소·교환 시 이전 계획 무효화와 새 계획을 검증한다. 같은 논리 예약 계보·실제 시작 시각의 이미 보낸 시작 알림을 후속 ID 때문에 재발송하지 않는다.
- 트랜잭션 실패 시 알림함·outbox가 생성되지 않는다. Push 실패는 예약 성공을 되돌리지 않는다.
- worker 재시작·중복 실행·발송 후 처리기록 전 중단·일시 오류·만료 endpoint를 검증한다. DB 알림은 중복되지 않고 외부 표시 중복 가능성은 기록·완화한다.
- 탈퇴·비활성·팀 소속 변경 후 대기 Push 수신자를 다시 확인한다. 존속 팀 예약의 creator 탈퇴만으로 다른 조원의 예정 알림을 종료하지 않는다. 팀 해체 결과 안내에 필요한 관련 당사자 정보가 사라지지 않는다.
- 중요 공지는 전체 활성 회원에게 전달한다. 일반 공지 Push는 확정되지 않은 범위를 자동으로 확대하지 않는다.
- 알림 읽음 처리와 구독 등록·해제는 본인만 가능하다. 한 기기에서 계정 전환 시 이전 계정 Push 연결이 남지 않는다.

## 11. 중요한 브라우저·실기기 흐름

### 내 공연조 일정 자동화·브라우저 검증

| 시나리오 | 확인할 결과 |
|---|---|
| 공연조 하나·복수 소속 | 현재 소속 전체 또는 선택한 팀 일정만 표시; 다른 팀원이 만든 팀 예약도 포함 |
| 일반/고정 통합 | MANUAL과 실제 FIXED 예약을 한 목록에 표시; 개인·취소·교체·미개방 패턴은 제외 |
| 패턴 수정·회차 취소 | 최신 실제 예약 시간으로 갱신, 취소한 회차만 제외, 다음 주 회차 유지 |
| 날짜·시간·상태 | 서버 today~bookableThrough의 OPEN 날짜, 날짜/시작 시간 오름차순, 확정/진행 중/종료 구분 |
| 팀 필터·빈 상태 | 현재 소속만 선택 가능, 결과가 없으면 안내와 시간표 연결 |
| 일정 선택 | `/reservations?date=YYYY-MM-DD`의 해당 날짜와 기존 상세/취소 권한 적용 |
| 접근·계정 변경 | 미로그인 차단, 미소속 예약 제외, 다른 계정/소속 변경 후 이전 Query 초기화 |
| PC·모바일·회귀 | 가로 overflow 없이 시간/팀/출처 읽기, 기존 예약 생성·취소와 관리자 흐름 유지 |

프론트 단위 테스트는 목록 선택·정렬·OPEN/소속/상태 필터와 기간 API 요청·Query 갱신을 확인하고, 실제 브라우저 검증은 별도 임시 PostgreSQL의 합성 계정으로 수행한다. 기존 실제 개발 DB 예약은 검증 fixture로 변경하지 않는다. 최신 실행 수치와 성공/미실시 범위는 [RECURRING_ASSIGNMENTS](RECURRING_ASSIGNMENTS.md)의 6절에 기록한다.

1. 모바일과 PC에서 같은 날짜·자원의 상태와 정책을 확인하고 화면 전환이 API·mutation을 중복 실행하지 않는지 확인한다.
2. 일반 신규 개인 예약은 악기 하나, 교환 예외는 정확히 두 개까지 선택하게 한다. 90→두 60 배정 순서를 확인한다.
3. 남은 시간·60분 사용량·고장 경고·시작 직전 변경 금지·교환 만료·권한 상실의 메시지를 확인한다.
4. 두 사용자 화면에서 생성·취소·변경 후 polling/focus/refetch로 반영되는지, 충돌 후 재선택할 수 있는지 확인한다.
5. 모바일에서 시간·자원·긴 팀명·곡명이 잘리지 않고 가로 표 축소에 의존하지 않는지 확인한다. 터치·키보드·대비·하단 안전 영역을 확인한다.
6. iPhone Safari 홈 화면 앱, Android Chrome에서 설치·standalone·권한 허용·거절·실제 업무 Push·알림 클릭 후 최신 상태를 확인한다.
7. 미설치·미허용·오프라인·재연결에도 수신함과 정책이 일관적인지 확인한다. 오프라인 예약 변경 자동 제출은 없어야 한다.
8. 로그아웃·다른 계정 로그인 후 이전 데이터·알림·service worker 캐시가 노출되지 않는지 확인한다.

실제 기기 검증을 브라우저 화면 크기 에뮬레이션만으로 완료했다고 기록하지 않는다. 테스트 참여자와 기기는 운영 준비 체크리스트에서 확보한다. 지금 추가 시간 확보 질문을 요구하지 않는다.

### 다이어리 UI 최신 검증 (2026-10-11)

`codex/diary-ui-redesign` 로컬 최종 검사에서 Frontend 11개 파일·88건, 타입·ESLint·Next production build를 통과했다. 격리 DB의 실제 브라우저로 로그인·초대 가입·0/1/복수 소속·계정 전환·공유/팀 예약·취소·한도·불확실 응답 동일 요청 재확인·권한 회수·세션 만료와 기존 관리/일정 화면을 확인했다. 375~1920px 실제 viewport 8개에서 3단/2단/하루 10개 카드 전환과 가로 넘침 없음, modal Tab/Shift+Tab·Escape·포커스 복원을 확인했다. 실제 개발 DB 26개 테이블 건수·해시와 Flyway V1~V5·기존 관리자·Docker 볼륨을 보존했다.

후속 사용자 화면 피드백을 반영한 최종 화면은 작은 `JEONGEUM · SENTIMENTAL MUSIC`·굵은 닉네임 인사말·연한 로그인 ID/전역 역할을 표시한다. 모바일은 전체 제목·`STUDIO NOTE` 배지와 소개·계정·더보기 행을 유지한다. 최종 인사말 수정 후 프론트 88건·타입·lint·build를 통과했고, 격리 DB 합성 관리자·회원으로 실제 320/375/390/768/1440px에서 가로 넘침 없음·계정 안내 한 줄·계정 전환 후 이전 정보 비노출을 확인했다.

이번 UI 요청에서 백엔드는 변경/테스트 재실행하지 않았고 기존 JUnit 114건 결과를 확인했다. 실제 iOS/Android·가상 키보드·200% 확대·스크린리더·offline 전환·PWA/Push·운영 검증을 통과한 것으로 간주하지 않는다. 제어된 proxy 409/502/503과 실제 API 방어 검사를 구분한 시나리오·수정 파일·증빙·직접 확인 절차는 [DIARY_UI_REDESIGN](DIARY_UI_REDESIGN.md)을 따른다. 커밋·Push·`main` 대상 초안 PR·새 원격 CI 확인은 사용자 승인 범위이며, 새 원격 CI 결과는 다이어리 UI PR의 검사에서 확인한다. 정식 전환·`main` 병합은 별도 승인 후 진행한다.

## 12. 배포·백업·운영 종료 체크리스트

2026-10-10 최신 검증에서 Backend 114건(반복 배정 31건·기본 예약 31건), Frontend 66건(반복 배정 15건·내 공연조 일정 9건 포함), 타입·lint·양쪽 production build를 통과했다. 격리 DB 실제 백업 복원, 실제 서버 시작·종료·재시작과 개발 DB Flyway V1~V5·계정/예약/볼륨 보존도 확인했다. UI 단계 최종 대조는 세션을 제외한 24개 테이블이 동일했으며 세션 테이블 변화(7→8개)는 별도로 기록했다. 제어된 자정 cron·실제 잠금 timeout·자동 재시도와 관리자 UI, 내 공연조 일정의 최신 실행 기록 및 미검증 항목은 [RECURRING_ASSIGNMENTS](RECURRING_ASSIGNMENTS.md)의 6절을 따른다. 아래 운영 체크리스트의 완료를 뜻하지 않는다.

- [ ] 실제 도메인 HTTPS, 로그인·쿠키·CSRF, 내부 앱→PostgreSQL 연결과 health 확인.
- [ ] 빈 DB migration 적용 및 기존 버전에서 업그레이드 확인; 적용된 migration 수정 없이 진행.
- [ ] 초대·회원·팀·팀장·팀 곡·반복 시간표·6자원 기초 데이터 확인.
- [ ] 예약 생성·변경·교환·공지·수신함·Push를 운영과 같은 설정으로 smoke test.
- [ ] 애플리케이션 재시작 후 고정 회차·예외·대기 교환·시작 알림·outbox 유지 확인.
- [ ] 백업 파일에서 격리 DB로 복원하고 예약·점유·한도·계보·공지·알림 건수와 조회 확인.
- [ ] 복원 환경은 외부 Push 발송을 끄고 실제 사용자에게 과거 업무를 재발송하지 않게 설정.
- [ ] 로그·오류·반복 실패 알림·DB 저장량·비용 확인 경로 문서화.
- [ ] 2026-12-11 종료 시 신규 예약·미래 Push·worker 정리, 최종 백업·복원 확인·문서 보존.
- [ ] 유료 서버/DB 리소스 종료와 잔여 과금 확인; 백업 보존 위치·접근 권한 확인.

검증 기록에는 수행 일시, 환경·버전, 시나리오, 성공/실패/미검증, 필요한 화면 또는 로그 증거와 해결 상태를 남긴다. 운영 사용자 개인정보는 테스트 데이터·포트폴리오 자료에 그대로 포함하지 않는다.
