# UX 및 반응형 화면 설계

작성 기준: 2026-10-10, Asia/Seoul. 사용자 로고·남색·노란색과 하단 `JEONGEUM · SENTIMENTAL MUSIC` 문구를 유지한다. 인증 화면은 [AUTHENTICATION](AUTHENTICATION.md), 명단·팀 화면은 [MEMBER_TEAM_MANAGEMENT](MEMBER_TEAM_MANAGEMENT.md), 이번 일정·생성·취소 화면은 [RESERVATION_FOUNDATION](RESERVATION_FOUNDATION.md)을 따른다. 변경·교환·반복·공지·Push UI와 배포는 후속 단계다. 아래에서 **확정 정책**과 **UI 제안**을 구분한다. 예약 정책·권한의 상세 계약은 [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md), [RESERVATION_RULES.md](RESERVATION_RULES.md), [API.md](API.md)를 함께 확인한다.

## 1. 목표와 첫 운영 범위

2026-10-10 확정된 로그인 유지는 마지막 접속 후 90일이며 서버 요청 때 연장한다. 로그인 화면에 유지 기간과 공용 기기 로그아웃 안내를 표시한다. 브라우저 재실행 시 쿠키와 서버 세션을 먼저 확인해 현재 회원을 복원하고, 만료·로그아웃·회원 비활성화 시 기존 캐시를 비운다. 비밀번호나 별도 인증 토큰을 브라우저 저장소에 보관하지 않는다.

- 하나의 Next.js 코드베이스로 모바일과 PC를 지원한다.
- 첫 운영에 초대·인증·권한, 팀·팀별 곡 목록, 관리자 반복 일정, 예약·취소·변경·교환, 공지, 알림함, Web Push를 포함한다.
- 구현 시작 목표는 2026-10-23, 첫 배포 목표는 2026-10-30, 운영 종료 목표는 2026-12-11이다. 구현 7일은 목표이며 검증된 소요일수는 아니다. 배포 목표일부터 종료일까지 운영 기간은 6주다.
- 모바일은 날짜 선택과 하루 목록, PC는 주간 시간표를 사용한다. API 호출·예약 정책·Query 계층은 공유한다.

## 2. 브랜드와 화면 구성 제안

서비스 표기는 정음 / JEONGEUM을 사용한다. 사용자가 제공한 정음 로고와 네이비·노란색·흰색을 디자인 기준으로 삼는다. 정확한 색상 값과 아이콘 변형은 화면 시안 단계에서 확인한다.

| 요소 | UI 제안 |
| --- | --- |
| 배경·내용 영역 | 흰색 또는 밝은 중립색, 내용 구획을 명확히 분리 |
| 주요 글자·헤더 | 네이비 |
| 예약 실행·강조 | 노란색 배경과 짙은 글자 |
| 예약 상태 | 색상과 함께 가능·팀 합주·개인 사용·사용 중지 문구 표시 |
| 로고 | 로그인과 헤더 중심으로 사용; 작은 조작 버튼에는 명료한 글자·아이콘 사용 |
| 모바일 탐색 | 하단에 예약·내 일정·공지·내 정보, 헤더에 알림함 접근 |
| PC 탐색 | 상단 또는 좌측 탐색, 넓은 주간 일정과 보조 영역 |

로고 원본이나 사용자 안내 문구를 기존 참고 프로젝트에서 가져오지 않는다. 새로운 디자인 시스템 전체나 다크 모드는 첫 운영 필수 범위에 추가하지 않는다.

## 3. 주요 화면과 데이터 접근

활성 회원 인증을 기본 조건으로 하는 기술안을 제안한다. 일정·다른 팀 곡·인명 읽기 범위는 아래의 읽기 제안이며 외부 공개 시간표를 승인한 뜻이 아니다. 버튼 노출은 편의 기능이며 모든 쓰기 권한은 서버에서 재검증한다.

| 화면·행동 | 확정 권한 또는 읽기 제안 |
| --- | --- |
| 초대·로그인 | 초대·인증 정책에 따른 진입; 비활성 회원은 예약 사용 불가 |
| 일정 조회 | 읽기 제안: 활성 회원 내부 조회, 팀명·악기 점유 표시 |
| 일반 개인 예약 생성 | 활성 본인만 |
| 일반 팀 예약 생성 | 해당 팀에 소속된 활성 팀원 모두 |
| 개인 예약 변경·취소·교환 요청 | 본인 또는 전체관리자 |
| 팀 예약 변경·취소·교환 요청 | 활성·소속 검증을 통과한 작성자, 해당 팀장, 전체관리자 |
| 교환 승인·거절 | 상대 개인 예약자 또는 전체관리자; 상대 팀 예약 작성자·해당 팀장·전체관리자 |
| 팀별 곡 목록 추가·수정·삭제 | 전체관리자와 해당 팀장 |
| 팀별 곡 목록 읽기 | 활성 회원 내부 조회 제안; 외부 공개 없음 |
| 공지 | 전체관리자 작성·수정·중요 공지 고정; 활성 회원 내부 조회 제안 |
| 알림함·Push 구독 | 본인의 데이터만 조회·변경 |
| 반복 일정·악기 관리 | 전체관리자 |

전체관리자의 미소속 팀 일반 예약 대리 생성은 확정된 권한에 추가하지 않는다. 관리자 반복 배정 기능과 일반 예약 생성 권한을 구분한다.

**인명 노출 제안:** 시간표는 팀명·악기 점유를 먼저 보여준다. 다른 회원의 개인 예약은 기본적으로 악기 사용 상태를 표시하고, 연락처·로그인 식별자는 반환하지 않는다. 자신의 예약과 소속 팀 상세에는 필요한 표시 이름을 제공한다. 다른 팀의 전체 명단 공개 범위는 예약 생성 정책과 별개인 읽기 설계 제안이다.

## 4. 예약 화면

### 공통 데이터

상위 화면이 공통 schedule 조회 함수와 Query를 호출하고 DesktopSchedule / MobileSchedule에 동일한 응답을 전달한다. 주 단위 Query를 사용할 경우 모바일은 선택한 날짜만 추출한다. 화면 크기를 바꿔도 예약 요청 형식·권한·한도 계산이 달라지지 않는다.

조회에는 기준 날짜, 예약 블록, 각 자원의 점유·사용 중지, 팀 독점 사용, 본인의 조작 가능 여부, 서버 기준 시각과 예약 가능 범위를 포함하는 계약을 제안한다. 상세 예약과 팀 개인정보는 별도 권한 계약으로 조회한다. 숨겨진 두 UI 컴포넌트가 각각 API를 호출하는 구조를 피한다.

### 전 요일 공통 블록: 확정

| 블록 | 시간 | 길이 |
| --- | --- | --- |
| B01 | 12:00~13:00 | 60분 |
| B02 | 13:00~14:00 | 60분 |
| B03 | 14:00~15:00 | 60분 |
| B04 | 15:00~16:00 | 60분 |
| B05 | 16:00~17:00 | 60분 |
| B06 | 17:00~18:00 | 60분 |
| B07 | 18:00~19:30 | 90분 |
| B08 | 19:30~21:00 | 90분 |
| B09 | 21:00~22:30 | 90분 |
| B10 | 22:30~24:00 | 90분 |

평일·주말에 동일하게 적용한다. 시간 직접 입력, 자유 길이 선택, 드래그로 임의 구간 생성은 제공하지 않는다. 24:00은 표시용이며 서버의 끝 시각은 다음 날 00:00으로 처리한다.

### 모바일 제안

1. 오늘·이전/다음 날짜·날짜 선택기를 표시한다.
2. 선택한 날의 10개 블록을 세로 카드로 표시한다.
3. 각 카드에 시간, 6자원 상태, 전체 합주 여부와 예약 버튼을 둔다.
4. 일반 개인 예약은 사용 가능한 악기 하나를 선택한다. 두 악기 예외는 일반 신규 예약 폼에서 노출하지 않는다.
5. 팀 예약은 정규조·추가조 모두 합주실 전체 독점이다. 팀 사용 시간에는 개인 예약 버튼을 비활성화한다.

6자원은 보컬·건반·일렉기타·베이스·드럼·통기타다. 서로 다른 회원의 개인 예약은 서로 다른 자원으로 같은 블록을 공유할 수 있다. 한 회원의 동시간대 개인 예약 두 건은 허용하지 않는다.

### PC 제안

주간 7열과 고정 블록 10행으로 비교한다. 팀 독점은 팀 카드로, 개인 공유는 자원 상태를 간결하게 표시하고 상세에서 확인한다. 선택 날짜·예약 확인·내 다음 일정 등을 보조 영역에 배치한다. 60분·90분 행을 같은 높이로 그릴 경우 실제 시간 길이가 다름을 시간 레이블로 명확히 표시한다.

기본은 모바일, 태블릿은 하루 목록 중심, 넓은 화면은 주간 표현으로 확장한다. 가로 스크롤에 의존하지 않고 예약 상태를 글자와 함께 읽을 수 있게 한다. 하단 고정 탐색을 사용하면 iPhone 안전 영역과 내용 하단 여백을 처리한다.

## 5. 생성·한도·진행 중 예약

예약 가능 날짜는 한국 기준 오늘부터 14일 뒤까지다. 새 날짜는 00:00에 열린다. 반복 고정 회차가 먼저 적용되고 남은 시간은 평일·주말 모두 선착순이다.

서버가 블록 종료 전이라고 판단하면 시작한 블록의 잔여 시간도 예약할 수 있다. 예: 12:25에는 정해진 12:00~13:00 블록을 선택해 지금부터 13:00까지 사용한다. 확인 화면에 **예약 블록 12:00~13:00 / 이용 가능 약 35분 / 당일 60분 블록 사용량 60분**을 함께 표시한다. 임의 12:25~13:25 예약으로 바꾸지 않는다.

60분 블록의 하루 한도는 개인 회원별 120분, 팀별 120분으로 별도 계산한다. 관리자 고정 배정의 원래 회차·위치에서 사용하는 60분만 면제다. 이를 단건 변경·교환으로 옮긴 60분에는 일반 한도를 적용한다. 교환 상대나 도착한 시간대에 면제가 옮겨 붙지 않는다. 같은 날짜·블록·악기의 실질 변경 없는 요청은 원래 면제를 유지한다. 화면의 한도는 참고 정보이고 제출 시 서버가 최종 검증한다.

생성 흐름은 날짜·블록 → 개인/소속 팀 선택 → 악기 또는 전체 합주 확인 → 사용 가능 시간·한도·고장 경고 확인 → 서버 요청 → 확정 결과다. 서버 성공 전에는 예약 완료로 표시하지 않는다. 충돌 응답에서는 최신 점유를 다시 조회하고 선택 가능한 상태를 보여준다.

## 6. 취소와 변경

| 행동 | 동작 |
| --- | --- |
| 시작 전 취소 | 점유 해제, 해당 한도 사용량 복구, 기존 시작 알림 무효화 |
| 진행 중 취소 | 이력·이미 소비한 60분 한도 보존, 잔여 시간 점유 해제 |
| 종료된 예약 | 취소·변경 불가; 완료된 이용 이력 보존, 지난 시간 재예약 불가 |
| 일반 변경 | 원래 예약 시작 전만 가능; 새 시간·자원의 정책과 권한을 재검증 |
| 고정 회차 변경·취소 | 해당 날짜 회차만 변경; 다음 주 반복 패턴은 유지 |

진행 중 취소 후 잔여 시간 재예약은 진행 중 취소 허용과 잔여 블록 예약 허용에서 도출한 처리다. 취소자의 이미 소비한 한도와 새 예약자의 사용량은 각각 별도 보존·계산한다.

변경은 원래 예약자·팀을 유지한다. 실패하면 원래 예약이 유지되어야 한다. 기술 제안은 원본을 REPLACED 이력으로 보존하고 후속 예약을 만드는 방식이다. 기존 예약 ID의 상세에서 후속 예약 안내 또는 권한 확인 후 이동을 제공한다. 실행자가 관리자·팀장이더라도 creator를 실행자로 바꾸지 않는다. 변경 사건은 CHANGED이며 후속 행의 CREATED 알림을 추가로 보내지 않는다.

동일 날짜·블록·악기의 no-op 변경은 예약을 교체하지 않고 기존 고장 등록 전 예약 지위·면제·대기 교환·알림 계획을 그대로 유지한다. 해당 회차의 변경·취소·교환 결과를 일일 고정 회차 생성 작업이 원래 시간으로 되돌리지 않는다. 반복 패턴 자체의 변경은 전체관리자가 적용 시작일과 기존 예외를 확인하는 별도 화면으로 처리한다.

## 7. 교환 사용자 흐름

1. 변경 권한이 있는 시작 전 예약을 선택한다. 두 60분 묶음은 같은 날 연속, 같은 개인/팀, 같은 작성자여야 한다. 개인의 두 예약은 악기가 달라도 된다.
2. 상대 예약을 선택한다. 정규조·추가조·개인 간 교환을 지원하되, 양쪽 최종 자원 점유·한도·개인 중복 조건을 만족해야 한다.
3. 양쪽의 기존 시간과 도착 시간, 길이 변화, 유지되는 팀/회원·악기를 함께 보여준다. 120분과 90분 교환에서 이용시간이 달라짐을 명시한다. 두 악기 90분이 두 60분으로 나뉘면 해당 개인 예약자가 직접 악기 순서를 선택·저장한다.
4. 상대 측에 요청한다. 대기 중에는 원래 예약을 유지한다.
5. 상대의 승인 권한자는 서버의 최신 미리보기를 확인하고 승인 또는 거절한다. 필요한 개인 악기 순서가 미선택이면 승인을 완료할 수 없다. 전체관리자도 개인의 순서를 대신 선택하지 않고 저장된 배분을 사용한다.
6. 승인 성공 후 전체 변경 결과를 보여준다. 일부만 교환된 성공 상태를 만들지 않는다.

모든 source 예약에 대한 요청자 권한을 확인한다. 승인은 상대 측 권한을 별도로 확인한다. 다른 일반 팀원이 알림을 받았다고 승인 권한이 생기지는 않는다. 악기 배분은 해당 개인 예약자에게만 제공하는 PATCH /api/v1/exchange-requests/{id}/instrument-allocation 기술 계약을 따른다. 처음부터 두 건 묶음끼리의 2↔2 교환을 추가하지 않는다.

요청은 관련 source 중 가장 이른 시작 시각에 만료된다. 시작 시각에 도달한 경우 승인할 수 없다. 관련 예약 변경·취소, 요청자의 권한 상실, 개인 탈퇴에 따른 실제 개인 예약 취소, 팀 해체는 요청을 무효화한다. 상대 승인 후보 한 명이 역할·소속을 잃었다는 이유만으로 요청 전체를 무효화하지 않는다. 해당 사람의 승인 시도는 403으로 거절하고 다른 적법한 예약자·팀장·전체관리자의 승인 경로는 유지한다. 화면에는 대기·승인 완료·거절·만료·무효화와 사유를 구분한다.

교환의 원본과 후속 예약은 N:M 계보로 연결하는 기술안을 따른다. 응답의 후속 예약 목록으로 화면과 Query를 갱신한다. 후속 행마다 CREATED를 추가 발송하지 않고 하나의 논리 EXCHANGED 사건으로 안내한다.

### 개인 악기 예외: 확정

| 상황 | UI와 서버 규칙 |
| --- | --- |
| 일반 신규 개인 예약 | 60분·90분 모두 악기 한 종류 |
| 서로 다른 악기의 60분 두 예약이 교환으로 90분에 도착 | 한 예약에서 기존 두 악기 모두 90분 전체 점유; 최대 두 종류 |

| 두 악기 예외 90분을 다른 90분으로 일반 변경 | 같은 예약 주체 유지, 최대 두 악기 범위에서 선택·교체 가능; 점유·사용 중지 재검증 |

## 8. 팀·곡·운영 상태

팀 상세에 팀 종류·팀장·소속 상태·팀별 곡 목록·다음 예약을 표시한다. 곡 목록은 팀별 제목과 선택 아티스트 정도의 단순 목록으로 설계한다. 공용 곡 카탈로그·음원 검색·곡별 예약 주체는 추가하지 않는다. 곡 CRUD 버튼은 전체관리자와 해당 팀장에게만 노출하며 API도 같은 권한을 검사한다.

한 회원의 여러 정규조·추가조 소속을 목록으로 표시하고 예약할 소속 팀을 선택하게 한다. 정규조 선택을 단일 소속 입력으로 제한하지 않는다. 팀장 여부와 곡 수정 버튼은 선택한 팀의 현재 멤버십을 기준으로 판단한다.

이번 회원·팀 단계는 `/admin/members`에서 가입 전 명단 생성·이름 수정·기존 계정 연결과 전체 관리자 역할 변경을 제공한다. 명단에는 미가입·연결된 계정을 구분해 표시하고, 계정 연결 전에 선택한 명단과 로그인 ID를 확인한다. 초대 발급 화면에서는 미가입 명단을 선택한다. 이름으로 명단·계정을 자동 연결하지 않는다. `/teams`는 팀 목록·내 소속을, `/teams/[id]`는 팀별 소속·팀장·곡 목록과 권한에 맞는 작업을 제공한다. 다른 팀 일반 회원에게 내부 명단·로그인 ID를 공개하지 않는다. 가입 전 팀장 배정은 로그인 권한을 만들지 않으며 연결된 활성 계정에서만 권한이 생긴다.

개인 탈퇴 시 해당 개인의 미래·진행 중 개인 예약과 그 취소에 연관된 교환, 요청자 권한 상실에 해당하는 교환을 정리하되 존속하는 팀 예약은 일괄 취소하지 않는다. 팀 예약의 작성자가 탈퇴했을 때는 팀장·전체관리자의 관리와 다른 활성 조원의 예정 알림을 유지한다. 그 작성자가 상대 승인 후보였다는 이유만으로 유효한 대기 교환 전체를 종료하지 않는다. 팀 해체는 관련 미래·진행 중 팀 예약과 대기 교환 정리 결과를 보여준다. 이력 조회에서 현재 존재하지 않는 회원·팀 때문에 화면이 깨지지 않게 한다.

악기 사용 중지는 합주실 전체 폐쇄가 아니다. 개인 새 예약과 새 배치의 자원 검증에 적용하고, 팀 전체 합주에는 고장 악기를 명시해 경고한다. 기존 예약은 유지하고 사용 중지 상태를 보여준다. 유지된 기존 예약을 화면에서 자동 취소하지 않는다.

## 9. 공지·알림함·설치 흐름

전체관리자만 전체 공지를 작성하며 제목·본문·중요 공지 고정을 제공한다. 조별 공지는 추가하지 않는다. 공지 목록과 상세에서 중요 공지를 구분하고 상단에 고정한다. 중요 공지 알림은 전체 활성 회원에게 전달한다. 일반 공지의 Push 범위는 [NOTIFICATIONS.md](NOTIFICATIONS.md)의 확정 이벤트 표와 제안을 따른다.

알림함은 Push 설치·허용 여부와 관계없이 이용할 수 있다. 알림에서 예약·교환·공지 상세로 이동하고, 최신 상태가 달라졌으면 현재 상태를 함께 표시한다. 이미 무효화된 요청의 오래된 알림에서 승인할 수 없도록 한다.

PWA는 manifest·아이콘·standalone·service worker·오프라인 안내·Web Push를 포함한다. Next.js App Router의 manifest 지원을 사용할 수 있다. [Next.js 공식 PWA 가이드](https://nextjs.org/docs/app/guides/progressive-web-apps)

기능 지원을 확인하고 사용자가 알림 켜기 버튼을 눌렀을 때 권한을 요청한다. iPhone은 홈 화면 추가 → 설치된 앱 실행 → 알림 켜기 순서로 안내한다. iOS Web Push의 홈 화면 앱과 사용자 동작 조건을 반영한다. [WebKit 공식 설명](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

예약 변경을 오프라인 대기열에 저장해 재접속 때 자동 제출하지 않는다. 오프라인에서는 연결 안내를 보여주고, 재접속 시 점유·권한을 갱신한다. service worker의 인증 데이터 캐시·계정 전환 처리는 [NOTIFICATIONS.md](NOTIFICATIONS.md)를 따른다.

## 10. 갱신·오류·접근성 제안

- 예약 화면이 보일 때 15~30초 polling, 화면 복귀·네트워크 재연결 시 refetch, 본인의 변경 성공 후 관련 Query invalidate를 제안한다. invalidate만으로 다른 사용자의 화면이 갱신되지는 않는다. [TanStack Query 공식 문서](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)
- Push는 일정 데이터의 최종 상태가 아니다. 알림 클릭과 화면 복귀 시 API를 다시 조회한다.
- 401은 재로그인, 403은 현재 권한 설명, 예약 충돌은 재조회, 한도 초과는 서버 계산값 표시로 처리한다. 상세 오류 코드·상태는 API 계약에 맞춘다.
- 이중 제출 버튼을 막되 서버의 동시성 검증을 대체하지 않는다. 응답을 잃은 요청은 무작정 다시 생성하지 않고 최신 예약과 요청 결과를 확인한다.
- 터치 영역·본문 크기·키보드 탐색·포커스 복원·색상 대비를 확인한다. 상태 전달을 색상에만 의존하지 않는다.
- 정음 로고, 모바일 설치, 교환 미리보기, 고장 경고, 남은 시간 표시를 실제 기기 점검 항목에 포함한다. 검증 계획은 [TEST_PLAN.md](TEST_PLAN.md)를 따른다.
