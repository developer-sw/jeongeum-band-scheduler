# 실제 데이터 이전·공개 전환

## 2026-10-29 실행 기록

사용자는 실제 데이터 이전·공개 전환을 승인했고, 실제 회원·명단·팀·예약 데이터의 기존 서울 비공개 S3 운영 경로 암호화 백업·PC 독립 복원도 명시 승인했다. 공개 직전 확인도 완료했다. 새 설정 암호문의 PC 밖 추가 사본은 사용자 선택으로 제외하며 완료로 표시하지 않는다.

원본 앱의 쓰기를 동결하고 **12:01 KST** 새 최종 암호문을 만든 뒤 새 격리 PostgreSQL에 독립 복원했다. 원본 개발 PostgreSQL은 정상 중지 상태로 데이터·볼륨·자격증명·재시작 정책을 보존한다. 운영 쓰기가 시작된 뒤에는 원래 로컬 앱을 다시 열어 두 원본으로 사용하지 않는다.

기존 서버의 같은 PostgreSQL 컨테이너·볼륨에 후보 DB를 복원했다. 앱 미기동 상태에서 전체 행·29시퀀스·Flyway V1~V12·집계·관계 무결성·최소 앱 소유권을 대조한 후 후보를 기존 운영 DB 이름으로 전환했다. 기존 초기화 DB는 별도 이름과 같은 OID로 보존했다. 기존 운영 백업의 컨테이너·볼륨·DB 이름·역할 바인딩은 유지한다.

엄격한 schema 문자열 지문은 다르다. [준비 단계](DATA_MIGRATION_PREPARATION.md)의 40개 literal 배열 cast와 한 개 OR 괄호 결합 차이에 한정해 전체 metadata 동등성을 확인했고, 실제 엔진의 배열 33종·OR 27조합도 통과했다. 문자열 지문 자체가 같았다고 보고하지 않는다.

**16:22:13 KST** 새 실제 데이터 hourly 백업은 **16:22:16 KST** 원격 검증을 마쳤다. 정확한 S3 version을 PC로 내려받아 새 엔진·볼륨에 독립 복원하고 최종 원본의 전체 행·시퀀스·Flyway·집계·무결성·논리적 schema와 다시 대조했다. 검증 컨테이너는 중지하고 볼륨은 보존했다. 기존 weekly는 이전 빈 운영 DB일 수 있어 새 weekly 검증으로 확대하지 않는다.

rc.3 고정 이미지와 기존 비밀 설정을 재사용했다. 내부 앱 기동·DB health·로그인 화면·비로그인 보호 API 401·설치 이름 `정음`·Apple 아이콘·PNG 크기·manifest·서비스 워커를 확인했다. 세션 정리와 별도로 나머지 37테이블·29시퀀스·Flyway 지문의 기동 전후 보존과 기존 백업 지표 발행·신선도도 확인했다.

**실제 예약 앱 공개 전환을 완료했다:** https://bandjeongeum.studio/ . HTTPS 인증서를 정상 검증하고 앱 health·보호 API 401·보안 헤더·API/HTML `no-store`를 확인했다. 기존 준비 edge는 중지하여 보존했다. 사용자가 기존 계정으로 로그인하고 전체 관리자 권한·등록 명단·팀이 모두 정상임을 직접 확인했다.

Push 기능·반복 날짜 개방을 먼저 켜고 교환 만료·시작 알림 계획·Push 발송 순서로 기존 Backend만 재생성했다. **5개 기능/worker 플래그 모두 ON**, 15일 예약 날짜 개방 준비와 누락 계획·기한 지난 교환/시작 알림 작업의 정상 복구를 확인했다. 복구 시 활성 구독·Push 발송 대기는 없었으며 수동 업무 DML·실회원 대상 시험 공지는 실행하지 않았다. 이후 새 기기 등록은 가능하다.

활성화 후 **22:45:36 KST** 시작한 새 실제 데이터 hourly 백업은 **22:45:39 KST** 원격 검증을 마쳤다. 단발 systemd 백업 성공·새 snapshot 시각·신선한 감시 지표와 최종 앱/DB health·5개 플래그·날짜 개방·작업 복구 상태를 다시 확인했다. 이 새 백업을 PC에서 다시 복원한 결과로 확대하지 않으며 PC 독립 복원은 앞서 대조한 16:22 snapshot의 증빙이다. 기존 weekly가 이전 DB일 수 있다는 제한도 유지한다.

## 공개 과정의 보완과 복구 설정

- 비root Caddy가 읽어야 하는 공개 설정 2파일만 Linux `0644`로 조정했다. 비밀파일 내용·권한은 유지했다.
- upstream의 HTML 캐시 헤더가 edge 정책을 덮는 현상을 수정했다. `common.caddy`의 Cache-Control 3개에 지연 적용(`header >Cache-Control`)을 사용했고 실제 운영 Caddy validate/reload와 응답을 확인했다. HTML/API는 `no-store`, 정적 자산은 기존 immutable 정책이다. HSTS 검증은 같은 1년 정책에 `includeSubDomains`가 추가된 응답도 허용하며 실제 보호를 약화하지 않았다.
- 첫 worker 활성화에서 기존 Backend의 불투명 metadata 해시가 달랐다는 실패 증빙을 보존했다. 이전 Backend의 전체 metadata 원문을 저장하지 않아 최초 해시 일치라고 주장하지 않는다. 대신 이미지 기본값·렌더링한 Compose의 전체 환경변수·명령·사용자·healthcheck·자원 제한·읽기 전용 파일시스템·권한·정확한 비밀 bind/네트워크/로그 설정을 실제 컨테이너와 대조했다. Backend 밖 기존 자원·DB 인증·볼륨 보존도 확인했다. 다음 3회 활성화는 이 명시적 계약과 안정화한 전체 metadata의 전후 대조를 모두 통과했다.
- 최종 5개 플래그와 캐시/공개 설정을 포함한 **선택 34파일** 설정 복구본을 새 age 암호문으로 저장했다. 별도 Windows age 인증·새 폴더 실제 복원·내용/ACL 검사·임시 평문 정리와 실제 서버의 전체 내용/Linux 소유권·모드 aggregate 일치를 확인했다. Windows 복원을 Linux 소유권 재현이나 새 VM 재난 복구 성공으로 확대하지 않는다. 기존 암호문·복구키를 보존하며 새 암호문의 PC 밖 사본은 사용자 선택으로 미룬다.

## 보존·후속 검증

- 공개 시점부터 정상 사용자 쓰기가 생길 수 있다. 장애 시 최신 운영 데이터를 먼저 보존하며 오래된 로컬 dump로 덮어쓰지 않는다.
- 날짜 복구·교환 만료·시작 알림 계획과 시간표 GET은 정상 업무 쓰기다. 최초 snapshot 대조와 활성화 후 변경을 구분한다.
- 새 기기 등록은 이전 알림함을 소급 Push로 보내지 않는다. 복구 시점의 활성 구독에는 새 outbox가 생길 수 있으므로 구독·대기 작업을 확인하고 발송 worker를 마지막에 활성화한다. 기존 이력·중복 방지 키를 임의 삭제하지 않는다.
- 원본 DB·보존 DB·볼륨·암호문·실패 증빙을 삭제하지 않는다. 복구 개인키는 서버에 전송하지 않는다. 실제 회원/예약 집계·계정·행 지문·민감 설정은 Git 문서에 넣지 않는다.
- 운영 origin에서 iPhone/Android 홈 화면 재설치·기기 Push 수신/클릭은 후속 실제 기기 검증이다. 이전 합성 QA 결과나 worker 활성화를 운영 기기 수신 성공으로 보고하지 않는다.
- 이번 실행의 설정 보완과 기록은 로컬 미커밋 상태다. GitHub 게시·원격 CI·새 이미지 발행은 수행하지 않았다. 업무 코드와 rc.3 고정 이미지는 재사용했으며 전체 앱 회귀 테스트를 이번 실행에서 다시 돌린 것으로 보고하지 않는다.
