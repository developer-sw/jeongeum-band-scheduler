# 31일 예약 범위·모바일 상단 더보기 운영 배포 절차

작성일: 2026-11-04, `Asia/Seoul`. **실행 전 계획**이며 아래 단계의 성공을 미리 뜻하지 않는다.
사용자는 31일 예약 범위와 모바일 상단 더보기의 운영 배포를 요청했다.
업무 정책은 [예약 기간 확장](../docs/BOOKING_WINDOW_EXPANSION.md),
기존 배포·복구 계약은 [배포 절차](../docs/FRONTEND_RELEASE_ROLLOUT.md)와
[실제 데이터 이전 기록](../docs/DATA_MIGRATION_CUTOVER.md)을 따른다.

## 1. 대상과 보존 경계

- 예약 가능 기간은 서울 오늘부터 오늘+30일까지, 양 끝을 포함한 31개 날짜다.
- 모바일 상단 설명 줄 오른쪽에 배경 없는 굵은 계정·더보기 링크를 나란히 표시한다.
- 11월 3일 마지막 확인 시 운영은 15일 범위이며 Frontend rc.4, Backend·Caddy rc.3이다.
- 실제 배포 대상은 새 Backend와 Frontend 두 서비스다. 발행된 새 Caddy는 적용하지 않는다.
- 기존 PostgreSQL 컨테이너·DB·볼륨·자격증명·역할, Caddy·TLS·공개 네트워크를 보존한다.
- 기존 회원·명단·팀·예약·세션·Flyway V1~V12와 중지·동결한 예전 개발 원본을 보존한다.
- 추가 AWS 자원·유료 서비스·VM 재부팅·DB 초기화·데이터 이전은 이 배포에 포함하지 않는다.
- 새 migration은 없다. 기존 migration 강제 재적용이나 스키마 지문 검증 생략은 하지 않는다.

## 2. 소스·CI·이미지 발행

1. 이 절차를 검토한 배포 브랜치에서 게시하고 저장소의 승인 규칙에 따라 main에 반영한다.
2. **최종 최신 main SHA의 push CI 7개 job이 모두 성공**했는지 확인한다.
   Backend·Frontend·합성 컨테이너·발행 계약·백업 보호·운영 DB 백업·secret 권한을 포함한다.
3. 발행 도구의 정확한 main/push CI 가드를 유지한다. 문서만 바뀐 이전 main의 CI가 없다고
   과거 SHA를 현재 SHA처럼 취급하거나 수동 CI의 이벤트를 push로 바꾸어 기록하지 않는다.
4. 원본 저장소의 `release-images.yaml`을 main에서 수동 실행한다.
   예정 입력은 `version=v1.0.0-rc.5`, `visibility=public`, `publish=true`다.
   기존 버전이 이미 존재하면 출처·digest를 대조하고 충돌을 해결하기 전 발행하지 않는다.
5. 같은 main의 Backend·Frontend·Caddy 세 이미지를 한 번 빌드하고 같은 이미지로 합성 QA를 수행한다.
   candidate의 archive·QA SHA와 이미지 ID를 검증한 뒤 같은 실행에서 발행하며 재빌드하지 않는다.
6. 기존 SHA/version tag를 덮거나 삭제하지 않는다. 부분 실패는 원래 candidate를 유지하고
   같은 실행의 실패 job 재실행 절차를 사용한다. 기존 이미지와 실패 증빙도 보존한다.
7. 최종 `release.json`·`release.env`의 run·SHA·version·공개 범위·세 digest와 artifact SHA를 대조한다.
   registry의 version/SHA/manifest 참조·config digest·OCI 출처 label·Linux amd64를 확인한다.
   성공한 준비 job만으로 발행 완료를 선언하거나 candidate를 운영 입력으로 사용하지 않는다.

발행 가드는 [도구](../scripts/production-image-release.mjs)와
[기존 발행 계약](../docs/PRODUCTION_IMAGE_RELEASE.md)을 따른다. 발행 자체는 서버 배포가 아니다.

## 3. 운영 사전 점검과 읽기 전용 영향 예측

1. 정확한 기존 서버·Compose 프로젝트·서비스/이미지·mount·볼륨·DB 역할과 5개 플래그를 확인한다.
   현재 상태가 마지막 증빙과 다르면 정상 운영 변경인지 먼저 분리하고 이전 계약을 덮어쓰지 않는다.
2. 현재 서울 날짜와 운영의 `bookableThrough`를 확인해 실제 추가 구간을 정한다.
   기존 15일 범위가 유지되었다면 오늘+15일부터 오늘+30일까지 16개 날짜다.
3. 읽기 전용 DB snapshot에서 반복 패턴·적용 기간·팀 상태·회차 예외·기존 생성 회차를 조회한다.
   추가 날짜별 예상 회차·점유와 활성 수신자·기기 구독·대기 작업의 영향을 비공개로 계산한다.
4. 실제 날짜 개방 서비스나 시간표 GET은 누락 회차를 생성할 수 있으므로 예측 수단으로 실행하지 않는다.
   정상 알림 생성·Push 대기 작업·시작 1시간 전 계획까지 포함하며 단순 패턴 수만으로 확정하지 않는다.
5. 예측에 필요한 자료가 부족하거나 충돌·실패 날짜·예상 밖 대량 알림이 있으면 원인을 해결한 뒤 진행한다.
   실제 회원 이름·예약 상세·구독 endpoint·계정별 집계를 공개 문서나 로그에 넣지 않는다.

기간 확장은 기존 고정 회차의 실제 생성이며 알림함·Push·시작 계획이 함께 생길 수 있다.
알림을 조용히 생략·지연하거나 새로운 요약/일괄 발송 정책으로 바꾸지 않는다.

## 4. 변경 전 새 백업과 독립 복원

1. 기존 운영 백업 lock·source guard·최소 권한·비공개 목적지를 사용해 새 암호화 snapshot을 만든다.
2. S3 응답의 정확한 version·크기·SHA와 원격 재다운로드 검증, 최신 감시 지표를 확인한다.
3. 해당 암호문을 PC의 새 격리 PostgreSQL 엔진·빈 DB·전용 볼륨에 독립 복원한다.
   현재 운영 DB나 보존한 로컬 원본에 덮어쓰지 않고 복구 개인키를 서버에 전송하지 않는다.
4. 같은 snapshot의 테이블 내용·시퀀스·Flyway·무결성·최소 소유권과 schema 계약을 대조한다.
   원래 허용한 제한된 논리적 schema 동등성은 문자열 지문 일치와 구분한다.
5. 복원 성공·정확한 원본 바인딩·복구 경로를 확인하고 이전 이미지/설정/백업 상태를 보호 사본으로 남긴다.

백업과 복원 중 운영은 변할 수 있다. 서로 다른 시각의 live DB를 전체 행 불변으로 비교하지 않는다.
백업 도구의 실패 시 이전 성공 보존·감시와 기존 hourly/weekly 보존 정책을 유지한다.

## 5. Backend·Frontend 교체

1. 검증한 두 이미지를 고정 manifest digest로 미리 pull하고 실행 이미지의 출처·config를 재확인한다.
2. 원래 Compose·secret·권한·자원 제한을 보존하며 두 이미지 참조만 검토된 새 값으로 준비한다.
3. 새 Frontend는 기존 15일 서버 응답을 지원한다. Frontend 교체·health 확인 후 Backend를 교체해
   전환 중 화면/API 범위 불일치를 줄이고, 정지 시간과 작업 시작/완료 시각을 기록한다.
4. 기존 프로세스를 정상 종료하고 의존 서비스를 재생성하지 않는 서비스 한정 교체를 사용한다.
   `down -v`·전체 스택 재생성·PG/Caddy 재시작·동시 구/신 Backend 실행은 하지 않는다.
5. 기존 5개 기능/worker의 최종 활성 상태와 알림 정책을 유지한다. 새 Backend 기동 직후부터
   날짜 개방·누락 계획 복구·교환 만료·Push 발송이 실행될 수 있음을 반영해 관측을 시작한다.
6. 임시 정지나 재개가 필요하면 대상·시각·이전/최종 상태를 명시하고 이전 lease/작업을 보존한다.
   실행 제어를 알림 생략 정책으로 바꾸거나 작업/중복 방지 키를 삭제해 성공 처리하지 않는다.

서비스 교체가 정상 업무 쓰기를 완전히 동결하는 것은 아니다. 최신 운영 데이터를 먼저 보존한다.

## 6. 공개 앱·데이터·worker 확인

- HTTPS 인증서·health·비로그인 보호 API·캐시/보안 헤더와 기존 관리자 로그인/권한을 확인한다.
- 서버 `today`와 `bookableThrough`가 서울 오늘~오늘+30일이며 준비된 날짜만 OPEN인지 확인한다.
- 추가 날짜의 회차·점유·알림/시작 계획을 예측과 대조하고 중복·예외 재생성·실패 날짜를 확인한다.
- 기존 회원·팀·권한·세션·예약 계보·Flyway·볼륨 보존과 정상 날짜 개방/worker 변경을 구분한다.
- 재조회·복구 실행 후에도 고정 회차·대기 작업이 중복 생성되지 않는지 현재 상태와 이력으로 확인한다.
- 모바일 제목/배지 한 줄·설명 줄의 계정/더보기·투명 배경·이동, PC 기존 메뉴를 실제 폭에서 확인한다.
- 운영 데이터에 시험 예약·공지·Push를 만들거나 시간 조작·강제 실패로 검증하지 않는다.
- 제공자 수락·worker 성공을 iPhone/Android OS 실수신·클릭 성공으로 보고하지 않는다.

## 7. 변경 후 백업·복구본·감시

1. 실제 Backend/Frontend 새 digest와 그대로 유지한 Caddy/PG의 출처를 혼합 구성으로 기록한다.
2. 기존 백업 config/state와 객체 버전을 보존하는 명시적 출처 전환에서 새 hourly/weekly 암호문을 만든다.
   원래 성공 상태의 identity만 수정하거나 삭제해 가드를 통과시키지 않는다.
3. 새 정확한 version·SHA·감시 신선도·timer를 확인하고 PC의 별도 빈 DB에 다시 독립 복원한다.
4. 선택한 운영 설정 allowlist의 새 age 복구본을 만들고 별도 Windows 인증/디스크 복원·SHA/ACL·
   임시 평문 정리와 실제 서버 내용/Linux metadata 대조를 확인한다. 서버 전체 capture로 표현하지 않는다.
5. 기존 복구키·암호문·실패 증빙은 보존한다. 추가 암호문의 PC 밖 사본은 사용자 선택대로 연기한다.
6. 완료 보고는 실제 적용 SHA/digest·31일 범위·모바일 링크·백업/복원·남은 실기기 검증을 구분한다.

## 8. 중단·복귀

오류 시 새 쓰기·worker의 영향을 먼저 파악하고 최신 운영 데이터를 보존한다.
이전 앱 이미지/설정으로 복귀할 수 있지만 이미 만들어진 추가 날짜·예약·알림은 자동 철회되지 않는다.
구버전이 새 예약을 화면에서 숨길 수 있으므로 단순 이미지 복귀를 데이터 복구 완료로 보고하지 않는다.
발송된 Push는 철회할 수 없다. DB를 과거 dump로 덮거나 생성 행·lease·중복 방지 키를 임의 삭제하지 않는다.
변경 전·후 백업과 실제 실패 증빙을 유지하고 원인·영향·복귀 범위를 확인한 뒤 재개한다.
