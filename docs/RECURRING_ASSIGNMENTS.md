작성 기준: 2026-10-10, Asia/Seoul. 구현 브랜치: `codex/recurring-assignments`, 구현 시작 기준 main: `cf02718`(예약 기본 PR #6 병합). 반복 배정 관리자 UI의 최종 검증과 내 공연조 일정 구현·검증 결과를 보고한 뒤 사용자 승인으로 [PR #7](https://github.com/developer-sw/jeongeum-band-scheduler/pull/7)을 정식 전환·main 병합했다. 병합 커밋 `4fccdc7`의 [main CI](https://github.com/developer-sw/jeongeum-band-scheduler/actions/runs/38060582682)가 통과했다.

2026-10-12 후속 단건 예약 변경은 [RESERVATION_CHANGES](RESERVATION_CHANGES.md)에 별도로 기록했다. 고정 회차 변경·후속 취소의 예외와 원본 주차 링크, 다른 주차로 이동한 회차의 재생성 방지, 다음 주 패턴 보존을 격리 PostgreSQL에서 검증했다. 아래 기존 단계의 범위·검증 기록은 당시 결과로 유지한다.

## 1. 범위와 확정 정책

- 전체 관리자가 정규조·추가조의 매주 반복하는 요일·canonical 블록을 배정한다. 팀 소속이 없어도 이 관리 기능을 사용할 수 있다. 일반 팀 예약 생성 권한은 기존 소속 조건을 유지한다.
- 고정 배정은 여섯 악기를 모두 점유하는 팀 독점 예약이다. 원래 관리자 배정의 60분만 일반 하루 120분 한도에서 면제한다. 90분은 기존 정책대로 60분 한도에 합산하지 않는다.
- 수정은 적용 시작일을 지정한다. 단건 취소·변경·교환 예외, 진행 중·종료된 회차와 이용 이력을 보존한다. 개별 취소는 다음 주 배정을 끝내지 않는다.
- 기존 예약이 충돌하면 배정 전체 적용을 거절하고 충돌 목록을 반환한다. 관리자에게 필요 시 기존 예약을 명시적으로 취소할 수 있는 기존 기능을 제공한다.
- 예약 가능 날짜는 한국 오늘~오늘+14일의 15개 날짜다. 새 날짜는 고정 배정을 먼저 반영한 뒤 공개한다. 시작 전·진행 중 블록은 이용할 수 있고 종료된 블록은 새 예약을 생성하지 않는다.

예약 변경·교환·악기 고장 관리·탈퇴/팀 해체 정리·공지·Push는 이번 범위에서 구현하지 않는다. 이번 회차 예외 모델은 후속 변경·교환이 원래 시간에 재생성되지 않도록 확장할 수 있게 둔다. 팀별 곡·계정 연결·90일 세션과 사용자 수정 문구를 유지한다.

## 2. 회차와 경계의 기술 계약

확정 정책을 구현하는 기술 기준은 기존 [RESERVATION_RULES](RESERVATION_RULES.md)의 반복 배정 절을 따른다.

- 하나의 배정은 매주 한 블록이다. 두 연속 60분 고정 합주는 배정 두 개로 구성한다.
- 회차 키는 `assignmentId + weekStartDate`이며 주 시작은 서울 월요일이다. 요일·실제 예약 날짜·revision을 키로 사용하지 않는다.
- 패턴 이력은 새 revision으로 추가한다. 취소 예외는 tombstone으로 남아 자동 개방·패턴 변경에서 되살리지 않는다. 예약 날짜를 기존 예약 행에 덮어쓰지 않고, 아직 시작 전인 직접 고정 예약만 관리 작업으로 취소·후속 고정 예약에 연결한다.
- 적용 시작일이 포함된 주는 원래 예정일과 새 예정일이 모두 적용일 이후이고 아직 시작 전이며 예외가 없는 회차만 옮긴다. 한쪽이 적용일 이전이면 기존 주차를 보존하고 다음 적용 가능한 주부터 새 패턴을 적용한다. 한 배정의 같은 주에 자동 회차를 두 번 만들지 않는다.
- 패턴의 시작 전 경계 판정은 revision의 승인 시각인 `created_at`을 기준으로 고정한다. 최종 잠금 후 승인 시각을 다시 확인하여 저장한다. 재시작·지연 생성 때의 현재 시각 때문에 이미 승인한 미래 revision을 이전 요일로 되돌리지 않는다. 이미 실제로 생성된 회차의 시작·예외 보존은 해당 예약·회차를 기준으로 검사한다.
- `endDate`는 포함 날짜다. 종료일 이후 새 회차 생성과 아직 시작 전인 직접 고정 회차를 정리한다. 시작한 회차·개별 예외·그 후속 예약은 일반 종료 명령으로 취소하지 않는다. 미래 종료일까지는 날짜 조건에 따라 계속 생성한다.
- 종료는 되돌리기 없는 기술 계약이다. 종료일 설정 이후 패턴 PATCH와 종료일 연장은 `ASSIGNMENT_ENDED`로 거절한다. 오늘 이후 범위에서 기존 종료일과 같거나 더 이른 날로 종료일을 조정할 수 있다. 종료 tombstone을 다시 생성하지 않는 안전한 API 제한이며 신규 운영 정책으로 취급하지 않는다. 다시 배정할 때는 별도 신규 배정을 사용하고 기존 이력을 보존한다.
- 지연 복구 또는 최초 배정 시 이미 시작했으나 끝나지 않은 회차는 `usableFrom=max(now, blockStart)`로 생성한다. 이미 끝난 회차는 과거 예약을 새로 만들지 않는다. 패턴 수정은 이미 시작한 기존 회차를 보존한다.
- 열린 구간뿐 아니라 기간이 겹치는 미래 요일·블록 패턴도 검사한다. preview는 점유를 확보하지 않는다. 실제 적용은 현재 버전·권한·점유를 잠금 안에서 다시 검사한다.
- 요일 변경으로 새 예정일이 오늘+14일 밖이면 기존 직접 고정 회차의 점유를 정리하고 동일한 회차를 PLANNED로 보관한다. 그 날짜를 미리 공개하지 않고 개방 구간에 들어온 뒤 고정 예약으로 반영한다.

## 3. 저장과 동시성

V1~V4를 유지하고 새 V5 migration을 추가한다.

| 구성 | 책임 |
|---|---|
| `recurring_assignments` | 팀, 최초 배정 관리자, 포함 종료일, 상태, 관리 version |
| `recurring_assignment_revisions` | 적용 시작일, 요일, 블록의 append-only 패턴 이력 |
| `recurring_occurrences` | 안정적인 주차 키, 예정 위치, revision, 회차 상태·예외 |
| `recurring_occurrence_reservations` | 원본·현재 예약과 회차의 N:M 연결 |
| `recurring_schedule_guard` | 미개방 미래 패턴의 동시 조회/저장을 직렬화 |
| `recurring_idempotency_requests` | 관리 mutation의 실행자·경로·입력 fingerprint·배정 결과 |
| `booking_days.recurring_prepared` | V4 날짜를 보존하며 고정 반영 완료를 구분 |

공통 잠금 순서는 `directory_mutation_guard → 관련 users ID → teams ID → assets ID → recurring_schedule_guard → booking_days 날짜 → reservations ID`다. 패턴 관리 guard는 UPDATE, 날짜 생성은 SHARE를 사용한다. 사용자/팀 행은 NO KEY UPDATE, 악기는 SHARE, 날짜·예약은 UPDATE이며 각 집합은 오름차순이다. 최종 회차 unique·악기 점유 unique·ledger unique도 유지한다.

자동 고정 생성의 operation 실행자는 SYSTEM, 예약 생성자는 최초 배정 관리자다. 그 관리자의 현재 팀 소속이나 계정 상태가 역사적 생성자 연결을 바꾸지 않는다. 팀이 활성인지 재검증한다. FIXED 예약·여섯 점유·면제 RESERVE 0 항목·회차 연결을 한 트랜잭션에 저장한다. 관리자 패턴 수정/종료는 현재 관리자 권한을 다시 검사하고 관리 작업 이력을 남긴다.

실패하면 기존 패턴·회차·예약·점유·한도와 idempotency 성공 기록을 모두 유지한다. 단건 취소는 기존 예약 취소 트랜잭션 안에서 연결된 회차를 CANCELED_EXCEPTION으로 기록한다.

## 4. API와 관리자 화면

기본 경로는 `/api/v1/recurring-assignments`다. 현재 활성 전체 관리자만 조회·쓰기 가능하며 쓰기는 기존 세션·CSRF를 사용한다.

| 요청 | 입력·역할 |
|---|---|
| GET | 기본 오늘~오늘+14일의 배정·revision·회차 목록. `from/to`는 최대 31일 |
| POST /preview | 신규 `{teamId, weekday, blockCode, effectiveDate}` 또는 수정 `{assignmentId, expectedVersion, teamId, weekday, blockCode, effectiveDate}` |
| POST | 신규 배정; `Idempotency-Key` 필수 |
| PATCH /{id} | `{expectedVersion, weekday, blockCode, effectiveDate}`; 주체 팀을 바꾸지 않음, `Idempotency-Key` 필수 |
| POST /{id}/end | `{expectedVersion, endDate}`; `Idempotency-Key` 필수 |

`weekday`는 월요일 1~일요일 7이다. ID는 문자열로 반환한다. preview 응답은 `canApply`, `conflicts`, `plannedOccurrences`이며 보존하는 회차를 함께 안내한다. 적용 중 충돌은 `409 ASSIGNMENT_CONFLICT`, 오래된 version은 `409 VERSION_CONFLICT`이다. 충돌 목록은 기존 API envelope의 `error.conflicts`에 반환한다. 같은 성공 키/본문 재시도는 새로운 배정 없이 현재 배정 결과를 반환하고, 반복 배정 기능 안에서 다른 경로/본문으로 키를 재사용하면 거절한다. 기본 예약과 반복 배정의 키 저장 범위는 별도이며 UI는 각 mutation에 새 UUID를 발급한다.

배정 응답은 `id/teamId/teamName/teamKind/status/version/createdByUserId/endDate/revisions/occurrences`다. revision은 `id/revisionNo/effectiveDate/weekday/blockCode`, 회차는 `id/weekStartDate/revisionId/originalScheduledDate/originalBlockCode/state/reservationIds`를 제공한다. preview의 계획 회차는 `weekStartDate/date/blockCode/state/preserved`, 충돌은 `type(PATTERN 또는 RESERVATION)/assignmentId/reservationId/date/weekday/blockCode/teamId/teamName`이다. 개인정보인 로그인 식별자나 개인 이름은 충돌 목록에 포함하지 않는다.

`/admin/recurring-assignments`에서 팀·요일·블록·적용일 선택, 미리보기, 충돌 확인, 적용, 수정, 포함 종료일 설정을 제공한다. 미리보기 후 입력이 바뀌면 다시 검사한다. 적용 성공을 서버 응답 후 표시하고 불확실한 네트워크 실패는 같은 키로 확인한다. 관리자 역할 상실·계정 전환 때 해당 Query와 화면을 초기화한다. 일정과 상세에는 직접 고정 예약·한도 면제를 구분한다.

동일 미래 적용일의 revision이 여러 개면 가장 큰 revision 번호를 최신 패턴으로 선택한다. 카드의 가장 가까운 예정 패턴과 편집창 초기값에 같은 규칙을 적용한다. 포함 종료일을 넘는 revision은 예정 패턴에서 제외하고 변경 이력에는 보존한다. `VERSION_CONFLICT`가 확정된 뒤 **배정·시간표 새로 확인**을 누르면 낡은 수정·종료 창을 닫고 최신 카드에서 다시 선택하도록 안내한다. 기존 입력에 새 version을 자동으로 넣어 덮어쓰지 않으며, 불확실한 네트워크 요청의 본문·키는 보존한다.

재시도 키·입력은 해당 화면이 마운트된 동안 메모리에만 유지한다. 전체 새로고침·화면 이탈·탭 닫기 후에는 유지하지 않으므로 목록을 먼저 확인한다. 오프라인 요청을 저장해 나중에 자동 실행하지 않는다.

## 5. 날짜 개방과 장애 복구

- 서울 00:00 스케줄, 서버 준비 완료 시 복구, 주기적인 누락 날짜 복구를 사용한다. 일정 조회·예약 생성 전에도 개방 구간을 준비하여 자정 실행 누락을 복구한다.
- 날짜 하나씩 독립 트랜잭션으로 `PREPARING → 고정 회차 반영 → recurring_prepared=true 및 OPEN`을 처리한다. 같은 날짜를 여러 번 실행해도 회차 unique와 잠금으로 중복 생성하지 않는다.
- 기존 예약과 예상 밖의 충돌 또는 DB 실패가 있으면 그 날짜는 공개하지 않는다. 다른 날짜의 준비는 계속하고 후속 실행에서 다시 시도한다. 실패한 고정 회차를 무시하고 빈 시간으로 공개하지 않는다.
- 기존 예약 트랜잭션이 directory guard를 가진 상태에서 별도 개방 트랜잭션을 호출하지 않는다. 개방 준비를 선행한 뒤 일반 예약 서비스가 현재 개방 상태·범위·권한을 재검증한다.
- 테스트에서는 `jeongeum.recurring.worker.enabled=false`로 자동 작업자를 끄고 공개 개방 진입점 `RecurringOpeningService.openBookableWindow()`와 가변 Clock으로 자정·재실행을 결정적으로 검증한다. 운영 기본값은 활성이다.
- 별도 실행 검증에서는 worker를 활성화하고 Spring에 실제 등록된 자정 cron과 60초 catch-up을 제어된 Clock·TaskScheduler로 실행했다. 프로덕션 개방·복구 서비스와 실제 PostgreSQL 잠금을 사용하며 개발 PC 시각이나 개발 DB를 조작하지 않는다.

주기 복구·조회 구간 최대 31일·재시도 키 보존은 기술 설정이다. 확정된 예약 가능 기간과 일일 한도를 확장하는 정책이 아니다. Push/outbox 연결은 후속 알림 구현과 함께 처리하며 이번 단계에서 실제 Push 발송을 주장하지 않는다.

## 6. 검증과 실제 DB 보호

구현 후 실제 PostgreSQL Testcontainers에서 기존 데이터 V4→V5 보존, 정규/추가 배정·여섯 점유·면제, 자정과 누락 복구, 중복 worker, 취소 예외, 경계 주차, 수정/종료, 미래 패턴 경합, preview 이후 충돌·전체 rollback·권한 변경을 검증한다. 프론트는 API 요청·query·권한·실패와 미리보기 흐름 및 타입·lint·build를 확인한다. 별도 임시 DB의 합성 계정으로 PC·모바일 화면을 점검한다.

실제 로컬 V4 DB의 관리자 계정과 세션, 회원·팀·예약 테이블을 V5 적용 전 ignored 경로에 논리 백업한다. Docker 데이터 볼륨을 초기화하거나 실제 회원 데이터를 테스트에 사용하지 않는다. 백업 생성 확인과 실제 복원 검증은 구분한다.

실제 DB에서는 합성 계정·팀·예약·배정을 만들지 않았다. 실제 서버 재시작 후 회원 홈이 보이고 로그인 상태가 유지됨은 사용자가 직접 확인했으며 후속 실제 JVM 재시작과 DB 해시 대조도 수행했다. 실제 개발 환경의 공개 홈·로그인 화면·미인증 관리자 접근 보호를 확인하고, 관리자 mutation은 격리 DB 화면에서 검증한다. 복원·scheduler 검증용 임시 컨테이너와 JVM은 종료했다.

서버 재시작 단계의 26개 테이블 동일 결과와 이번 UI 단계의 최종 대조를 구분한다. 이번에는 접속 관련 세션 2개 테이블에서 변화가 있었으며 다른 24개 테이블의 기존 계정·예약·설정·이력은 동일했다. 세션 증가를 특정 요청 하나의 영향으로 단정하지 않는다.

기존 요일로 미래 회차가 돌아갈 수 있던 지연 복구 문제는 revision 승인 시각을 저장·사용하도록 수정했고 회귀 테스트에 포함했다. 시작 경계는 최종 잠금 후 현재 시각으로 재검증한다. 관리자 권한은 초기 대상 조회 전과 잠금 후 확인한다. 90분 고정 예약의 60분 면제 오표시는 제거하고 DB에도 60분만 면제될 수 있는 제약을 추가했다.

관리자 UI 최종 보완은 같은 미래 적용일의 낡은 revision 선택, version 충돌 뒤 목록만 갱신되어 낡은 편집 입력이 남는 문제, 종료일 이후 패턴을 앞으로 적용될 패턴처럼 보여주던 문제를 수정했다. 포함 종료일 당일의 패턴은 유지하고 종료일 이후 패턴은 변경 이력만 남긴다. 관련 회귀 테스트를 추가했으며 기존 성공/불확실한 요청의 처리와 사용자 UI 문구를 보존했다.

자정·누락 복구·중복 작업자·권한 경합은 가변 Clock과 실제 PostgreSQL의 별도 트랜잭션으로 검증했다. 후속 실행에서는 등록된 자정 cron 자체의 dispatch와 10초 실제 잠금 timeout·60초 자동 재시도를 검증했다. 실제 벽시계 자정까지 기다린 검증, 후속 변경·교환 API의 예외 생성, 실서비스 트래픽·실기기 PWA/Push·운영 외부 백업 복원은 미검증이다. 백업 보존·해시 비교 도구와 결과 JSON은 `.local/` 및 `backups/`에만 두며 Git에 넣지 않는다.

위 로컬 검증 결과를 보고한 뒤 사용자 승인으로 기능 커밋 `e26e649`를 Push하고 PR #7을 생성했다. Push·PR CI 모두 통과 후 추가 승인으로 정식 PR 전환·main 병합을 완료했으며, 병합 커밋 `4fccdc7`의 main CI도 통과했다. 로컬 main을 같은 커밋으로 동기화했다. 최신 모바일 실행 검증의 미완료 상태는 병합과 별개로 유지한다.

## 7. 내 공연조 일정 모아보기

회원 메뉴의 **내 공연조 일정**에서 `/my-schedule`로 접근한다. 별도 페이지를 선택한 이유는 여러 날짜를 한 번에 확인하는 조회 흐름을 날짜별 시간표·생성·취소와 분리하면서 기존 `/reservations`의 기능을 유지하기 위해서다. 로컬 기본 주소는 `http://127.0.0.1:3000/my-schedule`이다.

기존 기간별 `GET /api/v1/reservations?scope=mine&from=YYYY-MM-DD&to=YYYY-MM-DD`, schedule과 현재 회원의 소속 정보 Query를 재사용한다. 서버의 한국 오늘부터 `bookableThrough`까지 현재 소속 팀의 실제 `CONFIRMED` 예약과 `OPEN` 날짜만 남기고 날짜·시작 시간 오름차순으로 표시한다. 일반 팀 예약과 실제 생성된 고정 회차를 통합하며 개인 예약·취소/교체 이력·PLANNED 미래 패턴은 확정 목록에 표시하지 않는다. 다른 팀원이 만든 소속 공연조 예약도 포함한다.

정규조·추가조, 일반 예약·고정 배정, 확정 · 예정·진행 중·종료 상태와 날짜·요일·시작/종료 시각을 표시한다. 전체 소속 팀 또는 특정 팀을 선택할 수 있다. 소속은 있지만 빈 목록이면 **내 공연조는 열린 기간에 확정된 합주 일정이 없어요**를 안내하고, 팀이 없으면 **아직 소속된 공연조가 없어요**와 관리자에게 구성·계정 연결을 확인하라는 안내를 표시한다. 각 일정은 `/reservations?date=YYYY-MM-DD`의 해당 날짜로 연결하며 취소 이력도 기존 화면에서 확인한다. 20초 주기·포커스·재연결·수동 갱신과 공통 예약 Query 무효화로 최신 상태를 확인한다. 미로그인·계정 전환·현재 소속 변경은 기존 세션·Query 범위·서버 권한 검증을 따른다.

새 API·테이블·migration을 추가하지 않았으며 기존 예약 권한·한도·현재 소속 조건과 개인 예약 이력을 유지한다. 신규 화면의 자동화·실제 브라우저 최종 결과는 6절의 최신 실행 결과에 함께 기록한다.

## 8. 추가 모바일 직접 확인 절차

이번 브라우저 도구에서는 390×844 설정·새 탭·새로고침 이후에도 실제 DOM viewport 폭이 1280px로 유지됐다. 이 화면을 모바일 통과 증빙으로 사용하지 않는다. 아래 절차는 개발 PC의 Chrome/Edge에서 확인하는 방법이다. 현재 서버는 PC의 `127.0.0.1`에 연결되어 있어 실제 휴대전화의 같은 주소로 PC 서버에 접근할 수 없다. 실제 iPhone/Android 확인은 접속 가능한 환경이 준비된 뒤 별도로 진행하며, 이번 작업에서 서버 바인딩이나 네트워크 노출을 바꾸지 않는다.

1. 개발 PC의 Chrome/Edge에서 `http://127.0.0.1:3000/my-schedule`를 열고 로그인한다. `F12`로 개발자 도구를 열고 `Ctrl+Shift+M`으로 Device Toolbar를 켠 뒤 Responsive 크기를 390×844로 설정한다. Console의 `window.innerWidth`가 실제로 390인지 확인한다. 개발 DB에서는 조회만 하고 생성·수정·취소 시나리오는 합성 계정의 격리 QA DB에서 확인한다.
2. 제목·기간·필터·팀 이름·시간·예약 출처·상태·하단 사용자 문구가 잘리지 않고 가로 스크롤 없이 읽히는지 확인한다. 일정 카드가 세로로 배치되고 버튼을 충분한 영역으로 누를 수 있어야 한다.
3. 전체 공연조와 한 팀을 번갈아 선택해 목록이 바뀌는지 확인한다. 팀이 없는 계정·일정이 없는 팀에서는 안내와 합주실 예약 링크를 확인한다.
4. **시간표·예약 확인**을 눌러 해당 날짜가 선택되는지, 다시 돌아와 계정·필터·현재 목록을 확인한다. 로그아웃 후 일정 페이지는 로그인 안내여야 한다.
5. 격리 QA에서 일반 예약·고정 회차가 함께 표시되는 목록과 회차 취소·패턴 변경 후 수동 갱신을 확인한다. 관리자 화면에서는 요일·블록·적용일 입력, 새 미리보기, 충돌 목록·종료 안내도 세로 화면에서 읽고 조작할 수 있어야 한다.
