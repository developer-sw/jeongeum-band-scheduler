# 예약 가능 기간 31일 확장

기준일: 2026-11-03, `Asia/Seoul`. 사용자가 **30일 뒤까지, 오늘 포함 31일**을 확정했다. 작업 브랜치는 `codex/booking-window-31-days`이며, 기존 main `0230b876888660244d1a373cee88d57171612341`에서 시작했다.

코드·문서 수정과 격리 검증 후 사용자가 GitHub 반영을 승인했다. 커밋·Push·main 대상 초안 PR과 동일 HEAD의 원격 CI를 확인하며, 최종 원격 결과는 해당 PR의 검사 상태를 기준으로 한다. **운영 사이트는 후속 배포 전까지 오늘+14일의 15개 날짜를 사용한다.** 기존 운영 DB·중지한 로컬 개발 원본·회원 계정·예약·Docker 볼륨을 보존한다. 아래 로컬 결과와 원격 CI·운영 반영을 구분한다.

## 확정 정책과 공통 기준

- 서버의 서울 `today`부터 `today+30일`까지 양 끝을 포함한다. 예를 들어 2026-11-03이면 마지막 날짜는 2026-12-03이며 2026-12-04는 범위 밖이다.
- 달력의 한 달이나 30×24시간이 아니라 서울 달력 날짜의 30일 뒤다. 월말·연말·윤년에도 같은 계산을 적용한다.
- `BookingWindow.ADVANCE_DAYS=30`, `DATE_COUNT=31`, `through(today)`를 예약 생성·변경·교환·일정·반복 배정과 날짜 개방에서 공유한다. 잠금 대기 후에도 현재 서울 날짜를 다시 검증한다.
- 새 마지막 날짜는 서울 자정에 개방한다. 해당 날짜의 고정 회차를 먼저 확정하고 `recurring_prepared=true`인 `OPEN` 날짜만 일반 예약에 공개한다. 준비 실패한 날짜는 공개하지 않고 기존 누락 복구·재시도 경로를 사용한다.
- 일일 한도·고정 블록·권한·악기 점유·단건 변경/교환의 원자성·고정 회차 예외와 기존 알림 정책은 유지한다. 기간 확장을 이유로 기존 예약을 삭제·이동하거나 예외 회차를 재생성하지 않는다.

## API와 화면

`GET /api/v1/schedule`의 기본 범위와 응답의 `bookableThrough`를 오늘+30일로 맞춘다. `from/to` 지정도 개방 범위 안의 최대 31개 날짜를 허용한다. 예약·반복 배정 목록의 한 요청 최대 31일 계약은 유지하므로 양 끝을 포함한 32개 날짜 요청은 거절한다. 교환 후보 조회와 실제 교환 확정도 현재 개방 범위를 검증한다.

응답 필드를 추가하지 않는다. 프론트의 달력·날짜/주간 탐색·내 공연조 일정·예약 변경 범위와 안내는 서버의 `today/bookableThrough`에 맞춘다. 모바일/PC 레이아웃과 사용자 문구 `JEONGEUM · SENTIMENTAL MUSIC`은 유지한다. 전체 범위가 31일이므로 기존 한 요청 최대 31일 목록 계약 안에서 조회할 수 있다.

## 데이터와 운영 적용 영향

기존 날짜·예약·반복 회차 schema는 날짜를 저장하며 15일만 허용하는 DB 제약이 없다. 새 migration이나 기존 Flyway 파일 수정·데이터 초기화 없이 공통 날짜 정책을 변경한다.

현재 15일 범위에서 31일 범위로 운영 Backend를 올리면 기동·주기 복구 또는 일정 조회가 **추가 16개 날짜**를 준비할 수 있다. 고정 배정이 있는 날짜에는 실제 예약 회차·점유·알림함 항목·구독별 Push 대기 작업과 시작 1시간 전 계획이 기존 정책대로 생성될 수 있다. 알림을 조용히 생략·지연하거나 새로운 요약 정책으로 바꾸지 않는다. 각 날짜 준비는 기존 독립 트랜잭션·중복 방지 제약을 사용한다.

운영 적용 전에는 동일 SHA의 CI·이미지, 새 암호화 백업·독립 복원과 복구 경로를 확인하고 추가 구간의 예상 회차·알림 영향을 검토한다. 이전 코드로 이미지를 되돌려도 새로 생성된 회차·알림을 자동 삭제하거나 외부로 발송한 Push를 철회하지 않는다. 운영 데이터나 회원 알림을 되돌리기 위해 DB를 임의 복원하지 않는다. 실제 GitHub 게시·병합·운영 반영은 해당 단계의 승인 범위를 따른다.

전체 Backend 실행은 371건 중 370건 통과, `ReminderIntegrationTest`의 기존 3회차 기대값 1건 실패였다. 31일 범위의 금요일 5회차와 종료 후 1회 유지·4회 취소에 맞춰 테스트 기대값만 보완하고 해당 suite 17건을 재실행해 모두 통과했다. 전체 실행 결과와 재실행 결과를 고유 테스트별로 대조한 최종 결과가 371건 통과다. 업무 코드의 알림 생략이나 검증 완화는 없다.

격리 테스트는 합성 계정과 Testcontainers의 별도 PostgreSQL만 사용한다. 실제 운영·중지한 개발 원본 DB에는 접속하지 않았다. worker 검증은 실제 서비스 콜백과 PostgreSQL을 사용했으며, 이번에 새 코드를 운영 서버에서 기동·재부팅하거나 실제 자정까지 대기한 검증은 아니다. 통합 테스트·빌드 성공을 운영 부하 여유나 실제 단말 Push 수신 성공으로 확대하지 않는다. 기존 날짜별 15일 배포·검증 기록은 실행 당시 결과로 보존한다.
