# 예약 운영 규칙

기준일: 2026-10-09 (Asia/Seoul)

이 문서는 사용자와 확정한 예약 정책을 기록한다. `권고안`으로 표시한 DB·트랜잭션·표현 방식은 정책을 구현하기 위한 기술 설계다. 문서 작성 승인은 실제 구현, migration 생성, Git 초기화 또는 배포 승인이 아니다.

## 1. 서비스와 예약 주체

- 합주실은 하나다.
- 전역 역할은 `MEMBER`, `GLOBAL_ADMIN`이다. 팀장은 팀 멤버십의 역할이며 별도 전역 역할이 아니다.
- 팀 종류는 정규조 `REGULAR`, 추가조 `ADDITIONAL`이다.
- 회원은 여러 정규조와 여러 추가조에 소속될 수 있다. 정규조 소속을 한 개로 제한하지 않는다.
- 전체 관리자가 팀을 만들고 팀원을 구성한다. 임원은 전체 관리자이면서 팀장일 수 있다.
- 가입은 개인별 1회용 초대를 사용한다. 별도의 관리자 가입 승인 절차를 확정한 것은 아니다.
- 활성 팀원 모두 소속 팀의 예약을 생성할 수 있다. 개인 예약은 본인의 예약이다.
- 팀 예약 생성 권한을 팀 전체 예약 편집 권한으로 확대하지 않는다. 변경·취소는 예약자, 해당 팀장, 전체 관리자에게 적용하며 현재 회원·팀 소속과 역할을 다시 검사한다.
- 전체 관리자가 미소속 팀의 일반 예약을 대리 생성하는 기능은 확정하지 않았다. 관리자의 주간 고정 배정은 별도의 관리 기능이다.
- 예약의 주체와 최초 예약자를 구분한다. 팀 예약의 주체는 팀이고, 예약자는 생성한 회원이다. 변경·교환에서도 예약자와 주체를 유지한다.
- 팀별 곡 목록은 필수다. 곡 목록은 예약 시간 충돌의 기준이 아니며 팀과 예약을 일대일로 제한하지 않는다.

## 2. 운영 시간과 고정 블록

평일과 주말에 같은 시간표를 사용한다. 운영 시간은 12:00~24:00이다.

| 블록 코드 | 표시 시간 | 분량 | 시작 분 | 종료 분 |
|---|---|---:|---:|---:|
| B01 | 12:00~13:00 | 60 | 720 | 780 |
| B02 | 13:00~14:00 | 60 | 780 | 840 |
| B03 | 14:00~15:00 | 60 | 840 | 900 |
| B04 | 15:00~16:00 | 60 | 900 | 960 |
| B05 | 16:00~17:00 | 60 | 960 | 1020 |
| B06 | 17:00~18:00 | 60 | 1020 | 1080 |
| B07 | 18:00~19:30 | 90 | 1080 | 1170 |
| B08 | 19:30~21:00 | 90 | 1170 | 1260 |
| B09 | 21:00~22:30 | 90 | 1260 | 1350 |
| B10 | 22:30~24:00 | 90 | 1350 | 1440 |

- 사용자가 임의 시작·종료 시각이나 분량을 입력하는 예약은 허용하지 않는다.
- API는 날짜와 블록 코드를 받아 서버의 고정 시간표로 해석한다.
- `24:00`은 종료 표시다. 실제 날짜·시각 계산에서는 다음 날 `00:00`, `Asia/Seoul`로 처리한다.
- 예약 날짜는 합주실의 서울 기준 운영일이다. UTC 날짜로 바꾸어 일일 한도나 날짜 경계를 계산하지 않는다.
- 120분은 인접한 60분 예약 두 건이다. 임의의 120분 블록을 새로 만들지 않는다.

## 3. 예약 가능 날짜와 진행 중 예약

- 서울 날짜 기준 `오늘`부터 `오늘 + 14일`까지 예약할 수 있다. 양 끝을 포함하므로 열린 날짜는 15개다.
- 새 날짜는 서울 시각 `00:00`에 개방한다.
- 정규조·추가조 고정 배정이 없는 모든 시간은 팀과 개인이 선착순으로 예약할 수 있다. 평일 주간도 포함한다.
- 현재 진행 중인 블록의 잔여 시간도 예약할 수 있다. 예를 들어 14:10에 비어 있는 B03을 예약하면 사용 가능 시간은 14:10~15:00이다.
- 이 경우에도 선택한 블록은 B03이며 일일 한도는 60분을 소비한다.
- 종료한 블록은 새로 예약할 수 없다.
- 시작·종료 판단은 클라이언트 시간이 아니라 서버 시각으로 한다. 잠금 대기 후 쓰기 직전에 다시 확인한다.

권고안: `예약 블록 시작`, `예약 효력 시작`, `예약 블록 종료`를 구분한다. 효력 시작은 서버 확정 시점과 블록 시작 중 늦은 시각이다. 이는 실제 출입·연주 시간을 측정한다는 뜻이 아니다.

## 4. 합주실 독점과 개인 공유

악기 종류는 보컬, 건반, 일렉기타, 베이스, 드럼, 통기타의 여섯 종류다.

| 예약 유형 | 합주실 사용 방식 | 자원 점유 |
|---|---|---|
| 정규조 팀 예약 | 합주실 독점 | 여섯 자원을 모두 점유 |
| 추가조 팀 예약 | 합주실 독점 | 여섯 자원을 모두 점유 |
| 일반 개인 예약 | 다른 개인과 공유 가능 | 선택한 악기 하나 |
| 교환으로 생성된 개인 90분 예외 | 다른 개인과 공유 가능 | 서로 다른 악기 최대 두 개 |

- 같은 날짜·블록에서 같은 악기는 한 예약만 점유한다.
- 서로 다른 악기를 사용하는 개인 예약은 공존할 수 있다.
- 개인 회원은 같은 시간에 여러 개인 예약을 중복 보유할 수 없다. 90분 두 악기 예외는 예약 한 건이 자원 두 개를 점유하는 형태다.
- 팀 예약은 개인 예약 및 다른 팀 예약과 같은 블록에 공존할 수 없다.
- 팀이 여섯 자원을 점유하는 것은 합주실 독점성을 표현하기 위해서다. 팀원 여섯 명이 반드시 참석하거나 모든 장비를 실제 사용한다는 의미가 아니다.
- 같은 팀이 같은 블록을 중복 예약하거나 개인과 팀이 충돌하는 것도 서버가 차단한다.

## 5. 일일 60분 블록 한도

| 주체 | 한도 범위 | 일반 60분 예약 한 건 | 90분 예약 |
|---|---|---:|---:|
| 개인 회원 | 해당 회원의 개인 예약, 서울 날짜별 | 60분 | 한도에 합산하지 않음 |
| 팀 | 해당 팀의 팀 예약, 서울 날짜별 | 60분 | 한도에 합산하지 않음 |

- 개인과 팀의 한도는 별도이며, 서로 다른 팀의 한도도 별도다.
- 일반 60분 예약은 주체별 하루 최대 120분이다.
- 관리자 고정 배정의 원래 회차·위치에서 사용하는 60분 예약은 면제다.
- 해당 고정 예약을 사용자 단건 변경·교환으로 옮겨 생성한 60분 예약에는 일반 한도를 적용한다. 고정 배정에서 출발했다는 이유만으로 면제를 계속 전달하지 않는다.
- 14:10에 B03의 잔여 시간을 예약해도 60분을 소비한다.
- 악기 개수가 아니라 블록을 기준으로 계산한다.
- 시작 전 취소는 해당 예약의 한도 소비를 복구한다.
- 시작 후 취소는 점유를 해제하지만 한도 소비는 유지한다. 고정 면제로 0분을 소비한 예약은 유지할 소비량도 0분이다.
- 이미 시작한 예약의 소비량과 앞으로 예약한 소비량을 함께 합산한다. 활성 예약만 조회해서 한도를 계산하면 안 된다.
- 변경·교환은 기존 예약의 복구와 새 예약의 소비를 반영한 최종 합계로 검증한다. 어느 주체·날짜라도 한도를 넘으면 전체 작업이 실패한다.

권고안: `quota_entries`에 예약 시 소비와 시작 전 해제·교체에 따른 복구를 기록한다. 시작 후 취소에는 복구 항목을 만들지 않는다. 동일 예약의 중복 복구를 금지한다.

## 6. 취소

- 예약자, 해당 팀의 현재 팀장, 전체 관리자는 미래·진행 중 예약을 취소할 수 있다.
- 개인 예약에는 팀이 없으므로 예약자와 전체 관리자 권한을 적용한다.
- 과거 예약은 이력으로 보존하며 취소·변경으로 과거 기록을 다시 쓰지 않는다.
- 취소는 예약 전체를 대상으로 한다. 개인 두 악기 예약도 두 악기를 함께 해제한다.
- 예약 상태, 자원 해제, 필요한 한도 복구, 교환 요청 무효화 및 알림 이벤트를 한 트랜잭션으로 처리한다.
- 재시도한 취소가 자원을 다시 해제하거나 한도를 두 번 복구해서는 안 된다.
- 취소 완료 후 같은 시간의 새 예약은 현재 규칙과 한도를 다시 검증한다.

권고안: 취소 사유와 실행자를 기록하고 예약 및 자원 선택 이력을 물리 삭제하지 않는다.

## 7. 변경

- 변경은 예약 시작 전에만 가능하다.
- 주체와 예약자는 유지하면서 날짜·블록·개인 악기를 변경할 수 있다.
- 새 위치의 날짜 개방, 한도, 합주실·개인·악기 점유, 고장 상태를 다시 검사한다.
- 팀 예약은 독점성을 유지한다. 개인 예약은 일반적으로 악기 하나다.
- 두 악기 예외는 90분에만 허용한다. 60분으로 변경하는 개인 예약은 악기 하나 조건을 만족해야 한다.
- 이전 예약 해제와 새 배치가 모두 성공해야 한다. 실패하면 이전 예약과 한도를 그대로 보존한다.
- 변경한 예약을 참조하는 대기 중 교환 요청은 무효화한다.

권고안: 변경 시 원본을 `REPLACED`로 보존하고 후속 예약 ID를 반환한다. 주체와 예약자는 그대로 복사하고 실제 변경 실행자는 별도로 기록한다. 날짜·블록·악기가 모두 같은 요청은 배치를 바꾸지 않는 no-op로 처리한다. 이 경우 기존 고정 면제와 고장 등록 전 예약의 지위를 잃지 않는다.

예약 이력을 저장하는 ID·후속 예약 방식은 [ERD 설계](ERD.md)의 기술 계약을 따른다.

## 8. 교환

### 8.1 허용 모양

- 정규조, 추가조, 개인 사이의 교환을 허용한다.
- 예약 한 건 ↔ 한 건을 허용하며 60분 ↔ 90분도 가능하다.
- 인접한 60분 두 건 ↔ 90분 한 건도 허용한다.
- 두 건 묶음은 같은 날짜, 인접한 60분 블록, 같은 개인 또는 팀, 같은 최초 예약자여야 한다.
- 개인 두 건은 서로 다른 악기일 수 있다.
- 각자 예약의 주체와 예약자를 유지한다. 교환은 상대방의 예약 주체를 가져오는 동작이 아니다.
- 각자의 악기를 유지한다. 팀은 여전히 합주실을 독점한다.

### 8.2 개인 악기 배분

- 개인 60분 두 건의 악기가 같으면 90분 결과는 그 악기 하나다.
- 개인 60분 두 건의 악기가 다르면 90분 결과 예약 한 건이 두 악기를 90분 전체에 걸쳐 점유한다.
- 이 예외는 교환으로 생성된 90분 예약에만 허용하며 최대 두 악기다. 일반 생성 API에서 두 악기를 자유롭게 고르지 않는다.
- 개인 90분 한 악기 예약이 두 개의 60분으로 바뀌면 두 예약 모두 그 악기를 유지한다.
- 개인 90분 두 악기 예약이 두 개의 60분으로 바뀌면 각 60분에는 한 악기를 배정한다. 사용자가 악기 순서를 선택한다.
- 두 악기를 유지해야 하는 90분 예약과 단일 60분 예약의 1:1 교환은 60분 한 악기 규칙을 만족할 수 없다. 두 60분으로 나누는 허용된 형태를 사용한다.
- 반복 교환으로 예외 악기 수가 두 개를 넘을 수 없다.

### 8.3 요청과 승인

- 교환 요청은 양쪽의 모든 예약이 시작 전이어야 한다.
- 상대 예약자, 상대 팀의 현재 팀장 또는 전체 관리자가 승인할 수 있다.
- 개인 상대방에는 팀장 권한을 적용하지 않는다.
- 승인 권한은 요청 생성 당시의 역할만으로 판단하지 않고 승인 시 다시 검사한다.
- 요청은 양측 예약 ID·버전과 악기 배분을 기록한다.
- 요청은 양측에서 가장 이른 블록 시작 시각에 만료된다. 그 시각 이상이면 승인할 수 없다.
- 원본 예약의 변경·취소·팀 해체, 요청자의 권한 유실은 관련 요청을 무효화한다.
- 특정 승인 후보 한 명의 팀장 해제·탈퇴만으로 요청 전체를 자동 무효화하지 않는다. 다른 적법한 예약자·현재 팀장·전체 관리자는 현재 권한을 검증받고 승인할 수 있다.
- 권한을 잃은 사람이 승인하면 `403`으로 거절한다. 존속 팀 예약의 생성자가 탈퇴했다는 이유만으로 다른 사람이 적법하게 요청한 교환까지 무조건 종료하지 않는다.
- 요청 생성만으로 자원을 해제하거나 새로운 자원을 점유하지 않는다.

### 8.4 승인 트랜잭션

1. 현재 회원·팀·승인 권한과 모든 원본 예약 버전을 확인한다.
2. 가장 이른 시작 시각과 만료를 다시 확인한다.
3. 교환 결과 날짜·블록·악기 배분을 계산한다.
4. 교환 당사자의 원래 점유만 제외하고 제3자의 점유를 검사한다.
5. 새 배치의 고장 상태와 양측 주체·날짜별 최종 한도를 검사한다.
6. 양측 원본 해제, 후속 예약·자원 생성, 한도 반영, 요청 완료, 이력 및 알림 이벤트를 원자적으로 처리한다.

예: 개인이 다른 개인과 공유하던 블록으로 팀 예약을 옮기면, 교환 상대방이 아닌 개인 예약이 남아 있어 교환이 실패할 수 있다. 그 예약을 자동 취소하지 않는다.

실패하면 양쪽 기존 예약, 자원과 한도를 모두 보존한다. 권고안: 대기 요청은 `PENDING`, 원자적 교환 완료는 `COMPLETED`로 구분한다. 승인 권한이 없는 행위는 `403`, 원본 변경·요청자 권한 유실은 `INVALIDATED`, 시작 경과는 `EXPIRED`로 처리한다. 새 위치의 일시적 점유·장비·한도 검증 실패는 예약을 바꾸지 않고 충돌 응답을 반환한다. 대기 요청의 상세 오류 코드는 API 계약에서 구분한다.

## 9. 관리자 주간 고정 배정

- 정규조와 추가조에 관리자 주간 고정 배정을 사용한다.
- 사용자의 취소·변경·교환은 해당 회차 한 번의 예외다. 전체 주간 시간표를 바꾸지 않는다.
- 전체 시리즈 변경은 전체 관리자가 적용 시작일을 지정해서 수행한다.
- 시리즈 변경 후에도 이미 생성된 단건 취소·변경·교환 예외는 보존한다.
- 새 고정 배정 또는 전체 수정이 기존 예약과 충돌하면 해당 변경을 거절하고 기존 예약을 유지한다.
- 충돌 목록을 미리 보여주고 실제 적용 트랜잭션에서도 다시 검증한다.
- 진행 중·과거 회차와 이력은 전체 수정으로 다시 쓰지 않는다.
- 팀 해체 시 주간 배정을 종료하고 팀의 남은 예약을 취소한다.

권고안: 회차는 `assignment_id + 서울 기준 week_start_date`로 식별한다. 실제 예약 날짜·블록 또는 패턴 버전을 회차 식별 키로 사용하지 않는다. 요일을 바꾸더라도 같은 주차의 취소 예외를 잃지 않는다.

권고안: 적용 시작일이 포함된 경계 주차에서는 원래 예정일과 새 예정일이 모두 적용 시작일 이후이고, 아직 시작하지 않았으며 개별 예외가 없는 회차에만 새 패턴을 적용한다. 한 날짜가 경계 이전이면 그 주의 원래 회차를 유지하고 다음 적용 가능한 주차부터 변경한다. 같은 주에 두 회차를 추가로 만들지 않는 기술 기준이다.

권고안: 일반 시리즈 종료일 이후의 아직 시작 전·개별 예외 없는 직접 고정 회차는 취소하고 새 회차 생성도 중단한다. 취소 예외와 변경·교환의 후속 예약은 보존하며 필요하면 관리자가 해당 예약을 명시적으로 취소한다. 진행·과거 회차도 종료 명령만으로 취소하지 않는다. 팀 해체는 이 일반 종료와 구분하여 남은 팀 예약 전체를 취소한다.

권고안: 신규·수정 배정은 이미 개방된 날짜의 실제 점유뿐 아니라 적용 기간이 겹치는 미래 주간 패턴끼리의 요일·블록 충돌도 검사한다. 열린 15일만 검사하고 이후의 고정 충돌을 남기지 않는다.

## 10. 개방과 반복 생성

- 새 날짜를 선착순 예약에 공개하기 전에 해당 날짜의 고정 배정을 반영한다.
- 재실행, 재시작, 중복 스케줄러 실행에도 같은 회차를 중복 생성하지 않는다.
- 취소·변경·교환된 회차는 자동 생성 작업이 원래 위치에 다시 만들지 않는다.
- 서버가 `00:00`에 잠시 중단됐더라도 다음 실행에서 필요한 날짜를 복구한다.
- 화면의 빈 상태만으로 고정 배정이 없는 것으로 판단하지 않는다. 개방 상태와 생성 완료를 함께 확인한다.
- 고정 배정으로 생성한 예약에도 예약자·회차·원래 배정 위치를 보존한다. 자동 실행자는 `SYSTEM`으로 구분한다.

## 11. 회원·팀 종료

### 서비스 회원 탈퇴

- 미래·진행 중 개인 예약을 자동 취소한다.
- 존속하는 팀의 예약은 탈퇴한 회원이 생성했더라도 유지한다.
- 시작 후 취소한 개인 60분 예약의 소비 이력은 유지한다.
- 탈퇴 회원의 로그인·예약·승인 권한을 차단한다. 예약자 표시를 이유로 탈퇴 회원의 접근을 허용하지 않는다.
- 팀장은 전체 관리자가 후임을 지정한다. 자동 승계나 탈퇴 금지를 확정한 것은 아니다.

### 팀 해체

- 미래·진행 중 팀 예약을 취소하고 반복 배정을 종료한다.
- 과거 예약과 한도 소비·관리 이력을 보존한다.
- 해체된 팀을 대상으로 새 예약이나 자동 고정 예약을 생성하지 않는다.

권고안: 서비스 탈퇴 없이 팀원만 제거할 때도 존속 팀의 예약을 유지한다. 이는 서비스 탈퇴의 팀 예약 유지 원칙과 맞추는 제안이며 별도의 확정 정책으로 확대하지 않는다.

## 12. 장비 고장

- 고장은 악기별로 관리한다. 합주실 전체 차단 기능은 필요하지 않다.
- 고장 등록 전에 존재하던 예약은 자동 취소하지 않는다.
- 고장 악기를 포함한 새로운 개인 예약은 차단한다.
- 기존 개인 예약도 새 날짜·블록·악기로 변경하거나 교환하면 현재 고장 상태를 다시 검증한다.
- 팀 예약은 고장 상태에서도 가능하며 고장 안내를 표시한다.
- 고장을 팀 독점용 자원 점유와 같은 unique 충돌 행으로 표현하지 않는다. 그렇지 않으면 장비 하나의 고장이 모든 팀 예약을 막는다.
- 고장 등록·해제의 실행자와 이력을 보존한다.

권고안: 악기 행 잠금으로 고장 등록과 새 개인 예약의 순서를 확정한다. 예약이 먼저 확정됐으면 고장 등록 후에도 기존 예약으로 유지하고, 고장 등록이 먼저 확정됐으면 새 개인 예약을 거절한다.

## 13. 동시성과 오류 처리

이 절은 확정 정책을 구현하는 기술 권고안이다.

- 한 합주실·고정 열 블록·수십 명 규모에서는 서울 날짜별 `booking_days` 행 잠금으로 해당 날짜의 예약 변경을 직렬화한다.
- 같은 PostgreSQL을 사용하는 여러 서버 인스턴스에도 DB 잠금이 적용된다.
- 생성, 변경, 취소, 교환 승인, 고정 배정 적용·개방, 회원 탈퇴, 팀 해체에 같은 잠금 규약을 적용한다.
- 잠금은 관련 사용자/팀 행 → 악기 행 → 반복 패턴 guard(해당 작업만) → 날짜 행 → 예약 행 순서로 취득한다. 각 단계 안에서는 ID 또는 날짜 오름차순으로 정렬한다.
- 반복 패턴 쓰기와 날짜 개방은 별도 singleton guard도 사용한다. 아직 개방되지 않은 미래 패턴에는 날짜 행이 없을 수 있으므로 서로 다른 팀·관리자의 설정 경합을 이 guard로 보호한다. 일반 예약은 이 전역 guard를 사용하지 않는다.
- 사용자 대상에는 주체뿐 아니라 실행자·승인자를 포함한다. 팀 구성 변경도 영향을 받는 사용자와 팀을 같은 순서로 잠근다.
- 변경·교환은 기존·새 날짜와 한도에 영향을 주는 모든 날짜를 잠근다.
- 잠금 후 입력 버전과 대상 날짜·자원 집합을 다시 읽는다. 달라진 대상이 잠금 집합 밖에 있으면 더 뒤에서 역순 잠금을 추가하지 않고 트랜잭션을 다시 시작한다.
- 점유 partial unique, 개인 동시 예약 unique, 회차 unique와 ledger 중복 방지 제약을 최종 방어선으로 둔다.
- 존재 여부 조회만으로 중복을 막거나 JVM 안의 `synchronized`만으로 여러 서버의 경합을 처리하지 않는다.
- 승인 화면이나 사용자 응답을 기다리는 동안 DB 트랜잭션을 유지하지 않는다.
- 성공은 commit 이후다. 예약 충돌·한도 초과·권한 유실·만료·버전 불일치를 구분해서 반환하고 화면은 서버 상태를 다시 조회한다.
- 알림 전송 실패가 이미 commit한 예약을 되돌리지 않도록 이벤트와 전송을 분리한다.

구체적인 제약, 상태, 이력과 잠금 순서는 [ERD 설계](ERD.md)를 따른다.

## 14. 필수 검증 시나리오

- 같은 악기 경합은 한 예약만 성공하고 서로 다른 악기의 개인 예약은 공존한다.
- 팀 독점 예약과 모든 개인 예약은 같은 블록에 공존하지 않는다.
- 개인 회원의 같은 시간 중복 예약을 거절한다. 90분 두 악기 예외는 한 예약이다.
- 같은 주체의 동시 60분 요청이 하루 120분 한도를 넘지 않는다.
- 진행 중 잔여 예약은 60분을 소비한다. 시작 전 취소는 복구하고 시작 후 취소는 유지한다.
- 원래 관리자 고정 60분은 면제이며 사용자 변경·교환 후 일반 60분은 소비한다.
- 교환 1:1, 1:2, 2:1 및 개인 90분 두 악기의 생성·분배가 정책에 맞는다.
- 교환과 취소·변경·권한 변경·만료의 경합에서 원자성과 요청 무효화가 유지된다.
- 교환이 제3자 점유·고장·한도에 막히면 양측 예약이 유지된다.
- 고정 배정 중복 실행, 날짜 개방, 요일 변경, 취소 예외, 서버 재시작에서 중복·재생성이 없다.
- 시리즈 수정 충돌은 기존 예약을 보존하고 전체 적용을 거절한다.
- 회원 탈퇴는 개인 예약만 취소하며 존속 팀 예약을 유지한다. 팀 해체는 팀 예약·시리즈를 종료한다.
- 고장과 예약 경합에서 commit 순서에 따른 신규/기존 예약 경계가 유지된다.
- 실제 PostgreSQL의 별도 연결·별도 트랜잭션으로 검증하고 성공 수는 commit 이후 집계한다.

## 15. 개인정보와 공개 범위

일정의 공개 범위와 실명 노출 수준은 아직 사용자 확정 사항이 아니다.

권고안: 인증한 회원에게 팀명·시간·예약 상태·악기를 보여주고 이메일, 초대코드, 푸시 구독 정보는 일정 응답에 포함하지 않는다. 예약자 이름과 팀원·곡 목록의 노출 범위는 UI/API 계약에서 제안임을 표시하고 검토한다. 이 권고안을 무인증 공개 일정의 승인으로 해석하지 않는다.

## 16. 근거

- [PostgreSQL partial indexes](https://www.postgresql.org/docs/current/indexes-partial.html): 한 테이블 안의 활성 점유 행에만 unique를 적용하는 근거.
- [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html): 행 잠금, 트랜잭션 종료 시 해제, 일관된 잠금 순서와 advisory lock 대안.
- [PostgreSQL index uniqueness checks](https://www.postgresql.org/docs/current/index-unique-checks.html): 미확정 충돌 행의 commit/rollback을 기다린 뒤 unique를 판정하는 동작.
- [PostgreSQL date/time types](https://www.postgresql.org/docs/current/datatype-datetime.html): 운영일 `date`와 감사 시각 `timestamptz`의 구분.
