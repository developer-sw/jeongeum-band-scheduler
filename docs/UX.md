## 1. 목표와 첫 운영 범위

2026-10-10 확정된 로그인 유지는 마지막 접속 후 90일이며 서버 요청 때 연장한다. 로그인 화면에 유지 기간과 공용 기기 로그아웃 안내를 표시한다. 브라우저 재실행 시 쿠키와 서버 세션을 먼저 확인해 현재 회원을 복원하고, 만료·로그아웃·회원 비활성화 시 기존 캐시를 비운다. 비밀번호나 별도 인증 토큰을 브라우저 저장소에 보관하지 않는다.

- 하나의 Next.js 코드베이스로 모바일과 PC를 지원한다.
- 첫 운영에 초대·인증·권한, 팀·팀별 곡 목록, 관리자 반복 일정, 예약·취소·변경·교환, 공지, 알림함, Web Push를 포함한다.
- 구현 시작 목표는 2026-10-23, 첫 배포 목표는 2026-10-30, 운영 종료 목표는 2026-12-11이다. 구현 7일은 목표이며 검증된 소요일수는 아니다. 배포 목표일부터 종료일까지 운영 기간은 6주다.
- 모바일은 날짜 선택과 하루 목록, PC는 주간 시간표를 사용한다. API 호출·예약 정책·Query 계층은 공유한다.

## 2. 브랜드와 화면 구성 제안

2026-10-23 사용자 요청: iPhone·Android 홈 화면 설치 이름은 `정음`으로 통일한다. 첨부한 따뜻한 정음 SVG를 원형 글씨와 함께 PNG로 변환해 iPhone 180px apple-touch-icon과 Android 192/512px 일반 아이콘·안전 여백이 있는 512px maskable 아이콘에 사용한다. manifest의 name/short_name과 Apple 웹 앱 제목을 동일하게 지정하고 앱 ID·시작 URL은 `/`로 유지한다. 현재 공개 준비 페이지에도 같은 설치 정보를 적용하며 예약 서비스의 공개 전환과는 구분한다. 기존 설치 항목은 새로 추가해 이름·아이콘을 확인한다.

서비스 표기는 정음 / JEONGEUM을 사용한다. 2026-10-11 사용자 요청에 따라 회장 HTML의 크림·브라운·골드·그린 감성과 첨부 SVG·기타 캐릭터를 적용한다. 원본 SVG의 `ACOUSTIC GUITAR CLUB`은 수정하지 않으며 공식 브랜드 표기는 확인이 필요하다. 기존 남색 로고 파일도 보존한다.

로고 원본이나 사용자 안내 문구를 기존 참고 프로젝트에서 가져오지 않는다. 이번 공통 디자인 변경은 사용자 승인된 범위이며 다크 모드는 추가하지 않는다. 외부 폰트·CDN에 의존하지 않고 시스템 한국어 sans fallback을 사용한다.

로그인한 `/`는 월간 달력·주간 시간표·현재 소속 공연조 요약·공유 빠른 예약 폼으로 구성한다. 1360px 이상은 3단, 1100~1359px는 달력 팝업+2단, 1099px 이하는 날짜 스트립과 하루 10개 카드, 767px 이하는 바텀시트와 하단 탭을 사용한다. 요약은 서울 오늘부터 다가오는 7일의 실제 확정 예약이며 요약 선택은 현재 홈의 날짜로 연결한다. 내 계정·로그아웃은 `/account`, 기능 진입점과 준비 중 목록은 `/more`로 이동한다. `/reservations`·`/my-schedule`·팀·관리 화면은 보존한다.

로그인한 메인은 작은 `JEONGEUM · SENTIMENTAL MUSIC` 브랜드 문구, 굵고 진한 `닉네임님, 안녕하세요.` 제목, 작고 연한 `아이디: 현재 로그인 ID 역할: 현재 계정 역할` 안내 순서로 표시한다. 닉네임·아이디·역할은 현재 세션 정보를 사용하며 계정 화면과 같은 전체 관리자/회원 역할 표기를 따른다. 일반 길이의 아이디·역할은 한 줄로 배치하고, 긴 아이디는 화면을 넘치거나 잘리지 않도록 줄바꿈한다. PC와 모바일의 기존 글씨 크기·굵기를 유지한다. 하단 `JEONGEUM · SENTIMENTAL MUSIC` 문구도 유지한다. 상단에 `1시간 단위 슬롯 연속 최대 2시간` 문구는 사용하지 않으며 예약 시간·한도 정책은 기존 서버와 시간표 안내를 따른다.

2026-10-16 후속 디자인: PC의 인사말과 공연조 강조 선택은 위쪽을 맞춰 배치하고 세로 여백을 줄인다. 제목은 `📌 다가오는 7일 합주`, `✏️ 빠른 예약`으로 표시하며 기타 캐릭터 옆에 `오늘도 맹연습 화이팅! 소리 맞춰봐요 🎶`를 PC·모바일 모두 제공한다. 모바일 헤더는 로고를 제목·소개 두 줄의 왼쪽 중앙에 두고 두 텍스트의 시작점을 맞춘다. `STUDIO NOTE`와 계정·더보기 진입은 유지한다. 관리자 확인 문구는 가입한 계정도 연결 후 카드에서 관리자로 지정할 수 있고 연결 자체로 권한이 바뀌지는 않음을 쉽게 안내한다. 예약·권한의 처리 계약은 바꾸지 않는다.

## 3. 주요 화면과 데이터 접근

2026-10-16 사용자 확정: `/admin/members`는 **전체 관리자 → 팀장 → 일반 회원** 세 영역과 인원 수·바로가기를 제공한다. 같은 명단·계정은 한 카드로 표시하고 관리자 겸 팀장은 관리자 영역에만 표시하되 담당 팀장은 보조 정보로 유지한다. 각 카드에 전체 관리자 지정·해제를 배치하고, 확인·취소·실패·완료 안내도 해당 카드 안에 표시해 상단 확인 영역까지 이동할 필요가 없도록 한다. 가입 전/후 모두 같은 위치에서 처리하며, 미가입 지정은 개인 초대 가입 때 적용함을 안내한다. 역할 변경으로 영역이 바뀌면 고유 ID로 완료 안내와 포커스를 해당 카드에 유지한다. 실행부터 재조회까지 중복 실행을 막고 상태가 바뀐 선택은 다시 확인한다. 수동 계정 연결은 기존 전역 권한이 유지됨을 확인한다. 마지막 활성 관리자 해제는 버튼과 서버에서 차단하며 이름 수정·연결·탈퇴 확인과 브랜드를 보존한다.

활성 회원 인증을 기본 조건으로 하는 기술안을 제안한다. 일정·다른 팀 곡·인명 읽기 범위는 아래의 읽기 제안이며 외부 공개 시간표를 승인한 뜻이 아니다. 버튼 노출은 편의 기능이며 모든 쓰기 권한은 서버에서 재검증한다.

| 화면·행동 | 확정 권한 또는 읽기 제안 |
| --- | --- |
| 초대·로그인 | 초대·인증 정책에 따른 진입; 비활성 회원은 예약 사용 불가 |
| 일정 조회 | 읽기 제안: 활성 회원 내부 조회, 팀명·악기 점유 표시 |
| 내 공연조 일정 | 활성 회원의 현재 소속 정규조·추가조의 실제 확정 예약 조회 |
| 일반 개인 예약 생성 | 활성 본인만 |
| 일반 팀 예약 생성 | 해당 팀에 소속된 활성 팀원 모두 |
| 개인 예약 변경·취소·교환 요청 | 본인 또는 전체관리자 |
| 팀 예약 변경·취소·교환 요청 | 활성·소속 검증을 통과한 작성자, 해당 팀장, 전체관리자 |
| 교환 승인·거절 | 상대 개인 예약자 또는 전체관리자; 상대 팀 예약 작성자·해당 팀장·전체관리자 |
| 팀별 곡 목록 추가·수정·삭제 | 전체관리자와 해당 팀장 |
| 팀별 곡 목록 읽기 | 활성 회원 내부 조회 제안; 외부 공개 없음 |
| 공지 | 전체관리자 작성·수정·중요 공지 고정; 활성 회원 내부 조회 제안 |
| 알림함·Push 구독 | 본인의 데이터만 조회·변경 |
| 반복 일정·악기 관리 | 전체관리자 |

전체관리자의 미소속 팀 일반 예약 대리 생성은 확정된 권한에 추가하지 않는다. 관리자 반복 배정 기능과 일반 예약 생성 권한을 구분한다.

**인명 노출 제안:** 시간표는 팀명·악기 점유를 먼저 보여준다. 다른 회원의 개인 예약은 기본적으로 악기 사용 상태를 표시하고, 연락처·로그인 식별자는 반환하지 않는다. 자신의 예약과 소속 팀 상세에는 필요한 표시 이름을 제공한다. 다른 팀의 전체 명단 공개 범위는 예약 생성 정책과 별개인 읽기 설계 제안이다.

## 4. 예약 화면

### 공통 데이터

상위 화면이 공통 schedule 조회 함수와 Query를 호출하고 DesktopSchedule / MobileSchedule에 동일한 응답을 전달한다. 주 단위 Query를 사용할 경우 모바일은 선택한 날짜만 추출한다. 화면 크기를 바꿔도 예약 요청 형식·권한·한도 계산이 달라지지 않는다.

조회에는 기준 날짜, 예약 블록, 각 자원의 점유·사용 중지, 팀 독점 사용, 본인의 조작 가능 여부, 서버 기준 시각과 예약 가능 범위를 포함하는 계약을 제안한다. 상세 예약과 팀 개인정보는 별도 권한 계약으로 조회한다. 숨겨진 두 UI 컴포넌트가 각각 API를 호출하는 구조를 피한다.

### 모바일 제안

1. 오늘·이전/다음 날짜·날짜 선택기를 표시한다.
2. 선택한 날의 10개 블록을 세로 카드로 표시한다.
3. 각 카드에 시간, 6자원 상태, 전체 합주 여부와 예약 버튼을 둔다.
4. 일반 개인 예약은 사용 가능한 악기 하나를 선택한다. 두 악기 예외는 일반 신규 예약 폼에서 노출하지 않는다.
5. 팀 예약은 정규조·추가조 모두 합주실 전체 독점이다. 팀 사용 시간에는 개인 예약 버튼을 비활성화한다.

6자원은 보컬·건반·일렉기타·베이스·드럼·통기타다. 서로 다른 회원의 개인 예약은 서로 다른 자원으로 같은 블록을 공유할 수 있다. 한 회원의 동시간대 개인 예약 두 건은 허용하지 않는다.

### PC 제안

주간 7열과 고정 블록 10행으로 비교한다. 팀 독점은 팀 카드로, 개인 공유는 자원 상태를 간결하게 표시하고 상세에서 확인한다. 선택 날짜·예약 확인·내 다음 일정 등을 보조 영역에 배치한다. 60분·90분 행을 같은 높이로 그릴 경우 실제 시간 길이가 다름을 시간 레이블로 명확히 표시한다.

기본은 모바일, 태블릿은 하루 목록 중심, 넓은 화면은 주간 표현으로 확장한다. 가로 스크롤에 의존하지 않고 예약 상태를 글자와 함께 읽을 수 있게 한다. 하단 고정 탐색을 사용하면 iPhone 안전 영역과 내용 하단 여백을 처리한다.

## 5. 생성·한도·진행 중 예약

예약 가능 날짜는 한국 기준 오늘부터 14일 뒤까지다. 새 날짜는 00:00에 열린다. 반복 고정 회차가 먼저 적용되고 남은 시간은 평일·주말 모두 선착순이다.

서버가 블록 종료 전이라고 판단하면 시작한 블록의 잔여 시간도 예약할 수 있다. 예: 12:25에는 정해진 12:00~13:00 블록을 선택해 지금부터 13:00까지 사용한다. 확인 화면에 **예약 블록 12:00~13:00 / 이용 가능 약 35분 / 당일 60분 블록 사용량 60분**을 함께 표시한다. 임의 12:25~13:25 예약으로 바꾸지 않는다.

60분 블록의 하루 한도는 개인 회원별 120분, 팀별 120분으로 별도 계산한다. 관리자 고정 배정의 원래 회차·위치에서 사용하는 60분만 면제다. 이를 단건 변경·교환으로 옮긴 60분에는 일반 한도를 적용한다. 교환 상대나 도착한 시간대에 면제가 옮겨 붙지 않는다. 같은 날짜·블록·악기의 실질 변경 없는 요청은 원래 면제를 유지한다. 화면의 한도는 참고 정보이고 제출 시 서버가 최종 검증한다.

생성 흐름은 날짜·블록 → 개인/소속 팀 선택 → 악기 또는 전체 합주 확인 → 사용 가능 시간·한도·고장 경고 확인 → 서버 요청 → 확정 결과다. 서버 성공 전에는 예약 완료로 표시하지 않는다. 충돌 응답에서는 최신 점유를 다시 조회하고 선택 가능한 상태를 보여준다.

## 6. 취소와 변경

| 행동 | 동작 |
| --- | --- |
| 시작 전 취소 | 점유 해제, 해당 한도 사용량 복구, 기존 시작 알림 무효화 |
| 진행 중 취소 | 이력·이미 소비한 60분 한도 보존, 잔여 시간 점유 해제 |
| 종료된 예약 | 취소·변경 불가; 완료된 이용 이력 보존, 지난 시간 재예약 불가 |
| 일반 변경 | 원래 예약 시작 전만 가능; 새 시간·자원의 정책과 권한을 재검증 |
| 고정 회차 변경·취소 | 해당 날짜 회차만 변경; 다음 주 반복 패턴은 유지 |

진행 중 취소 후 잔여 시간 재예약은 진행 중 취소 허용과 잔여 블록 예약 허용에서 도출한 처리다. 취소자의 이미 소비한 한도와 새 예약자의 사용량은 각각 별도 보존·계산한다.

변경은 원래 예약자·팀을 유지한다. 실패하면 원래 예약이 유지되어야 한다. 기술 제안은 원본을 REPLACED 이력으로 보존하고 후속 예약을 만드는 방식이다. 기존 예약 ID의 상세에서 후속 예약 안내 또는 권한 확인 후 이동을 제공한다. 실행자가 관리자·팀장이더라도 creator를 실행자로 바꾸지 않는다. 변경 사건은 CHANGED이며 후속 행의 CREATED 알림을 추가로 보내지 않는다.

동일 날짜·블록·악기의 no-op 변경은 예약을 교체하지 않고 기존 고장 등록 전 예약 지위·면제·대기 교환·알림 계획을 그대로 유지한다. 해당 회차의 변경·취소·교환 결과를 일일 고정 회차 생성 작업이 원래 시간으로 되돌리지 않는다. 반복 패턴 자체의 변경은 전체관리자가 적용 시작일과 기존 예외를 확인하는 별도 화면으로 처리한다.

### 현재 구현: 관리자 반복 배정 화면

`/admin/recurring-assignments`는 현재 활성 전체 관리자만 사용할 수 있다. 관리자 메뉴의 **고정 배정**에서 접근하며 팀장 역할만으로는 화면·API 관리 권한을 얻지 않는다. 일반 회원의 시간표에는 관리자 고정 배정 표시를 제공한다. 직접 고정 60분에는 한도 면제를, 고정 90분에는 기존의 60분 한도 비대상을 안내한다.

1. 활성 정규조·추가조, 매주 요일, 정해진 시간 블록, 적용 시작일을 선택한다. 적용 시작일은 한국 날짜 기준 오늘부터 지정하며, 아직 열리지 않은 미래 패턴 충돌도 검사한다.
2. **배정안 미리 확인**에서 충돌과 계획 회차·보존할 예외를 확인한다. 미리보기는 시간을 확보하지 않는다. 팀·요일·블록·적용일 등 입력이 바뀌면 이전 미리보기를 무효화하고 다시 확인한다.
3. **확인한 배정 생성** 또는 **확인한 패턴 적용**에서 최종 점유·현재 권한·version을 다시 검사한다. 서버 성공 응답을 받은 뒤 적용을 표시한다. 충돌이면 기존 예약·배정·개별 예외를 유지하고 충돌 목록을 표시한다.
4. 배정 카드에서 현재·예정 패턴과 변경 이력, 조회 주차의 회차·개별 예외를 확인한다. 회차 취소는 **시간표·회차 취소**에서 처리하며 해당 날짜의 회차만 취소하고 반복 패턴은 유지한다. 취소 예외는 다음 개방이나 패턴 수정으로 되살리지 않는다.

같은 미래 적용일에 여러 번 수정한 이력이 있으면 가장 큰 revision 번호가 해당 날짜의 최신 패턴이다. 카드의 예정 패턴과 편집창 초기값은 이 규칙을 함께 적용하며, 더 뒤의 적용일 패턴을 가장 가까운 예정 패턴으로 오표시하지 않는다. `VERSION_CONFLICT`가 확정되면 최신 목록을 명시적으로 불러온 뒤 이전 수정·종료 창을 닫고 다시 선택하도록 안내한다. 낡은 입력에 최신 version만 자동으로 넣어 적용하지 않는다. 불확실한 네트워크 응답의 본문·재시도 키는 이 처리로 폐기하지 않는다.

**종료 지정**은 배정을 유지할 마지막 날짜를 선택하는 작업이다. `endDate` 당일까지 회차를 만들 수 있고, 이후의 시작 전·개별 예외 없는 직접 고정 예약만 정리한다. 개별 취소·변경·교환 예외와 진행·과거 회차는 보존한다. 미래 종료일이 설정된 배정은 **종료일 지정**으로 표시하고 그 날짜까지 유지됨을 안내한다. 예정 패턴의 적용일이 포함 종료일을 넘으면 앞으로 적용될 패턴으로 표시하지 않고 변경 이력만 보존한다. 패턴 수정·종료일 연장은 허용하지 않으며 미래 종료일은 **종료일 앞당기기**에서 오늘부터 기존 종료일까지로 조정한다. 이 제한은 이력을 되살리지 않기 위한 이번 API의 기술 계약이다.

불확실한 응답에는 새 쓰기를 막고 **같은 요청 결과 다시 확인**을 제공한다. 화면 안에서는 원래 본문과 재시도 키를 사용하며 오프라인 자동 제출은 하지 않는다. 이 임시 요청은 화면 메모리에 보관하므로 페이지 이동·전체 새로고침·탭 종료 뒤에는 복원되지 않는다. 다시 접속하면 최신 배정·예약 목록을 먼저 확인한다. 관리자 역할 상실·비활성화·계정 전환·로그아웃 시 관리 화면과 이전 권한의 Query를 초기화하고 쓰기마다 서버 권한을 재검증한다.

단건 예약 변경은 아래 화면에서 실제 `CHANGED_EXCEPTION`을 기록한다. 교환 개발은 [RESERVATION_EXCHANGES](RESERVATION_EXCHANGES.md)를 따르며 알림은 후속 단계다. 패턴 관리의 검증 결과는 [RECURRING_ASSIGNMENTS](RECURRING_ASSIGNMENTS.md), 단건 변경 결과는 [RESERVATION_CHANGES](RESERVATION_CHANGES.md)를 따른다.

### 현재 구현: 단건 예약 변경

`/reservations`의 예약·이력에서 **변경**을 선택한다. 다이어리 예약 상세와 더보기의 **예약 변경**에서도 연결한다. 조회된 `canChange`와 서버 기준 현재 시각으로 시작 전 원본만 제공하며, 관리자에게는 선택 날짜의 다른 회원·팀 예약도 권한에 따라 표시한다.

주체·최초 작성자는 고정하고 목적 날짜·정해진 블록·개인 악기를 선택한다. 현재 예약과 변경 목적지, 잔여 이용 시간·60분 사용량·고정 면제 해제·팀 고장 경고를 확인한 뒤 제출한다. 진행 중 목적지의 잔여 시간은 허용하되 원본은 시작 전이어야 한다. 관리자가 다른 주체를 변경할 때 실행자 자신의 한도를 그 주체의 한도로 표시하지 않는다.

서버 성공과 목록 갱신 후 후속 예약을 표시하고 원본 교체 이력을 남긴다. 동일 배치는 원본을 유지한다. 충돌·낡은 version·시작 경계에서는 최신 상태를 확인한 뒤 다시 선택한다. 불확실한 응답은 본문·키를 유지한 **같은 요청 결과 다시 확인**으로 처리하며 추가 변경을 막고 오프라인 자동 제출은 하지 않는다. 원본 상세의 후속 링크로 여러 번 변경한 이력도 따라갈 수 있다.

### 현재 구현: 내 공연조 일정 모아보기

활성 회원 메뉴의 **내 공연조 일정**에서 `/my-schedule`로 접근한다. 별도 페이지는 여러 날짜의 목록 조회를 위한 공간이며 `/reservations`의 날짜별 시간표·예약 생성·취소·내 개인·소속 팀 예약과 이력은 유지한다.

서버의 한국 오늘~실제 예약 가능 마지막 날짜(기본 오늘+14일)의 열린 날짜에서 현재 소속 공연조의 확정 예약을 날짜·시작 시간순으로 표시한다. 다른 팀원이 만든 일반 팀 예약과 실제 생성된 반복 고정 회차를 한 목록에 넣고 예약 출처를 구분한다. 개인 예약, 취소·교체된 예약, 미개방 미래 패턴은 확정 공연조 일정에 넣지 않는다. 오늘 이미 끝난 확정 예약은 종료 상태로 표시하며 진행 중·앞으로의 확정 상태도 구분한다.

전체 공연조가 기본 필터다. 현재 소속된 정규조·추가조 중 하나를 선택할 수 있으며 날짜·요일·시작/종료 시간·공연조 이름·종류를 카드에 함께 표시한다. 일정 선택은 해당 날짜의 `/reservations?date=YYYY-MM-DD`로 연결한다. 소속은 있지만 빈 목록이면 **내 공연조는 열린 기간에 확정된 합주 일정이 없어요**를 표시하고, 팀이 없으면 **아직 소속된 공연조가 없어요**와 구성·계정 연결 확인 안내를 표시한다. 합주실 예약 링크는 모든 상태에서 제공하며 취소 이력도 기존 날짜별 예약 이력에서 확인한다.

PC·모바일 모두 읽을 수 있는 카드 목록과 공통 Query 계층을 사용한다. 20초 주기·화면 포커스·재연결·수동 갱신으로 서버 상태를 확인하고 예약 mutation과 반복 배정 적용 후 같은 예약 Query를 무효화한다. 계정·현재 소속·역할 변경 시 Query 범위를 바꾸어 이전 권한의 목록을 유지하지 않는다. 미로그인은 기존 로그인 안내로 진입을 보호하고 쓰기 동작을 이 목록에 새로 추가하지 않는다.

## 7. 교환 사용자 흐름

2026-10-12 로컬 구현·검증한 `/exchanges`는 기존 다이어리 UI·예약 화면·더보기에서 연결한다. 후보 API는 시작 전 확정 예약의 최소 배치 정보와 묶음 식별을 제공하며 다른 개인 예약 상세의 일반 조회를 허용하지 않는다. 실제 화면·상태·재시도·검증 기록은 [RESERVATION_EXCHANGES](RESERVATION_EXCHANGES.md)를 따른다. 알림함·Push 없이도 목록을 직접 조회해 현재 요청 상태를 확인하며 Push 구현 완료로 간주하지 않는다.

1. 변경 권한이 있는 시작 전 예약을 선택한다. 두 60분 묶음은 같은 날 연속, 같은 개인/팀, 같은 작성자여야 한다. 개인의 두 예약은 악기가 달라도 된다.
2. 상대 예약을 선택한다. 정규조·추가조·개인 간 교환을 지원하되, 양쪽 최종 자원 점유·한도·개인 중복 조건을 만족해야 한다.
3. 양쪽의 기존 시간과 도착 시간, 길이 변화, 유지되는 팀/회원·악기를 함께 보여준다. 120분과 90분 교환에서 이용시간이 달라짐을 명시한다. 두 악기 90분이 두 60분으로 나뉘면 해당 개인 예약자가 직접 악기 순서를 선택·저장한다.
4. 상대 측에 요청한다. 대기 중에는 원래 예약을 유지한다.
5. 상대의 승인 권한자는 서버의 최신 미리보기를 확인하고 승인 또는 거절한다. 필요한 개인 악기 순서가 미선택이면 승인을 완료할 수 없다. 전체관리자도 개인의 순서를 대신 선택하지 않고 저장된 배분을 사용한다.
6. 승인 성공 후 전체 변경 결과를 보여준다. 일부만 교환된 성공 상태를 만들지 않는다.

모든 source 예약에 대한 요청자 권한을 확인한다. 승인은 상대 측 권한을 별도로 확인한다. 다른 일반 팀원이 알림을 받았다고 승인 권한이 생기지는 않는다. 악기 배분은 해당 개인 예약자에게만 제공하는 PATCH /api/v1/exchange-requests/{id}/instrument-allocation 기술 계약을 따른다. 처음부터 두 건 묶음끼리의 2↔2 교환을 추가하지 않는다.

요청은 관련 source 중 가장 이른 시작 시각에 만료된다. 시작 시각에 도달한 경우 승인할 수 없다. 관련 예약 변경·취소, 요청자의 권한 상실, 개인 탈퇴에 따른 실제 개인 예약 취소, 팀 해체는 요청을 무효화한다. 상대 승인 후보 한 명이 역할·소속을 잃었다는 이유만으로 요청 전체를 무효화하지 않는다. 해당 사람의 승인 시도는 403으로 거절하고 다른 적법한 예약자·팀장·전체관리자의 승인 경로는 유지한다. 화면에는 대기·승인 완료·거절·만료·무효화와 사유를 구분한다.

교환의 원본과 후속 예약은 N:M 계보로 연결하는 기술안을 따른다. 응답의 후속 예약 목록으로 화면과 Query를 갱신한다. 후속 행마다 CREATED를 추가 발송하지 않고 하나의 논리 EXCHANGED 사건으로 안내한다.

## 8. 팀·곡·운영 상태

2026-10-14 관리자 회원 탈퇴·팀 해체 확인 흐름은 [MEMBER_TEAM_LIFECYCLE](MEMBER_TEAM_LIFECYCLE.md)을 따른다. `/admin/members`와 `/teams/{id}`의 관리자 영역에서 대상을 확인하고 영향 범위·존속 팀 예약/과거 이력 보존·기기/세션 정리를 설명한 뒤 명시적으로 제출한다. 같은 원래 요청으로 결과 재확인, version/현재 권한 오류와 오프라인 쓰기 차단을 제공한다. 본인 서비스 탈퇴나 팀장 해체 권한은 추가하지 않는다.

팀 상세에 팀 종류·팀장·소속 상태·팀별 곡 목록·다음 예약을 표시한다. 곡 목록은 팀별 제목과 선택 아티스트 정도의 단순 목록으로 설계한다. 공용 곡 카탈로그·음원 검색·곡별 예약 주체는 추가하지 않는다. 곡 CRUD 버튼은 전체관리자와 해당 팀장에게만 노출하며 API도 같은 권한을 검사한다.

한 회원의 여러 정규조·추가조 소속을 목록으로 표시하고 예약할 소속 팀을 선택하게 한다. 정규조 선택을 단일 소속 입력으로 제한하지 않는다. 팀장 여부와 곡 수정 버튼은 선택한 팀의 현재 멤버십을 기준으로 판단한다.

이번 회원·팀 단계는 `/admin/members`에서 가입 전 명단 생성·이름 수정·기존 계정 연결과 전체 관리자 역할 변경을 제공한다. 명단에는 미가입·연결된 계정을 구분해 표시하고, 계정 연결 전에 선택한 명단과 로그인 ID를 확인한다. 초대 발급 화면에서는 미가입 명단을 선택한다. 이름으로 명단·계정을 자동 연결하지 않는다. `/teams`는 팀 목록·내 소속을, `/teams/[id]`는 팀별 소속·팀장·곡 목록과 권한에 맞는 작업을 제공한다. 다른 팀 일반 회원에게 내부 명단·로그인 ID를 공개하지 않는다. 가입 전 팀장 배정은 로그인 권한을 만들지 않으며 연결된 활성 계정에서만 권한이 생긴다.

개인 탈퇴 시 해당 개인의 미래·진행 중 개인 예약과 그 취소에 연관된 교환, 요청자 권한 상실에 해당하는 교환을 정리하되 존속하는 팀 예약은 일괄 취소하지 않는다. 팀 예약의 작성자가 탈퇴했을 때는 팀장·전체관리자의 관리와 다른 활성 조원의 예정 알림을 유지한다. 그 작성자가 상대 승인 후보였다는 이유만으로 유효한 대기 교환 전체를 종료하지 않는다. 팀 해체는 관련 미래·진행 중 팀 예약과 대기 교환 정리 결과를 보여준다. 이력 조회에서 현재 존재하지 않는 회원·팀 때문에 화면이 깨지지 않게 한다.

악기 사용 중지는 합주실 전체 폐쇄가 아니다. 개인 새 예약과 새 배치의 자원 검증에 적용하고, 팀 전체 합주에는 고장 악기를 명시해 경고한다. 기존 예약은 유지하고 사용 중지 상태를 보여준다. 유지된 기존 예약을 화면에서 자동 취소하지 않는다.

전체 관리자는 **관리 → 악기 고장 관리**, 모바일 **더보기 → 악기 고장 관리**의 `/admin/instrument-faults`에서 여섯 악기 상태와 등록·복구 이력을 확인한다. 정상 악기는 사유를 입력하고 등록 내용을 확인한 뒤 처리하며, 고장 악기는 최신 이력을 확인하고 선택 복구 메모와 함께 복구한다. 다른 관리자의 변경으로 버전이 오래되면 최신 상태를 다시 확인한다. 응답 유실 시 같은 본문·키의 결과를 명시적으로 재확인할 때까지 다른 쓰기를 막고 오프라인 자동 실행을 하지 않는다. 계정·권한 변경 시 이력과 작성 상태를 분리한다. LEGACY는 기존 고장 상태의 확인 기록이며 해당 시각을 최초 등록 시각으로 표시하지 않는다. 상세 계약·검증은 [INSTRUMENT_FAULTS](INSTRUMENT_FAULTS.md)를 따른다.

## 9. 공지·알림함·설치 흐름

2026-10-13 공지·알림함 구현은 기존 다이어리 헤더와 더보기에서 `/notices`, `/notifications`로 연결한다. 공지 상세 `/notices/{id}`는 활성 회원이 조회하고 전체 관리자에게만 작성·수정·삭제 조작을 제공한다. 일반 텍스트 줄바꿈을 보존하고 HTML을 실행하지 않는다. 중요 공지는 목록 위에 고정하며, 사용자가 확정한 대로 **처음 중요 공지로 작성할 때만** 전체 활성 회원의 알림함에 안내한다. 작성 확인에 이 시점을 설명하며 수정·고정 변경으로 재알림하지 않는다.

알림함은 읽지 않은 건수·전체/미읽음 필터·이전 항목·개별/전체 읽음을 제공한다. 전체 읽음은 조회 응답의 서버 시각까지만 처리한다. 알림 이동 대상은 내부 공지·예약·교환 경로만 허용하고 이동 후 해당 API의 현재 권한을 검사한다. 삭제된 공지·바뀐 예약·무효화된 교환의 오래된 알림은 기존 수신함 이력을 보존하며 새 변경 권한을 부여하지 않는다. 계정·역할·소속·비활성화 시 Query와 작성·재시도 상태를 분리한다. 공지 쓰기의 성공 응답이 유실되면 같은 본문·키 재확인 전 다른 쓰기를 막고 오프라인 자동 제출하지 않는다. 실제 검증 상태는 [NOTICES_NOTIFICATIONS](NOTICES_NOTIFICATIONS.md)를 따른다.

전체관리자만 전체 공지를 작성하며 제목·본문·중요 공지 고정을 제공한다. 조별 공지는 추가하지 않는다. 공지 목록과 상세에서 중요 공지를 구분하고 상단에 고정한다. 중요 공지 알림은 전체 활성 회원에게 전달한다. 일반 공지의 Push 범위는 [NOTIFICATIONS.md](NOTIFICATIONS.md)의 확정 이벤트 표와 제안을 따른다.

알림함은 Push 설치·허용 여부와 관계없이 이용할 수 있다. 알림에서 예약·교환·공지 상세로 이동하고, 최신 상태가 달라졌으면 현재 상태를 함께 표시한다. 이미 무효화된 요청의 오래된 알림에서 승인할 수 없도록 한다.

PWA는 manifest·아이콘·standalone·service worker·오프라인 안내·Web Push를 포함한다. Next.js App Router의 manifest 지원을 사용할 수 있다. [Next.js 공식 PWA 가이드](https://nextjs.org/docs/app/guides/progressive-web-apps)

기능 지원을 확인하고 사용자가 알림 켜기 버튼을 눌렀을 때 권한을 요청한다. iPhone은 홈 화면 추가 → 설치된 앱 실행 → 알림 켜기 순서로 안내한다. iOS Web Push의 홈 화면 앱과 사용자 동작 조건을 반영한다. [WebKit 공식 설명](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

예약 변경을 오프라인 대기열에 저장해 재접속 때 자동 제출하지 않는다. 오프라인에서는 연결 안내를 보여주고, 재접속 시 점유·권한을 갱신한다. service worker의 인증 데이터 캐시·계정 전환 처리는 [NOTIFICATIONS.md](NOTIFICATIONS.md)를 따른다.

## 10. 갱신·오류·접근성 제안

2026-10-14 Push 설정은 `/notifications/settings`에서 제공한다. 사용자 버튼에서만 권한을 요청하고 미지원·HTTP·서버 미설정·거절·구독 실패와 본인 기기 목록을 구분한다. iPhone 설치 안내·기기별 해제·이전 계정 메시지 보호·캐시 제한은 [WEB_PUSH_REMINDERS](WEB_PUSH_REMINDERS.md)를 따른다. 로그아웃하면 해당 기기의 발송 연결만 정리하며 다른 기기는 유지한다.

- 예약 화면이 보일 때 15~30초 polling, 화면 복귀·네트워크 재연결 시 refetch, 본인의 변경 성공 후 관련 Query invalidate를 제안한다. invalidate만으로 다른 사용자의 화면이 갱신되지는 않는다. [TanStack Query 공식 문서](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)
- Push는 일정 데이터의 최종 상태가 아니다. 알림 클릭과 화면 복귀 시 API를 다시 조회한다.
- 401은 재로그인, 403은 현재 권한 설명, 예약 충돌은 재조회, 한도 초과는 서버 계산값 표시로 처리한다. 상세 오류 코드·상태는 API 계약에 맞춘다.
- 이중 제출 버튼을 막되 서버의 동시성 검증을 대체하지 않는다. 응답을 잃은 요청은 무작정 다시 생성하지 않고 최신 예약과 요청 결과를 확인한다.
- 터치 영역·본문 크기·키보드 탐색·포커스 복원·색상 대비를 확인한다. 상태 전달을 색상에만 의존하지 않는다.
- 정음 로고, 모바일 설치, 교환 미리보기, 고장 경고, 남은 시간 표시를 실제 기기 점검 항목에 포함한다. 검증 계획은 [TEST_PLAN.md](TEST_PLAN.md)를 따른다.
