## 사용자 확정 범위

- 전체 관리자만 전체 공지를 작성·관리하고 활성 회원이 조회한다. 조별 공지·공개 외부 게시판은 추가하지 않는다.
- 제목·본문·중요 고정을 제공한다. 2026-10-13 사용자 선택으로 **처음 중요 공지로 작성할 때만** 활성 회원별 알림함 안내를 만든다. 일반 공지 작성·수정·일반→중요 전환·고정 해제/재고정은 재알림하지 않는다.
- 개인 관련 예약 알림은 본인, 팀 예약 알림은 해당 팀의 활성 조원 전체가 받는다. 실제 고정 회차 생성도 즉시 생성 알림을 만든다.
- 예약 변경·취소, 교환 요청·완료·거절·철회·만료·무효화 결과를 관련 당사자에게 제공한다. 같은 사건에서 여러 역할인 사용자는 한 건만 받으며 관리자라는 이유로 모든 예약 알림을 받지 않는다.
- 본인 알림만 조회·읽음 처리한다. 알림을 받은 사실은 예약 편집·교환 승인 권한이 아니다. 내부 이동 후 현재 권한과 현재 상태를 다시 검사한다.
- Web Push·시작 1시간 전 알림·탈퇴/팀 해체 예약 정리는 첫 운영 필수 후속 단계다. 이번 사이트 내 알림 기록을 실제 단말 발송으로 표시하지 않는다.

## 기술 구현 계약

공지 제목은 trim 후 1~120자, 본문은 1~10000자 일반 텍스트다. 첨부 파일·HTML 편집기를 추가하지 않는다. `/api/v1/notices`는 공지 조회·등록, `/{id}`는 상세·수정·삭제다. 중요 고정·작성 시각·ID 내림차순 cursor와 limit으로 목록을 제공한다. 공지 ID는 문자열, version은 숫자, 시각은 ISO 형식이다.

공지 쓰기는 `Idempotency-Key`를 요구한다. 현재 활성 전체 관리자·version을 공통 guard→사용자→공지 잠금 뒤 재검사하고 상태·최초 중요 알림·재시도 기록을 10초 제한의 한 트랜잭션에서 확정한다. 같은 실행자의 같은 경로·정규화 본문·키 재시도는 같은 공지를 재확인하며 다른 재사용은 거절한다. 삭제는 `deleted_at`으로 공개 조회에서 숨기고 알림 참조와 재시도 기록을 보존하는 기술 선택이다. 성공 응답 유실 시 같은 본문·키로 명시적으로 재확인한다.

`GET /api/v1/notifications`는 본인의 목록·미읽음 건수와 이전 ID cursor를 반환한다. `PATCH /{id}/read`는 본인 항목의 최초 읽음 시각을 보존하고 다른 사용자의 ID는 404다. `POST /read-all`은 `{through}`의 서버 기준 시각 이하까지 처리하며 미래 시각을 거절한다. 목록은 전체/미읽음 필터를 지원한다.

V9는 `announcements`, `notice_idempotency_requests`, `notifications`를 추가한다. 이전 migration을 수정하거나 기존 예약에 알림을 소급 생성하지 않는다. 알림에는 논리 사건 key·유형·수신자·내부 이동 대상·읽음/생성 시각과 필요한 operation/예약/교환/공지 참조를 기록하며 `(event_key,user_id)`를 unique로 둔다.

알림 발행 서비스는 업무 트랜잭션 안에서만 호출한다. 생성은 실제 예약 ID, 변경·취소는 operation과 원본 예약, 교환은 request ID와 상태 사건으로 중복을 식별한다. no-op·재시도·회차 재개방은 새 사건이 아니다. 변경·교환의 후속 예약 행마다 별도 CREATED를 발행하지 않는다. 예약을 변경·취소하거나 패턴 회차를 정리해 무효화된 대기 교환도 같은 트랜잭션에 기록한다. 실패 시 업무·알림·재시도 기록을 함께 롤백한다.

## 화면

`/notices`는 중요 고정·일반 공지 목록과 관리자 작성, `/notices/{id}`는 상세와 관리자 수정·삭제 확인을 제공한다. `/notifications`는 본인 미읽음 건수·필터·이전 항목·개별/전체 읽음과 내부 상세 이동을 제공한다. 기존 PC 헤더와 모바일 더보기에서 연결하며 계정/권한 전환과 오프라인·응답 유실을 기존 공통 API·Query·쓰기 상태 규약으로 처리한다.
