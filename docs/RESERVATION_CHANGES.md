# 단건 예약 변경 구현과 검증

작성 기준: 2026-10-12, Asia/Seoul. 사용자 요청에 따라 README 갱신은 미루고 `codex/reservation-change`에서 개발한다. 확정 정책은 [PROJECT_CONTEXT](PROJECT_CONTEXT.md)와 [RESERVATION_RULES](RESERVATION_RULES.md), API·DB·화면 계약은 [API](API.md)·[ERD](ERD.md)·[UX](UX.md)를 따른다. 실제 개발 DB 계정·예약·볼륨을 보존하며 새 기능의 쓰기 검증은 Testcontainers 또는 임시 PostgreSQL에서 수행한다.

## 범위와 데이터 처리

`PATCH /api/v1/reservations/{id}`는 현재 활성 계정의 개인 예약자·소속 팀 예약 작성자/팀장·전체 관리자 권한을 검사한다. 원본은 CONFIRMED이며 시작 전이어야 한다. 목적지는 한국 오늘~오늘+14일의 개방 완료 날짜, 종료 전 고정 블록이다. 진행 중 목적지의 남은 시간도 허용하고 60분 사용량은 60분으로 계산한다. 팀·개인 주체, purpose, 최초 작성자는 변경할 수 없다.

새 요청은 개인 예약 주체도 ACTIVE여야 하며 INACTIVE/WITHDRAWN이면 관리자 대리 변경과 no-op도 403으로 거절한다. 존속하는 활성 팀 예약의 최초 작성자가 비활성화·탈퇴한 경우에는 현재 적법한 팀장·관리자가 해당 팀 예약을 변경할 수 있고 최초 작성자를 그대로 보존한다.

실제 변경은 원본 REPLACED·version 증가, 원본 점유 해제·시작 전 60분 사용량 복구, 후속 CHANGE 예약·새 점유·새 RESERVE, V6 계보, CHANGE operation과 PATCH 재시도 결과를 한 트랜잭션에서 저장한다. 관리자 대리 변경도 최초 작성자를 유지하고 operation에 실행자를 기록한다. 60분 고정 면제는 실제 이동 후 유지하지 않는다. 같은 날짜에서는 해제할 원본 사용량을 최종 한도에서 빼고 다른 날짜에서는 각 주체의 당일 사용량을 별도로 검증한다.

개인은 정상 신규 배치에서 한 악기를 선택하며 기존 두 악기 90분 예외만 목적 90분에서 최대 두 종류를 허용한다. 60분으로 이동하면 한 종류를 요구한다. 새 개인 배치의 고장·동시간 개인 중복·악기 점유를 거절하고 팀 배치는 여섯 자원 독점과 고장 경고를 적용한다. 동일 날짜·블록·악기 집합은 no-op으로 원본 ID·version·면제·기존 고장 예약 지위를 유지하며 재시도 기록만 남긴다.

예외 자격은 상세의 `dualAssetException`으로 전달한다. 기존 교환 예외의 90분 내 이동에서는 한 종류만 선택해도 자격을 유지하고 최대 두 종류 선택을 허용한다. 60분 이동에서는 자격을 해제한다. 이는 서버가 보존하던 예외 출처를 화면에도 명시하는 계약이며 일반 예약에 두 종류 자격을 새로 부여하지 않는다.

단건 고정 회차 변경은 원래 assignment/week 식별자를 유지하고 CHANGED_EXCEPTION 및 현재 SUCCESSOR 링크를 기록한다. 목적지가 다른 주차여도 원래 위치에 재생성하지 않고 다음 주 반복 패턴은 유지한다. 후속 예약을 취소하면 같은 회차의 CANCELED_EXCEPTION을 기록한다.

## 잠금·재시도·조회

공통 guard 아래 성공 재시도부터 확인한다. 새 요청의 적격성을 확인한 무쓰기 계획 단계에서 준비되지 않은 목적 날짜가 발견된 경우에만 별도 날짜 개방을 수행하고 최종 쓰기 트랜잭션으로 다시 진입한다. 쓰기는 `directory_mutation_guard → 관련 사용자 ID → 팀 ID → 악기 ID → 원본/목적 날짜 오름차순 → 원본 예약` 순으로 잠그며 10초 제한을 적용한다. 현재 권한·활성 상태·version·시각·개방 상태·점유·고장·한도를 최종 잠금 후 재검증한다. 실패하면 원본·점유·사용량·계보·회차 예외와 성공 재시도 기록을 모두 롤백한다.

`Idempotency-Key`는 실행자·PATCH 경로·원본 version·목적 날짜/블록·정규화한 악기 집합에 연결한다. 같은 키/본문의 재시도는 같은 결과 ID를 반환하고 다른 본문은 IDEMPOTENCY_KEY_REUSED로 거절한다. 재시도도 현재 편집·조회 권한을 요구한다. Summary/Detail의 canChange는 조회 당시의 조작 가능 여부이며 서버가 제출 시 재검사한다. Detail의 successorIds는 직접 후속 예약을 연결한다.

이미 성공한 요청의 재확인은 새 배치를 만들거나 날짜 개방을 실행하지 않는다. 실행자의 현재 활성 상태·권한을 검사하고 기존 성공 결과를 돌려주므로 결과 예약의 시작 시각·예약 가능 기간·개인 주체 상태가 이후 바뀌었어도 중복 변경을 만들지 않는다.

## 후속 연결과 제한

교환 요청·알림함·Push 테이블과 API는 아직 없다. 이번 CHANGE operation은 후속 무효화·CHANGED 사건 연동 지점이며 실제 교환 무효화·알림 재계획·Push 발송은 구현 완료로 주장하지 않는다. 후속 구현에서는 no-op의 관련 상태를 유지하고 실제 변경의 단일 사건만 처리하며 successor별 CREATED 알림을 중복 만들지 않는다. 불확실한 요청의 본문·키는 현재 열린 화면의 메모리에서만 유지되므로 새로고침·이동 이후에는 현재 예약과 이력을 먼저 확인해야 한다. 10초 제한은 각 쓰기 트랜잭션 기준이며 별도 날짜 개방 준비를 포함한 HTTP 요청 전체의 상한은 아니다.
