# 실제 데이터 이전 준비

2026-10-29 후속: 실제 이전·공개 전환과 실제 데이터의 기존 S3 암호화 백업·독립 복원을 승인받았다. 최종 쓰기 동결·운영 DB 이전·새 운영 백업의 PC 독립 복원·내부 앱 검증과 현재 공개 경계는 [실제 이전 기록](DATA_MIGRATION_CUTOVER.md)을 따른다. 아래 준비 범위와 미실행 설명은 이전 단계의 기록이다.

이 문서는 로컬 개발 DB의 준비용 백업과 별도 복원·대조 범위, 이후 운영 이전의 승인 경계를 정리한다. 업무 정책의 기준은 [PROJECT_CONTEXT](PROJECT_CONTEXT.md)와 [RESERVATION_RULES](RESERVATION_RULES.md)이며, 실제 운영 적용 순서는 [PRODUCTION_INSTALL_PLAN](PRODUCTION_INSTALL_PLAN.md)을 따른다.

## 승인 범위와 현재 상태

현재 승인 범위는 정확한 기존 로컬 개발 DB를 식별하고 읽기 전용으로 백업·기준선을 확보한 뒤, 네트워크가 없는 새 PostgreSQL과 전용 새 볼륨에 독립 복원하여 SQL로 대조하는 **이전 준비**다. 기존 계정·회원·명단·팀·예약·개발 볼륨과 설정을 보존한다. 원본에 정리 SQL을 실행하거나, 복원 검증을 위해 Backend를 기동하지 않는다.

실제 운영 DB로 데이터 이전, 공개 앱 전환, AWS 변경과 GitHub 게시를 승인한 것으로 해석하지 않는다. 새 설정 암호문의 PC 밖 추가 사본은 사용자 선택에 따라 당분간 제외하며, 이번 준비의 선행 조건으로 다시 요구하지 않는다. 이 선택이 PC 밖 사본 검증 완료를 뜻하지는 않는다.

### 스키마 표현 차이의 분리 검증

최초 엄격 비교가 제약조건·index 정의 **41개**의 문자열 차이로 거부되어 새 검증 대상을 중지했다. 행·시퀀스·Flyway·집계는 같았다. 원본 DB·schema를 고치거나 암호문을 다시 만들지 않고, 같은 복원본의 읽기 전용 후속 검사를 수행했다.

- **40개:** `ANY`/`ALL`의 대문자·밑줄 literal만 든 1차원 배열에서, typmod 없는 내장 varchar 배열 전체를 text 배열로 cast한 표현과 각 같은 원소를 text로 cast한 표현의 차이였다. 연산자·순서·중복·값을 유지하고 정확한 두 문법만 대조했다. PostgreSQL 17도 text/varchar의 binary coercion을 설명하며, 이번 실제 엔진의 catalog와 **서로 다른 배열 33종의 값·text[] 타입**을 직접 확인했다. [공식 CREATE CAST 문서](https://www.postgresql.org/docs/17/sql-createcast.html)
- **1개:** 지정한 `time_blocks_check1`에서 OR 연쇄의 괄호 결합 구조만 달랐다. 정확히 10개의 순서 있는 조건을 대응하고 각 AND 조건·코드·숫자는 원문 그대로 비교했다. 실제 엔진에서 TRUE/FALSE/NULL의 **27가지 OR 결합 조합**도 확인했다.

원본 원시 schema 지문은 저장 manifest에, 복원본 원시 지문은 후속검사에서 산출한 복원 fingerprint에 각각 연결한 뒤 전체 metadata를 비교했다. 위 40+1 규칙 외의 필드는 하나도 제외하지 않았고 encoding·locale·컬럼·기본값·FK/unique/index·sequence 정의 등은 유지했다. 합성 archive 보호 **13개**, 좁은 schema 규칙 보호 **24개**를 통과했다. 이 결과는 schema 문자열 지문 자체가 같았다는 뜻이나 일반 SQL 표현 전체의 동등성 보장이 아니다.

실제 개발 snapshot의 독립 로컬 복원 결과이며, 운영 DB 이전·운영 앱 역할/자격증명의 실제 적용·Backend 기동·운영 origin 로그인/Push·전체 서비스 RPO/RTO·GitHub 게시 결과로 확대하지 않는다. 아래는 이 결과 이후 실제 전환에 적용할 계획이다.

## 준비용 snapshot과 최종 이전본의 구분

준비용 snapshot은 백업에 사용한 일관된 시점의 사본이다. 원본의 이후 회원·권한·예약 변경을 포함하는 최종 이전본으로 취급하지 않는다. 원본 앱과 worker가 계속 동작했다면 백업 직후 현재 DB와 수치가 달라질 수 있으므로, 동일 snapshot의 기준선과 복원본을 비교하고 시점 차이를 구분한다.

실제 이전 승인 후에는 쓰기 동결 시각과 최신 원본을 확인하고, 원본 앱·worker의 쓰기를 통제한 뒤 **새 최종 백업 → 독립 복원 → 데이터·권한·시퀀스 재대조**를 수행해야 한다. 원래 개발 DB와 운영 DB를 동시에 서비스의 쓰기 원본으로 사용하지 않는다. worker OFF만으로 사용자 쓰기가 차단된다고 가정하지 않는다.

적용된 V1~V12 migration의 스키마 기준은 Flyway 이력을 포함한 **39개 테이블·29개 시퀀스**다. 이는 코드의 예상 범위이며, 실제 원본의 목록·버전·checksum·적용 성공 상태를 별도로 확인한다. 예상과 다르면 임의 초기화나 migration 강제 재적용으로 맞추지 않는다.

행 수만 일치하는 것으로 보존을 판정하지 않는다. 안정된 순서와 타입 표현을 사용한 비공개 내용 지문, 관계·제약·시퀀스와 중요한 상태별 집계를 함께 비교한다. 비밀번호 해시·세션 속성·초대 해시·Push endpoint·개별 ID·개별 지문과 실제 회원/예약 집계는 공개 문서·로그·시험 fixture에 넣지 않는다. 시퀀스 확인에 `nextval`처럼 상태를 바꾸는 함수를 사용하지 않는다.

기존 관리자를 bootstrap으로 다시 만들거나 이름으로 계정·명단을 재연결하지 않는다. 전체 관리자의 팀장 겸임과 기존 팀 배정을 보존하고, 이미 가입한 계정의 실제 권한과 가입 전 명단의 예정 권한을 구분한다. 완료 이력·취소 후 사용량·변경/교환 원본과 후속 관계를 지우거나 현재 상태만으로 재계산하여 덮어쓰지 않는다.

## DB 소유권 매핑과 앱 권한

독립 복원의 DB 소유권·ACL을 원본과 비교하되, 개발 DB 자격증명을 운영에 그대로 사용하지 않는다. 원본 소유자와 복원 대상 역할의 대응을 명시하고, 역할명이 달라 생기는 의도된 매핑과 예상하지 못한 권한 누락을 구분한다. 역할/ACL 불일치를 무시하거나 전체 schema를 포괄 권한으로 열어 통과시키지 않는다.

복원·schema 소유 작업에 필요한 역할과 실제 앱의 최소 권한 역할을 분리한다. 운영 앱 역할에 superuser·역할 생성·DB 생성 권한을 부여하지 않으며, 앱 접속 권한과 테이블/시퀀스 접근·필요한 기본 권한을 별도로 검증한다. 구체 운영 역할 매핑과 실제 적용은 운영 이전 승인 후 확인한다. 역할 자격증명이나 비밀번호 해시는 공개 비교 결과에 출력하지 않는다.

## 순수 SQL 대조를 먼저 하는 이유

현재 시간표 조회는 [`ScheduleService.schedule`](../backend/src/main/java/kr/jeongeum/scheduler/reservation/service/ScheduleService.java)에서 날짜 준비를 호출하고 날짜 행을 확보한다. 따라서 **시간표 GET도 날짜·반복 예약·관련 알림 상태를 변경할 수 있다**. 반복 worker를 꺼 둔 상태를 앱 전체의 읽기 전용 상태로 간주하지 않는다. 로그인·세션 갱신·기동 시 Flyway도 최초 SQL 대조와 구분해야 한다.

이번 준비에서는 앱 미기동 복원본을 순수 SQL로 먼저 비교한다. 이후 앱 기동·시간표 조회·누락 날짜 복구를 검증할 때는 별도 승인된 복원 후보에서 수행하고, 원본 snapshot과의 동일성 검사 결과와 앱이 정상 생성한 복구 행을 분리해 기록한다. 기존 원본·운영 DB에서 시간 조작·강제 실패·복구 검증을 하지 않는다.

## 새 origin으로 이전할 때의 후속 처리

다음은 **기술 권고와 후속 실행 계획**이다. 이번 준비에서 세션·초대·구독·발송 작업을 정리하거나 새 도메인으로 실제 계정을 연결하지 않는다. 데이터 변경 도구·대상·감사 기록을 준비하고 운영 이전 시 승인 범위를 확인한 뒤 적용한다.

- **재로그인:** 인증은 JWT가 아닌 Spring Session JDBC다. 세션까지 원본과 대조해 보존한 후, 이전 후보의 기존 세션 종료 여부를 명시적으로 결정한다. localhost의 쿠키는 새 운영 도메인으로 전달되지 않으므로 기존 ID·비밀번호로 다시 로그인한다. 계정을 새로 만드는 것이 아니다. 동일 운영 origin 재시작의 로그인 유지 검증과 최초 origin 이전을 구분하며, 기존 90일 유휴 연장·Secure/HttpOnly/SameSite=Lax 계약을 유지한다.
- **초대 링크:** 초대 해시·명단 ID·만료/사용/해지 상태를 보존한다. localhost 초대 링크는 자동으로 새 도메인 링크가 되지 않는다. 운영 주소의 링크 안내 또는 명단 ID를 유지하는 재발급을 검토하되, 임의 재발급·만료 연장·예정 관리자 권한 변경은 하지 않는다. 원문 초대 코드를 해시에서 복구할 수 있다고 가정하지 않는다.
- **기기 설치·구독:** 이전 홈 화면 아이콘은 자동으로 새 주소로 바뀌지 않는다. 새 운영 주소에서 설치·로그인·권한 허용·기기 구독을 검증한다. 현재 구독 schema에는 origin/VAPID key 식별자가 없고 브라우저가 기존 구독을 재사용하므로, DB 복사나 단순 다시 연결만으로 운영 키와 안전하게 연결됐다고 단정하지 않는다. 초기 운영 VAPID 키를 고정하고 키 회전은 명시적 해제·재구독으로 별도 검증한다.
- **Push binding·outbox:** 이전 binding과 미발송 Push의 비활성/종료 범위를 후보 DB에서 감사 가능하게 정한다. 알림함·SENT/COMPLETED 이력·중복 방지 키는 임의 삭제하지 않는다. 작업 종류별 대기/재시도/처리 중 상태·lease·구독 binding version·예약 version·시작 시각·논리적 원본을 대조하고, 지연된 시작 알림이 발송될 범위를 확인한다. 이미 외부 Push 서비스가 수락한 알림을 철회하거나 전달 exactly-once를 보장하지 않는다.
- **반복 날짜·교환:** 기존 prepared 표식·회차·예외·연결을 그대로 복원한다. 반복 날짜 개방은 서울 오늘부터 +14일까지 기동·자정·정기 재시도로 복구한다. 취소/변경/교환 예외를 재생성하지 않는지, 종료된 팀/배정이 복귀하지 않는지 확인한다. 교환 만료와 시작 알림 계획의 정상 복구 변경분도 최초 snapshot 대조와 구분한다.

세부 근거는 [인증](AUTHENTICATION.md), [회원·팀 관리](MEMBER_TEAM_MANAGEMENT.md), [반복 배정](RECURRING_ASSIGNMENTS.md), [Push·시작 알림](NOTIFICATIONS.md), [배포 사전 점검의 데이터/origin 전환](DEPLOYMENT_PREFLIGHT.md)을 따른다.

## 후속 활성화와 공개 전환 게이트

운영 이전·내부 앱 검증·공개 전환은 별도 승인 후 아래 순서로 진행한다. 각 설정은 재기동 시 반영되는 값을 포함하므로 파일 변경만으로 활성/중단이 끝났다고 보고하지 않는다.

1. 최종 원본 쓰기를 동결하고 새 최종 백업·독립 복원·SQL 대조를 완료한다. 기존 원본/볼륨을 보존하고 원본·복원 대상 혼동을 막는다.
2. 전용 운영 DB에 복원하고 명시한 소유권 매핑·최소 앱 권한을 검증한다. 자동 worker와 외부 Push 기능을 모두 OFF로 두고, 승인된 범위에서 내부 앱을 순서대로 기동한다. 숨은 쓰기와 초기 Flyway 동작을 관측한다.
3. 후보 DB의 origin 후처리와 복구 가능한 운영 설정, 새 운영 DB의 암호화 백업·독립 복원·감시를 확인한다. 원래 빈 운영 스키마의 백업 성공만으로 이전한 실제 데이터의 보호 완료를 대신하지 않는다.
4. 쓰기 허용 여부·전환 시각·중단/복구 조건을 승인받아 공개 경로를 전환한다. 별도 차단 장치가 없으면 실제 계정이 로그인 가능한 시점부터 사용자 쓰기가 생길 수 있다고 본다.
5. 유효한 운영 키로 Push 기능만 ON, 모든 worker는 OFF인 상태에서 새 기기를 등록한다. 이후 반복 날짜 개방 → 교환 만료 → 시작 알림 계획을 각각 활성화·검증하고, 유효 대기 작업과 구독을 재검토한 뒤 Push 발송 worker를 마지막에 켠다.
6. 운영 origin에서 로그인/권한·예약·설치·실제 알림 수신/클릭·기기별 로그아웃·탈퇴 전체 차단을 확인한다. 이전 합성 주소의 성공을 이 검증으로 대체하지 않는다.

비교 실패·잘못된 원본·권한 과다/누락·예상하지 못한 쓰기·조기 worker 발송이 발견되면 다음 단계로 진행하지 않는다. 새 운영 쓰기가 발생한 뒤에는 최신 운영 DB와 변경 이력을 먼저 보존해야 하며, 오래된 로컬 dump를 덮어쓰거나 로컬 원본을 다시 열어 복구하지 않는다. 원본/볼륨 삭제·초기화·`down -v`·prune는 이전 준비나 롤백 수단으로 사용하지 않는다.
