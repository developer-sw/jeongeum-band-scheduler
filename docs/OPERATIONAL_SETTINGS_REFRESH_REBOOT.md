# 최신 설정 암호화 복구본 갱신·새 코드 재부팅 검증

기록일: **2026-10-28, Asia/Seoul**. 사용자 승인으로 [준비 대기 코드의 실제 적용](OPERATIONAL_READINESS_SERVER_VALIDATION.md) 후 남은 설정 복구본을 갱신했다. 설정 암호화·독립 복원, 재부팅 전후 보존 대조와 **부팅 후 정규 백업·감시의 자동 실행 관측을 완료**했다. [이전 34파일 복구본](OPERATIONAL_SERVER_VALIDATION.md)과 [이전 코드의 재부팅 기록](OPERATIONAL_REBOOT_VALIDATION.md)은 각 실행의 이력으로 보존한다.

## 최신 설정 복구본·독립 복원

선택한 설치 파일 **34개**를 기존 PC 원본에서 재구성해 새 암호문을 만들었다. 이전 33파일은 그대로 유지하고 `operational-backup.py` 하나만 main `351bf69`의 검증된 내용으로 바꿨다. 기존 unit의 실제 설치 바이트와 기본 도구 `79811a0`, rc.3 앱 `a00a791`·이미지 고정값을 유지하며 manifest에 기본 출처와 코드 한 파일의 override 출처를 구분했다.

| 검사 | 확인한 결과 |
|---|---|
| 새 암호문 | **4,099,108bytes**, 선택 34파일과 manifest·수동 복구 지침을 포함한 **36 members** |
| 저장본 인증 | Windows age **1.3.2**의 별도 프로세스가 저장된 새 암호문을 다시 복호화·인증 |
| 독립 디스크 복원 | 새 보호 폴더에 34파일을 실제 복원하고 내용·크기·SHA·Windows native ACL 대조 |
| 검증용 평문 정리 | 임시 복원 파일 34개와 검증용 자격증명·폴더를 정리, 남은 임시 평문 **0개** |
| 기존 원본 보존 | 원본 25파일·기존 helper·payload·이전 암호문 보존 |
| 키 경계 | 복구 개인키는 PC의 Windows age만 사용, 서버·Linux 컨테이너로 전달하지 않음 |

이는 **PC 원본으로 재구성한 선택 파일 복구본**이며 서버 전체 capture·VM 이미지·DB 백업이 아니다. Windows 디스크 복원은 Linux uid/gid/mode를 재현하지 않는다. Linux 메타데이터는 archive 기록과 아래 실제 서버 대조로 확인했으며, 실제 Linux 복원 공간의 소유권 재현 시험과 구분한다. OS·Docker·AWS CLI 설치, TLS/IAM·저장소 정책, 새 DB 엔진 재바인딩과 앱/worker/timer 활성화는 별도 수동 복구 절차다.

사용자는 새 암호문을 **우선 PC에 보관하고 PC 밖 사본은 나중에 마련**하기로 선택했다. 기존 복구키의 PC 밖 사본 확인과 새 설정 암호문의 외부 사본은 다른 항목이며, 후자는 아직 완료하지 않았다.

재개 후 사용자가 텍스트 편집기에서 글자가 깨져 보인다고 문의한 저장본을 **22:14:57 KST**에 다시 검사했다. `.tar.gz.age`는 암호화된 바이너리이므로 일반 문서처럼 읽을 수 없는 것이 정상이다. 저장 당시 SHA256·크기·age header가 일치했고 별도 age 프로세스의 인증 복호화와 내부 36개 member·선택 34파일의 내용/기록된 Linux 메타데이터 검사를 통과했다. 암호문은 수정하지 않았고 새 평문 파일도 쓰지 않았다. 이 재검사는 앞서 완료한 실제 디스크 복원을 반복한 시험과 구분한다.

## 실제 재부팅·보존 대조

AWS 콘솔에서 기존 VM의 계획 재부팅을 **한 번 요청**하고 새 boot ID와 **17:32:50 KST** 부팅을 확인했다. **17:34:24 KST** HTTPS GET은 기본 TLS 인증서 검증을 거친 200과 기존 준비 화면을 확인했다.

첫 사후 감사는 Docker 네트워크 ID의 엄격한 비교·정렬에서 거부됐다. **17:37:42 KST** 원시 자료를 Name 기준으로 대응한 읽기 전용 진단에서 **Docker 기본 bridge의 ID 한 건만 변경**됐음을 확인했다. 전후 네트워크 이름 집합·모든 네트워크 정의와 사용자 정의 네트워크 ID, 컨테이너·볼륨·DB 내용·인증 지문은 같았다.

이전 엄격 검사가 그대로 통과했다고 처리하지 않았다. 원래 감사 도구·기준선과 원시 차이 기록을 보존한 채, 별도 사후 검사에서 해당 한 건이 전후 모두 `Name=bridge`·`Driver=bridge`·`Scope=local`·`Internal=false`·label 없음·`default_bridge=true`인지를 요구했다. 그 기본 bridge의 ID 외 모든 감사 대상 필드와 나머지 기존 guard는 동일하게 대조했다.

**17:40:16 KST** 이 한정된 ID 예외를 적용한 사후 검사를 통과했다. 컨테이너 7개·볼륨 6개, 두 DB의 각 39테이블·29시퀀스·Flyway V1~V12·데이터/인증/소유권 지문, 새 복구본과 일치하는 선택 34파일의 내용·Linux 메타데이터와 기존 별도 33파일을 보존했다. timer 4개 enabled/active·운영 Backend 중지·worker/Push 5개 flag OFF와 앱 출처·이미지 고정값도 유지한다.
