작성 기준: 2026-10-14, Asia/Seoul. 이 문서는 확정된 알림 동작과 구현 제안을 정리한다. V9·전체 공지·사이트 내 알림함과 예약/교환 사건 연동은 main에 반영됐다. service worker, Push 구독/발송, 시작 1시간 전 계획·worker와 CSRF 보완도 로컬 최종 검증·새 V9 백업의 실제 복원·개발 DB V10 적용·최신 서버 기동·원격 CI 후 사용자 승인으로 PR #17을 main에 병합했다. 실기기 Push 수신·운영 HTTPS/외부 백업 검증은 후속 단계다. V9 계약은 [NOTICES_NOTIFICATIONS](NOTICES_NOTIFICATIONS.md), 최신 구현 선택·실제 실행 결과와 제한은 [WEB_PUSH_REMINDERS](WEB_PUSH_REMINDERS.md)를 따른다. 아래의 별도 제안 전체가 구현된 것은 아니다. 관련 화면은 [UX.md](UX.md), API 계약은 [API.md](API.md), 검증은 [TEST_PLAN.md](TEST_PLAN.md)를 따른다.

## 1. 확정된 서비스 동작

- 알림함과 Web Push는 첫 운영 필수 기능이다.
- 예약 생성 시 즉시 알림을 만든다. 관리자 반복 배정에서 자동 생성한 실제 회차도 예약 생성에 포함한다.
- 예약 시작 1시간 전 알림을 제공한다. 생성·변경·교환 처리 시 그 알림 예정 시각이 이미 지났으면 소급 발송하지 않는다.
- 변경·교환·취소로 이전 예약 기준 시작 알림을 무효화하고 새 상태에 맞게 처리한다.
- 개인 예약 관련 알림은 해당 개인에게, 팀 예약 관련 알림은 해당 팀의 활성 조원 전체에게 제공한다.
- 교환 요청·거절·승인·만료·무효화 결과를 관련 당사자에게 제공한다.
- 중요 공지 알림은 전체 활성 회원에게 제공한다.
- 2026-10-13 사용자 확정: 처음 중요 공지로 작성할 때만 알림함에 안내한다. 일반 공지와 수정·일반→중요 전환·고정 해제/재고정은 재알림하지 않는다.
- 탈퇴·팀 해체 등으로 예약 또는 대기 교환이 정리되면 관련 상태와 알림도 함께 정리한다. 회원 탈퇴 시 존속 팀 예약 자체를 일괄 취소하지 않는다.

Push를 받았다는 사실이 예약 또는 교환 성공을 의미하지 않는다. 성공 여부는 서버의 확정 결과와 알림함·현재 예약 상태로 확인한다.

## 2. 필수 이벤트와 수신자

| 이벤트 | 수신자 | 시점·주의사항 |
| --- | --- | --- |
| 개인 예약 생성 | 예약자 본인 | 예약 트랜잭션 확정 후 즉시 발송 대상 |
| 팀 예약 생성 | 해당 팀의 활성 조원 전체 | 작성자 포함, 관리자 고정 회차 생성 포함 |
| 예약 변경 | 개인 본인 또는 해당 팀 활성 조원 전체 | 변경 전후 시간·자원 표시, 기존 시작 알림 무효화 |
| 예약 취소 | 개인 본인 또는 해당 팀 활성 조원 전체 | 시작 전·진행 중 취소; 종료된 예약은 취소하지 않고 이용 이력 보존 |
| 시작 1시간 전 | 개인 본인 또는 발송 시 해당 팀의 활성 조원 전체 | 현재 유효 예약과 버전을 다시 확인 |
| 교환 요청 | 양측 예약 관련 개인/활성 조원과 활성 요청자 | 승인 버튼은 상대 측 승인 권한자에게만 제공 |
| 교환 승인 | 양측 예약 관련 개인/활성 조원과 활성 요청자 | 전 건의 교환이 확정된 뒤 한 업무 결과로 표시 |
| 교환 거절 | 양측 관련 당사자와 활성 요청자 | 원래 예약 유지 |
| 교환 만료 | 양측 관련 당사자와 활성 요청자 | 관련 예약 중 가장 이른 시작 시각 기준 |
| 교환 무효화 | 양측 관련 당사자와 활성 요청자 | 예약 변경·취소, 요청자 권한 상실, 개인 탈퇴에 따른 실제 예약 취소, 팀 해체 등 사유 표시 |
| 중요 공지 게시 | 전체 활성 회원 | 공지 상세로 이동 |
| 탈퇴·해체에 따른 예약·교환 정리 | 정리 대상 예약·교환의 관련 활성 당사자 | 정리 전 필요한 대상 정보를 확보하고 현재 활성 상태 재검증 |

한 이벤트에서 같은 사용자가 여러 역할에 해당해도 알림함 항목을 중복 생성하지 않는다. 전체관리자라는 이유만으로 모든 회원의 예약 Push를 받게 하지 않는다. 관리자에게 필요한 운영 오류 정보는 업무 알림과 구분한다.

팀 알림 수신과 팀 예약 조작 권한은 다르다. 일반 조원이 요청을 읽어도 다른 작성자의 예약을 변경하거나 교환에 승인할 수 없다. UI를 우회한 승인 API 호출도 차단한다. 상대 승인 후보 한 명의 역할·소속 해제는 해당 사람의 승인 시도를 403으로 거절하는 사유이며, 다른 적법한 승인자가 있다면 요청 전체를 무효화하는 사유가 아니다.

**추가 이벤트 제안:** 팀 생성·명단 변경, 악기 사용 중지·복구에 따른 영향 안내와 일반 공지의 알림함 수록은 필수 이벤트와 구분한다. 중요 공지 수정·고정 변경의 알림함 재알림은 2026-10-13 사용자 선택에 따라 이번 계약에 포함하지 않는다. 일반 공지마다 전체 Push를 보내는 정책은 임의로 확정하지 않는다. 악기 상태는 별도 알림 여부와 관계없이 예약 화면에서 확인할 수 있어야 한다.

## 3. 생성 즉시 알림과 고정 회차

관리자 반복 패턴과 실제 날짜의 예약 회차를 구분한다. 일일 작업이 예약 가능 범위에 새 고정 회차를 생성하면 해당 회차의 생성 알림을 즉시 만든다. 14일 뒤 예약이라는 이유로 생성 알림을 시작 직전까지 지연하거나 생략하지 않는다.

회차 생성 작업의 재실행은 새 생성 이벤트가 아니다. 같은 반복 패턴·날짜 회차의 중복 생성, 알림함 항목 중복, Push 대기열 중복을 막는다. 기존 단일 회차 변경·취소·교환 예외를 다시 원래 예약으로 생성해서도 안 된다.

**Push 요약 제안:** 최초 14일 범위 생성이나 관리자 일괄 배정으로 한 트랜잭션에서 다수 회차가 생성될 때, 사용자별 알림함은 회차별로 남기고 Push만 같은 작업 단위로 즉시 요약할 수 있다. 예: 정규조 일정 4건이 등록되었습니다. 이 제안은 생성 시점에 처리한다는 정책을 유지하며, 여러 날의 생성 이벤트를 모아 나중에 보내는 방식이 아니다. 요약을 채택하기 전 기본 계약은 건별 생성 즉시 발송 대상이다.

## 4. 시작 1시간 전 알림

알림 기준은 예약 블록의 정해진 시작 시각이다. 진행 중 블록 예약에서 실제 신청 시각을 새 예약 시작 시각으로 바꾸지 않는다.

| 처리 상황 | 동작 |
| --- | --- |
| 18:00 시작 예약을 15:00에 생성 | 17:00 시작 알림 예약 |
| 18:00 시작 예약을 17:30에 생성 | 생성 알림만 즉시, 지난 17:00 시작 알림 생략 |
| 이미 시작한 18:00~19:30 블록을 18:20에 생성 | 생성 알림만 즉시, 소급 시작 알림 없음 |
| 예약을 다른 시간으로 변경 | 이전 시작 알림 무효화, 새 알림 예정 시각이 미래이면 등록 |
| 두 60분과 90분 교환 승인 | 모든 이전 시작 알림 무효화, 최종 각 예약 블록 기준 새 알림 등록 |
| 예약 취소 | 시작 알림 무효화 |
| worker 재시작 후 지난 대기 건 발견 | 현재 유효 예약·버전·현재 시각을 확인; 시작이 지난 알림은 발송하지 않음 |

**경계 처리 제안:** 생성·변경 시 시작 1시간 전 시각이 현재 시각과 같으면 생성·변경 알림을 제공하고 별도의 시작 알림은 등록하지 않는다. 현재보다 엄격히 미래인 경우만 새 시작 알림을 예약하는 계약으로 중복을 줄인다. 정확한 비교 규칙은 API·worker 구현에 동일하게 적용한다.

60분 두 예약은 블록별 예약으로 유지되므로 시작 알림도 각 블록별 기준이다. 두 블록을 이어 연습할 때 두 번째 블록 알림이 첫 블록 시작 무렵에 올 수 있음을 화면 설명에 반영한다. 미리 알림을 첫 블록 하나로 통합하는 정책은 임의로 적용하지 않는다.

**동일 시각 중복 방지 제안:** 원본 REPLACED와 후속 예약 행의 새 ID만으로 시작 알림을 식별하지 않는다. 같은 논리 예약 계보와 실제 시작 시각에는 한 번만 보내고, 예약 버전은 낡은 계획의 무효화에 사용한다. 같은 시작 시각의 악기 변경에서 이미 보낸 시작 알림을 다시 보내지 않는다. ERD의 계보 root 예약 ID 집합과 실제 시작 시각을 정규화한 reminder 식별 키를 사용하며 N:M 병합·분할에서도 이를 검증한다.

worker 지연, 네트워크, 브라우저·OS 상태 때문에 단말 표시가 정확히 1시간 전에 일어남을 보장할 수 없다. 서버의 목표 처리 시각과 실제 발송 시각을 기록한다.

## 5. 알림함과 outbox: 구현 제안

소규모 서비스에서는 PostgreSQL 기반 worker를 제안한다. Redis·Kafka·별도 메시지 브로커를 첫 운영 필수 기술로 추가하지 않는다.

1. 예약·교환·공지 상태 변경 트랜잭션 안에서 업무 이벤트, 수신자별 알림함 항목, 발송 대기 outbox를 기록한다.
2. 트랜잭션이 실패하면 상태 변경·알림함·대기 발송도 함께 롤백한다.
3. worker는 커밋된 대기 건만 처리한다. Push 네트워크 호출을 예약 DB 트랜잭션 안에서 수행하지 않는다.
4. 발송 시 예약 버전, 활성 회원, 현재 필요한 팀 소속, 구독 상태와 만료를 확인한다.
5. 처리 결과·재시도 횟수·다음 처리 시각·마지막 오류를 기록한다. 운영자가 반복 실패를 확인할 수 있게 한다.

미래 시작 알림은 예약 트랜잭션에서 **계획 job만** 저장하는 기술안을 제안한다. 계획·발송 작업은 ERD의 같은 notification_jobs 테이블에서 REMINDER_PLAN / PUSH_DELIVERY로 구분하며 계획 단계의 notification_id는 nullable다. due 시점에 현재 예약·버전·수신자를 검증하고 시작 알림함 항목과 기기별 발송 작업을 같은 트랜잭션으로 만든다. 계획 처리 완료는 COMPLETED, 기기별 발송 성공은 SENT, 무효화된 계획·발송은 CANCELED로 구분한다. 예약 생성 시 14일 뒤의 시작 알림이 현재 알림함에 곧 시작한다는 항목으로 미리 나타나지 않게 한다. 구체 연결·재시도는 ERD의 기술 계약과 일치시킨다.

개념상 필요한 데이터는 이벤트 ID·유형·발생 시각·대상과 버전, 사용자별 읽음 상태·제목·본문·내부 이동 대상, outbox 처리 상태·시도 기록, 사용자 소유 Push 구독이다. 실제 테이블명·제약은 [ERD.md](ERD.md)와 일치시킨다.

중복 방지는 이벤트와 수신자의 조합, 구독별 발송 시도, 동일 논리 예약 계보와 실제 시작 시각을 구분한다. 예약 버전은 이전 계획 무효화와 현재 배치 검증에 사용하며 단독 중복 식별키로 사용하지 않는다. worker 동시 실행에서도 같은 대기 건을 두 worker가 동시에 처리하지 않게 한다.

외부 Push 요청 성공 직후 서버가 중단되면 재시도에서 중복 표시될 수 있다. end-to-end exactly-once 전달을 약속하지 않는다. 이벤트 식별자와 service worker 알림 tag를 활용해 동일 이벤트의 중복 표시를 줄이는 방식을 제안한다. 알림함의 업무 항목 중복은 DB 제약으로 막는다.

알림함은 서버에서 보존하는 확인 경로다. Push 발송 실패·미설치·권한 거절을 이유로 알림함 항목을 없애거나 예약을 실패 처리하지 않는다. 오래된 Push가 도착하면 클릭 후 현재 상태를 조회하고 변경·취소·만료 여부를 표시한다.

원본 REPLACED와 후속 예약 생성은 하나의 논리 변경 또는 교환 사건이다. 새 DB 행을 생성했다는 이유로 CHANGED/EXCHANGED와 별도의 CREATED를 함께 발송하지 않는다. no-op 변경은 업무 이벤트와 시작 알림 교체도 만들지 않는다. 기존 ID를 담은 알림은 권한을 확인해 이력과 후속 예약 목록으로 연결한다.

## 6. 수신자·탈퇴·권한 변경

생성 이벤트의 알림함 수신자는 이벤트 발생 당시 활성 대상자를 기준으로 기록하는 방식을 제안한다. 시작 알림은 발송 시점의 활성 대상자를 계산한다. 발송 전 탈퇴·비활성화된 회원이나 관련 팀 소속을 잃은 회원에게 새로운 팀 상세 Push를 보내지 않는다.

이전에 적법하게 수신한 본인 알림함 이력과 현재 예약 조작 권한은 구분한다. 알림의 내부 링크는 현재 권한을 검사한다. 과거 알림을 읽었다는 이유로 해체된 팀이나 다른 사람의 예약 API에 접근할 수 없다.

팀 해체는 정리 대상 예약과 대기 교환을 먼저 식별하고 관련 활성 당사자에게 결과를 기록한다. 해체 이후의 빈 팀 명단만 조회해서 필요한 안내를 모두 놓치지 않는다. 개인 탈퇴는 실제 취소되는 개인 예약과 요청자 권한 상실에 해당하는 교환·계획을 정리한다. 존속 팀 예약은 creator가 탈퇴했더라도 유지하며 다른 활성 조원에게 보낼 예정 알림도 계속한다. 탈퇴자가 상대 승인 후보였을 뿐이고 다른 적법한 승인 경로가 있으면 대기 교환을 종료하지 않는다.

## 7. 구독 API와 기기 수명주기 제안

2026-10-14 회원/팀 종료 정리는 [MEMBER_TEAM_LIFECYCLE](MEMBER_TEAM_LIFECYCLE.md)에서 구현·격리 검증한다. 탈퇴는 해당 회원의 모든 기기 구독과 미전송 작업·로그인 세션을 종료하며 다른 회원의 기기와 존속 팀 예약/계획을 유지한다. 팀 해체의 취소/교환 결과는 정리 전 확보한 관련 활성 당사자의 알림함에 기록하고 현재 상세 권한을 잃은 대상의 미전송 팀 상세 Push는 종료한다. 기존 알림함과 이미 외부로 전달된 알림을 삭제/철회하는 기능은 추가하지 않는다.

2026-10-14 사용자가 Web Push·시작 알림 구현을 요청했고 **로그아웃 시 해당 기기의 Push만 중단, 다른 기기 유지**를 확정했다. V10·API·화면·CSRF 보완과 실제 검증 범위는 [WEB_PUSH_REMINDERS](WEB_PUSH_REMINDERS.md)를 따른다. 아래 기술 제안 중 구현된 선택은 해당 문서와 API/ERD에 구분해 기록한다.

API 경로는 /api/v1 아래를 기준으로 하고 최종 세부 경로는 [API.md](API.md)에 맞춘다.

| API 영역 | 책임 |
| --- | --- |
| GET /notifications | 현재 사용자 본인의 목록·읽음 상태 조회 |
| PATCH /notifications/{id}/read | 본인의 항목만 멱등 읽음 처리 |
| POST /notifications/read-all | 본인 목록을 기준 시각까지 읽음 처리 |
| GET /push/public-key | VAPID 공개 키 조회, 비밀키 제외 |
| POST /push-subscriptions | 현재 사용자와 현재 브라우저 구독 연결 |
| GET /push-subscriptions | 본인 기기 목록, endpoint 원문 최소화 |
| DELETE /push-subscriptions/{id} | 본인 소유 구독만 해제 |

서버가 인증 정보에서 구독 소유자를 결정한다. 클라이언트가 다른 userId를 보내 구독을 등록할 수 없다. 동일 endpoint 재등록은 멱등 처리하고 계정 전환 시 기존 사용자에게 연결된 구독을 그대로 재사용하지 않는다.

구독 endpoint와 공개 키는 발송용 데이터이며 로그·공지·응답에서 무분별하게 노출하지 않는다. 서버 발송 URL 검증, HTTPS, 입력 길이 검증, 구독 API 인증·권한·CSRF 처리를 적용한다. 임의 내부 URL로 서버가 발송하도록 만들지 않는다. VAPID 비밀키와 인증 secret은 서버 환경변수로 관리한다.

하나의 사용자에게 여러 기기 구독이 있을 수 있다. 기기별 실패를 전체 알림 실패로 취급하지 않는다. 만료·해지 endpoint는 비활성화하고 일시 실패는 제한된 재시도를 수행한다. 단말 OS에 알림이 표시됐는지를 서버가 발송 응답만으로 확정했다고 기록하지 않는다.

로그아웃과 계정 전환 시 이전 계정의 활성 발송 연결과 클라이언트 Query 캐시를 정리한다. service worker가 인증된 API 응답과 이전 회원의 개인정보를 오프라인 캐시로 계속 제공하지 않게 한다.

## 8. 설치와 권한 흐름

1. HTTPS 사이트에서 로그인한다.
2. Push·service worker 지원 여부를 기능 검사한다.
3. 사용자가 설치 안내와 알림 켜기 버튼을 통해 진행한다. 페이지 진입만으로 권한 창을 반복 요청하지 않는다.
4. iPhone에서는 Safari의 홈 화면 추가 기능으로 설치하고, 설치된 웹 앱을 실행한다.
5. 사용자 버튼 동작에서 알림 권한을 요청한다. 허용 시 구독을 생성해 서버에 등록한다.
6. 허용·거절·미지원·구독 실패 상태를 화면에 명확하게 표시한다. 거절 상태에는 브라우저/OS 설정 안내를 제공하고 자동 재요청을 반복하지 않는다.
7. 미설치·미허용 상태에서도 예약·공지·교환·알림함을 사용할 수 있게 한다.

iOS Web Push는 홈 화면 웹 앱에서 사용자 직접 동작으로 권한을 요청하는 조건을 고려해야 한다. 서비스 기능 필수와 사용자의 OS 알림 허용은 별개다. [WebKit 공식 설명](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

manifest, standalone, 아이콘, service worker, 설치 안내는 단일 Next.js 앱에 포함한다. Next.js 공식 가이드의 프론트엔드 PWA 기능을 참고하되, 이 프로젝트의 예약·알림 업무 로직은 Spring 백엔드에 둔다. [Next.js 공식 PWA 가이드](https://nextjs.org/docs/app/guides/progressive-web-apps)

브라우저 API의 표시·tag 기능은 구현에 활용할 수 있다. 단말 표시 결과와 업무 이벤트를 혼동하지 않는다. [MDN showNotification 문서](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification)

## 9. 첫 배포·운영 점검

- iPhone 홈 화면 앱과 Android Chrome에서 설치·허용·알림 클릭·로그아웃·재로그인을 확인한다.
- 실제 예약 생성, 변경, 취소, 교환 승인과 시작 알림을 검증한다. 단순 테스트 Push 성공만으로 완료 처리하지 않는다.
- 알림 거절 회원도 수신함과 교환 결과를 확인할 수 있는지 검증한다.
- 서버 재시작 후 알림 대기열 복구, 이전 버전 알림 무효화, endpoint 만료 정리를 확인한다.
- 운영 종료 시 앞으로의 예약 알림·Push 발송을 중단하고 필요한 이력을 백업한다. 복원 점검용 환경에서 실제 회원에게 과거 Push를 재발송하지 않는다.
