# 새 운영 구성의 실제 재부팅·복구 검증

검증일: **2026-10-27, Asia/Seoul**. 사용자 승인으로 기존 Lightsail VM을 한 번 실제 재부팅하고, 설치된 새 운영 구성과 기존 합성 환경의 보존·자동 복구를 대조했다. 이번 기록은 [운영 서버 적용·실제 백업 검증](OPERATIONAL_SERVER_VALIDATION.md)의 후속이며, [이전 합성 환경 재부팅](OPERATIONS_REBOOT_VALIDATION.md)과 별도 실행이다. 기존 rc.3 이미지와 설치된 앱·백업 실행자를 유지했다.

**이번 06:53 KST 재부팅의 관측 범위는 완료했다.** 재부팅 전후 자원·DB·설정 보존, HTTPS 준비 화면, 두 감시 서비스의 자동 실행과 07:00 KST 자연 hourly 백업·새 S3 객체 검증을 확인했다. 이어 07:05 KST 감시가 새 snapshot을 반영하고 CloudWatch OK를 유지하는지도 독립 조회로 확인했다. 실제 회원 데이터 이전·예약 앱 공개와 아래 미검증 경계는 이 결과에 포함하지 않는다.

## 재부팅 전 보호와 기준선

재부팅 전에 새 운영 DB의 수동 단발 백업을 실행했다. **06:41:05~09 KST**(2026-10-26 21:41:05~09 UTC)에 새 백업과 원격 검증을 확인하고, **06:42:16 KST** 별도 AWS 읽기 전용 검사에서 정확한 원격 객체와 서버 기록의 aggregate 일치를 대조했다. 운영 IAM 범위·보존 정책·공개 차단·Governance·정확한 SNS 경보 조건은 불변이며, 당시 CloudWatch는 OK이고 최신 지표 시각은 06:41 KST였다. 이는 재부팅 전 수동 실행으로, 부팅 후 자연 hourly 발화와 구분한다.

**06:52:16 KST** 재부팅 전 전체 검사를 마쳤다. 비공개 기준선은 원본을 덮어쓰지 않는 root 전용 영속 경로에 디렉터리 `0700`·파일 `0600`으로 보관했다. 재부팅 후 검사는 사라질 수 있는 `/run`의 보조 도구에 의존하지 않도록 했다. 새 설정 34파일의 기존 암호문과 복구 개인키 원본도 보존했다.

## 실제 재부팅과 보존 대조

AWS 콘솔에서 기존 VM의 재부팅을 한 번 요청했다. 새 부팅 시각은 **06:53:03 KST**(2026-10-26 21:53:03 UTC)이며, **06:54:24 KST** 재부팅 후 전체 검사를 통과했다. 공개 HTTPS는 **06:54:14 KST** 기본 TLS 인증서 검증을 사용한 GET 200과 기존 준비 화면 문구로 확인했다. 자연 hourly 실행 뒤 **07:01:23 KST** 전체 검사를 다시 수행해 같은 보존 결과를 확인했다. 마지막 **07:07:57 KST** HTTPS 재조회에서도 기본 인증서 검증·HTTP 200·기존 준비 화면 문구를 확인했다.

|---|---|

| 두 DB 내용 | 각각 39테이블·29시퀀스·성공한 Flyway V1~V12. 전체 행·시퀀스·Flyway 지문 일치 |
| 두 DB 인증·권한 | 역할 인증 정보·멤버십과 DB/schema/table/sequence 권한의 비공개 지문 일치 |

두 DB의 검사는 서버의 기존 합성 DB와 실회원 없는 새 운영 스키마에 한정했다. 실제 개발 DB·관리자·회원·팀·예약 데이터에는 접속하거나 이를 이전하지 않았다. 역할 인증 정보·회원 데이터·개별 비밀파일의 내용이나 지문은 공개 문서에 포함하지 않는다.

사전 검사 중 빈 Docker 출력 줄 처리와 systemd의 사람이 읽는 `LastTriggerMonotonic` 표기를 정수로 취급한 오류는 비공개 읽기 전용 보조 도구에서 보완했다. 설치된 앱·백업 실행자·컨테이너 restart 정책을 수정해 통과시킨 결과는 아니다.

## 부팅 후 자동 백업·감시 관측

재부팅 후 네 timer의 enabled/active 확인과 실제 서비스 실행·원격 백업 성공을 각각 검사했다.

| 부팅 후 독립 AWS 검사 | **06:56:16 KST** CloudWatch OK·06:55 KST의 새 지표와 snapshot 나이 약 14.09분 확인. 당시 S3는 재부팅 전 단발 백업이며 정책·서버 기록과 일치 |
| 자연 hourly 발화 | **07:00 KST** 기존 합성·새 운영 타이머 모두 원래 예약으로 자연 실행한 증빙 확인 |

| 원격 객체 독립 대조 | **07:01:24 KST** AWS 읽기 전용 검사에서 새 운영 객체의 정확한 버전·암호화·Governance와 서버 성공 기록 aggregate 일치 확인. 최신 객체의 LastModified는 **07:00:28 KST** |

07:01 KST 검사 당시 CloudWatch의 지표 시각 **07:00:00 KST**·snapshot 나이 약 **19.26분**은 새 snapshot을 만든 07:00:20보다 먼저 실행한 감시의 이전 성공 기준 값이었다. 이후 원래 다음 **07:05 KST** 감시와 독립 조회에서 **새 지표 시각·snapshot 나이 약 5.18분**을 확인해 새 성공 기록의 반영까지 검증했다. 이전 값을 새 snapshot의 성공 증빙으로 취급하지 않았다.

최종 서버 증빙에서도 컨테이너·worker flag·네 timer, 두 자연 백업 성공과 exact-version S3 aggregate가 앞선 결과와 일치했다. DB·인증·설정 전체 지문 대조의 최종 시각은 **07:01:23 KST**이며, 이후 상태 확인과 검사 범위를 구분한다. 재부팅 전 백업이나 이전 timer 실행 기록을 부팅 후 성공 증빙으로 재사용하지 않았다.

## 이번 범위와 남은 경계

기존 서버·이미지·컨테이너·볼륨·개발 데이터·설정·이전 암호문을 보존했다. 새 AWS 리소스 생성, 운영 앱/worker 활성화, 실제 회원 데이터 이전·예약 앱 공개 전환은 수행하지 않았다. GitHub 게시·커밋·Push·PR 생성도 이번 승인 범위에 포함하지 않는다.

이 시험은 실회원 없는 새 운영 원본과 기존 합성 환경의 재부팅 복구 검사다. 실제 데이터의 최종 백업·쓰기 동결·독립 복원·이전 후 대조와 운영 origin 로그인/예약/Push 검증, 공개 전환은 후속 승인 단계다. 장시간 VM 장애·전체 서비스 재난 복구·부하 용량·전체 RPO/RTO 달성은 이 짧은 재부팅 시험으로 증명하지 않는다. 최신 34파일 암호문의 PC 밖 추가 사본 확인도 별도 항목으로 남긴다.

이번 재부팅은 정각을 건너지 않아 놓친 예약의 `Persistent` catch-up과 PostgreSQL 동시 기동 경합을 검증하지 않았다. 재부팅 당시 설치된 이전 백업 실행자에는 별도 PostgreSQL 준비 guard가 없었다. 후속 로컬 보완과 격리 systemd 검증은 [준비 대기 검증](OPERATIONAL_READINESS.md)을 따르며 새 guard는 아직 운영 서버에 적용하지 않았다. 당시 보호 범위의 한계이며 이번 재부팅에서 백업 실패가 발생했다는 뜻은 아니다.

실제 계정·IP·버킷·키·VersionId·개별 비밀파일 지문·자격증명·DB 덤프와 상세 실행 증빙은 Git 제외 비공개 위치에만 보관한다.
